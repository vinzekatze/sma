## 1. Гипотезы

**H1 (основная):** Oracle_p при расширении сетки до [2..80] систематически уходит за пределы 16. Если это так — прошлые эксперименты (скр.83-94) недоизмеряли размерность, и их выводы («r≈0 окончательно») преждевременны.

**H2:** Распределение oracle_p в [2..80] имеет выраженную структуру (не равномерное). Наличие пиков/впадин означает, что аттрактор предпочитает определённые масштабы, и это предсказуемо.

**H3:** Oracle потолок (rMAE при знании истинного oracle_p) значительно улучшится по сравнению с потолком при p∈[4..16] (скр.94: −67%).

**H4 (вспомогательная):** Ensemble 1/LOO в расширенном диапазоне покажет улучшение или деградацию по сравнению с −12.41% (скр.93). Результат определит, полезно ли расширение для практического метода.

## 2. Концепции, терминология, обозначения

| Обозначение          | Расшифровка                                                                                                                                                                                             |             |                                                              |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- | ------------------------------------------------------------ |
| **att**              | Аттрактор — выход Local Projective фильтра (m=9, d=3, k=30, n=3) применённого к ratio (close/logtrend). Медленная компонента биржевого ряда, которую мы прогнозируем.                                   |             |                                                              |
| **logtrend**         | Причинный OLS-тренд в логарифмической шкале. ratio = close / exp(a + b·t).                                                                                                                              |             |                                                              |
| **p_reg**            | Размерность регрессии: сколько последних значений att используется как вектор признаков в LWR. В прошлых экспериментах ограничивалось [4..16].                                                          |             |                                                              |
| **P_MAX**            | Максимальная размерность поиска соседей. X_full хранит P_MAX последних значений att для каждой библиотечной точки. Здесь P_MAX=300.                                                                     |             |                                                              |
| **p-aligned каскад** | Уровни каскада = p_reg × {1, 2, 4, ...} ≤ P_MAX (скр.93). Гарантирует вложенность: соседи, близкие в 2p-мерном пространстве, близки и в p-мерном. Пример: p=9 → [288, 144, 72, 36, 18, 9].              |             |                                                              |
| **ξ (xi)**           | Количество соседей для LWR. Правило: ξ = 3·(p+1)+5. При p=2: ξ=14; при p=80: ξ=248.                                                                                                                     |             |                                                              |
| **N_lib**            | Размер библиотеки (количество исторических точек, пригодных для поиска соседей). N_lib = N_bars − P_MAX. Для SBER 1d: 4829 − 300 = 4529.                                                                |             |                                                              |
| **acc_ang**          | Метрика поиска соседей: d_pos + λ·d_ang(acc). d_pos — евклидово расстояние в p_reg-мерном пространстве att; d_ang(acc) — косинусное расстояние между векторами ускорения (второй разности att). λ=0.01. |             |                                                              |
| **oracle_p**         | «Идеальный» p_reg: тот, при котором прогноз для данного origin был бы ближе всего к истинному значению. Знать заранее невозможно — верхняя оценка потенциала метода.                                    |             |                                                              |
| **oracle rMAE**      | rMAE (relative MAE) при выборе oracle_p: MAE(ошибок) / std(att).                                                                                                                                        |             |                                                              |
| **ensemble 1/LOO**   | Взвешенный ансамбль прогнозов по всем p_reg, вес = 1/LOO_error.                                                                                                                                         |             |                                                              |
| **LOO**              | Leave-One-Out кросс-валидация на наборе соседей. Оценивает качество модели без использования истинного будущего.                                                                                        |             |                                                              |
| **rMAE**             | relative MAE = mean(                                                                                                                                                                                    | pred − true | ) / std(att). Нормировка на std позволяет сравнивать тикеры. |
| **origin**           | Точка во времени, для которой строится прогноз (последняя известная свеча). Walk-forward: перебираем 20 origins с шагом 10 баров в хвосте ряда.                                                         |             |                                                              |

## 3. Методология и протокол

### Walk-forward схема
Для каждого origin t:
1. Берём исторические данные att[:t+1]
2. Формируем библиотеку: X_full (N_lib × 300), X_acc_full (N_lib × 300)
3. Для каждого p_reg ∈ P_REG_GRID:
   - Строим p-aligned каскад levels_aligned(p_reg, P_MAX=300)
   - Выполняем каскадный поиск ξ соседей с acc_ang метрикой
   - Вычисляем LWR прогноз и LOO-ошибку
4. Записываем все результаты в JSONL (онлайн, до следующего origin)
5. После всех origins: вычисляем oracle_p per origin, строим фигуры

### Построение X_full и X_acc_full
Используем `numpy.lib.stride_tricks.sliding_window_view` для O(1) построения матриц без копирования:
- X_full[i] = att[t_arr[i]-P_MAX+1 : t_arr[i]+1] — последние P_MAX значений att в момент t_arr[i]
- X_acc_full[i] — то же для acc (второй разности att)
- Матрицы строятся один раз per origin, используются для всех p_reg

### Метрика качества прогноза
rMAE = mean(|pred_i − true_i|) / std(att) по всем origins.

## 5. Критика постановки

**5.1 ξ несопоставим между p_reg**
При адаптивном ξ=3(p+1)+5: p=2→ξ=14, p=80→ξ=248. LOO-ошибки при разных p структурно разные — у малых p меньше соседей, модель хуже определена, LOO выше. Ensemble 1/LOO смещён к малым p. Вывод: ensemble в 95a носит иллюстративный характер; основной результат — oracle_p распределение.

**5.2 Агрессивный каскад для малых p**
p=2: каскад [256, 128, 64, 32, 16, 8, 4, 2] — 8 уровней. Ранние уровни фильтруют в 256-мерном пространстве при ξ=14, то есть оставляют 14 из 4529 кандидатов и расширяют на ±128 шагов. Это радикальная фильтрация. Может быть, что малые p получат систематически худших соседей из-за этого. Зафиксировано как нюанс, исследуется в 95b.

**5.3 Один тикер**
SBER может иметь специфическую динамику, не типичную для всех 8 тикеров. Обобщение результатов требует повторения на полном наборе (эксперимент 95c).

**5.4 P_MAX=300 и малые p_reg**
Для p_reg=2 верхний уровень каскада — 256 (не 300, так как 256 — максимальная степень 2, не превышающая 300). Для p_reg=75 верхний уровень — 300 (75×4=300). Небольшая асимметрия: некоторые p_reg используют пространство меньше P_MAX.

**5.5 Отсутствие оценщиков d_local**
95a — чисто диагностический. Оценщики d_local добавляются в 95b после понимания oracle_p распределения.

## 7. Анализ и выводы

### H1 — ПОДТВЕРЖДЕНА
69.4% oracle_p > 16. Эксперименты скр.83–94 с P_REG_GRID=[4..16] систематически недоизмеряли пространство поиска и обрезали более половины потенциально оптимальных p. Вывод «r≈0 — не артефакт» из скр.94 был преждевременным.

### H2 — ОТКЛОНЕНА
oracle_p не имеет выраженной структуры. CDF практически линейна → oracle_p близок к равномерному на [2..80]. Аттрактор не «предпочитает» конкретный масштаб. Q25=13, Q75=53 — широкий диапазон.

### H3 — ЧАСТИЧНО
Oracle потолок −92.2% против −67% из скр.94. Но это артефактно завышено (winner's curse при 79 p). Реальное улучшение потолка за счёт расширения диапазона есть, но точное значение требует нейтрализации инфляции (например, split-half подход).

### H4 — ПОДТВЕРЖДЕНА
Ensemble 1/LOO: −16.1% vs −12.41% (скр.93). Расширение диапазона p улучшило ансамбль. Однако значительная часть улучшения обусловлена тем, что 1/LOO-веса тяготеют к малым p (где LOO ниже), а малые p в среднем лучше на длинной истории.

### Ключевой отрицательный результат: LOO не является p-селектором

`loo_optimal_p` выбирает преимущественно p∈{2,3,4,5}. Корреляция с oracle_p: r=−0.066 (r²=0.004) — практически ноль. LOO систематически переоценивает качество малых p из-за **проклятия размерности**: в 80-мерном пространстве соседи объективно дальше, LOO-ошибка выше, независимо от качества прогноза. LOO полезен как вес в ансамбле (большие p получают меньший вес), но непригоден как критерий выбора единственного p.

### Парадокс: rMAE(p) растёт, но oracle_p равномерен

На ПЕРВЫЙ ВЗГЛЯД противоречие: если малые p лучше в среднем, почему oracle чаще выбирает большие?

Объяснение — **дисперсия предсказания растёт с p**: при большом p прогноз иногда очень точен (oracle его выбирает), но в среднем хуже. При малом p предсказание стабильнее, но без высоких точностей. Это согласуется с эффектом каскада: малые p получают больше уровней фильтрации (глубокий каскад), что стабилизирует соседей. Большие p — меньше уровней, более «случайные» соседи, выше дисперсия.

## 8. Дальнейшие направления

### 95b — Оценщики d_local (следующий приоритет)

LOO не работает как p-селектор. Нужны независимые от LOO оценщики локальной размерности:
- **Levina-Bickel (LB)**: d̂ = (K−2) / Σlog(r_K/r_i)
- **local TwoNN**: TwoNN на K ближайших соседях query (не глобально)
- **local PCA**: количество главных компонент, объясняющих ≥90% дисперсии в K-окрестности

Параметры 95b: p_search ∈ {20, 40, 80} (для поиска соседей оценщика), K_dim ∈ {50, 100, 200}, N_origins=200.

### 95c — Повторение на 8 тикерах

SBER может быть нетипичен. Результаты (прежде всего форма oracle_p распределения и rMAE(p) кривая) требуют верификации на полном наборе.

### Режимный анализ

t_orig ∈ [2328..4823] покрывает разные рыночные периоды. Разбивка по режимам (спокойный/волатильный по ATR или VIX) может объяснить, в каких условиях работают большие p и есть ли предпочтение масштаба внутри режима.

### Нейтрализация oracle inflation

Winner's curse при 79 p делает oracle rMAE (0.0179) нереалистичной оценкой. Методы нейтрализации: split-half oracle (отдельные origin для выбора p и для оценки) или bootstrap-коррекция.
