## 1. Гипотезы

**H1 (основная):** Хотя бы один из оценщиков d_local (LB, TwoNN_local, PCA) показывает значимую корреляцию с oracle_p (r² > 0.05). Если это так — оценка размерности помогает выбирать p_reg без знания будущего.

**H2:** Оценка d̂ чувствительна к p_search — размерности, в которой ищутся соседи для расчёта d. Если r²(d̂, oracle_p) меняется с p_search, значит поиск в пространстве правильной размерности критичен.

**H3:** При `p_search ≈ oracle_p` (то есть при p_search, близком к истинной оптимальной размерности) оценка d̂ лучше коррелирует с oracle_p, чем при далёком p_search. Это косвенно подтвердит, что оценщики работают, но требуют правильного масштаба.

**H4 (отрицательная, нулевая гипотеза):** Как показал 95a, LOO не предсказывает oracle_p (r²=0.004). Ожидается, что d̂-оценщики дадут r² > 0.004 — любой результат выше этой планки уже информативен.

## 2. Концепции, терминология, обозначения

| Обозначение | Расшифровка |
|---|---|
| **att** | Аттрактор — выход Local Projective фильтра (m=9, d=3, k=30, n=3). Медленная компонента, которую прогнозируем. |
| **oracle_p** | p_reg, дающий минимальную \|pred−true\| для данного origin. Требует знания будущего — верхняя граница. Берётся из 95a. |
| **p_search** | Размерность вложения, используемая ПРИ ПОИСКЕ соседей для оценки d̂. Отдельный параметр, не p_reg прогноза. Три значения: {20, 40, 80}. |
| **K_dim** | Количество ближайших соседей, используемых оценщиком d_local. Три значения: {50, 100, 200}. |
| **d̂_LB** | Оценка по Levina-Bickel: d̂ = (K−2) / Σlog(r_K/r_i), i=1..K−1. Метод MLE для локальной размерности, асимптотически несмещённый при K >> d. |
| **d̂_TwoNN** | Локальный TwoNN: для каждого из K_dim соседей вычисляем r2/r1 (отношение 2-го и 1-го расстояния), d̂ = log(2) / E[log(r2/r1)]. Применяется к K_dim соседям запроса, не ко всей библиотеке. |
| **d̂_PCA** | Эффективная размерность SVD: число главных компонент матрицы K×p_search, объясняющих ≥90% дисперсии. |
| **r²(d̂, oracle_p)** | Коэффициент детерминации — главная метрика 95b. Насколько оценщик объясняет вариацию oracle_p. |
| **LOO** | Leave-One-Out кросс-валидация. В 95a показала r²=0.004 — нижняя планка для сравнения. |
| **N_lib** | Размер библиотеки = N_bars − P_MAX. Для SBER 1d: 4529. |
| **null test** | Прогон на перемешанном (shuffled) att — d̂ на случайных данных должна упасть до ~1. Контроль что оценщик измеряет структуру ряда, а не артефакт алгоритма. |

## 3. Методология и протокол

### 3.1 Использование данных 95a

Для каждого origin из 95a уже известен `oracle_p`. Используем те же 200 origins (подвыборка из 500), чтобы сэкономить время и обеспечить согласованность.

Выбор 200 origins: равномерно из 500 (шаг 2 или 3 — зависит от числа origins в JSONL).

### 3.2 Алгоритм per-origin

Для каждого origin t:

1. Строим библиотеку X_full (N_lib × P_MAX) — идентично 95a.
2. Берём query-вектор `vec_query = att[t-p_search+1 : t+1]` (последние p_search значений).
3. Ищем K_dim ближайших соседей в p_search-мерном пространстве (L2; без acc_ang — оценщик d не нуждается в анг. компоненте).
4. На K_dim соседях вычисляем d̂_LB, d̂_TwoNN, d̂_PCA.
5. Повторяем для всех комбинаций (p_search ∈ {20,40,80}) × (K_dim ∈ {50,100,200}).
6. Записываем в JSONL.

### 3.3 Null test

Один прогон с `att_shuffled = np.random.permutation(att)` — те же origins, p_search=40, K_dim=100. Ожидаем d̂ ≈ p_search (нет структуры → все направления равнозначны).

### 3.4 Корреляционный анализ

После сбора всех d̂ per origin:
- Вычисляем r(d̂_method, oracle_p) для каждой комбинации (method, p_search, K_dim)
- Строим тепловую карту r² по (method × p_search) для K_dim=100
- Scatter-plot лучшей комбинации

## 5. Критика постановки

**5.1 Замкнутость (circular p_search)**
Оценщик d̂ вычисляется в пространстве размерности p_search. Если оптимальный p_reg=40, а мы ищем соседей при p_search=20 — мы смотрим в неправильное пространство. Это ключевой параметр 95b: три значения p_search проверяют чувствительность к этому выбору.

**5.2 LB при d̂ >> K/log(K)**
Levina-Bickel даёт смещённую оценку, если истинная размерность сопоставима с K. При d̂≈40 и K_dim=50 оценка ненадёжна. Значение K_dim=200 добавлено именно для этого случая.

**5.3 Соседи по L2, не по acc_ang**
В 95a соседи для LWR ищутся с acc_ang метрикой. Здесь для оценки d̂ используется чистый L2 — методологически проще и стандартно для оценщиков размерности. Это вносит несоответствие: oracle_p найден acc_ang-соседями, а d̂ — L2-соседями. Если оценщик покажет r²>0, следующий шаг — проверить, улучшит ли acc_ang метрику.

**5.4 oracle_p из 95a ≠ глобальный oracle**
oracle_p в 95a выбирался при acc_ang-поиске. Если бы поиск был L2, oracle_p мог быть другим. Сравнение d̂_L2 с oracle_p_acc_ang — частично смешанный эксперимент.

**5.5 Winner's curse в oracle_p**
oracle_p из 95a артефактно завышен (79 p на 500 origins — соотношение 6.3:1). Корреляция r² с oracle_p может быть занижена из-за шума в oracle_p. Более точный oracle потребовал бы split-half подхода.

**5.6 Один тикер**
Результаты могут быть специфичны для SBER. Обобщение — в 95c.

## 7. Анализ и выводы

### H1 — ОТКЛОНЕНА
Ни один оценщик не показал r²>0.05. Лучший результат — PCA (r²=0.015, p_val=0.086) — практически не отличается от нуля. Локальная размерность аттрактора не предсказывает oracle_p.

### H2 — ОТКЛОНЕНА
r²(d̂, oracle_p) не зависит от p_search: все значения ≈ 0 при p_search ∈ {20, 40, 80}. Выбор пространства для оценки размерности не влияет на результат.

### H3 — ОТКЛОНЕНА
Нет корреляции ни при каком p_search.

### H4 — ФОРМАЛЬНО ПОДТВЕРЖДЕНА, содержательно нет
Лучший r²=0.015 формально выше планки LOO (r²=0.004). Но это несущественно.

### Ключевые выводы

**1. Локальная размерность att стабильна.** Оценки d̂ по разным origins очень близки (std/mean ≈ 10-15%). Аттрактор в p_search-D пространстве имеет примерно одинаковую локальную структуру независимо от положения в att. Это объясняет нулевую корреляцию: если d̂ не меняется, оно не может предсказать переменный oracle_p.

**2. Null test подтверждает: структура в att есть.** Реальный att даёт d̂_LB≈10 vs shuffled d̂_LB≈20 при p_search=40. Оценщики работают корректно — они находят структуру. Но структура не меняется от точки к точке.

**3. TwoNN в локальной окрестности даёт артефактно малые d̂.** d̂_TwoNN≈2–3 независимо от p_search. Вероятная причина: временные соседи (t±1, t±2) всегда ближайшие в K-наборе, образуя концентрированный кластер — алгоритм видит "1D нить" и оценивает d̂≈1–3. TwoNN в данном контексте непригоден без исключения временных соседей.

**4. oracle_p управляется не размерностью, а чем-то другим.** Возможные кандидаты (не проверенные): локальное SNR (соотношение сигнал/шум), плотность библиотечных точек в окрестности, кривизна аттрактора, рыночный режим. Winner's curse также вносит шум в oracle_p.

## 8. Дальнейшие направления

### Исключение временных соседей в TwoNN
TwoNN искажён близкостью соседних временны́х точек. Нужно исключить точки |t_lib − t_query| < min_lag (например, min_lag = P_MAX) из K-набора. Может дать более реалистичную оценку d̂.

### Нормированный LOO как p-selector
LOO в 95a систематически выбирает малые p из-за меньшего ξ. Если нормировать LOO на std(y_nn) / sqrt(ξ) — убрать зависимость от числа соседей — возможно, получим менее смещённый p-selector. Проверяется без нового прогона из данных 95a.

### SNR как предиктор oracle_p
Гипотеза: в шумных периодах (высокий SNR noise/att) маленькое p устойчивее; в спокойных — большое p выигрывает. SNR вычисляется из уже имеющегося сигнала att и noise = ratio − att.

### 95c — повторение на 8 тикерах
SBER один. Если картина повторяется на 8 тикерах, результат надёжен.

### Принять равномерность oracle_p как факт
oracle_p ≈ Uniform[2..80] и не предсказуем стандартными оценщиками. Это означает, что оптимальная стратегия — робастный ансамбль (все p, 1/LOO-взвешивание), а не p-selection. Ансамбль 95a уже даёт −16% rMAE. Следующий шаг — улучшить ансамблирование, не p-selection.
