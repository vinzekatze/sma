# 25 — Волатильность-нормированный (адаптивный) порог зигзага

## 1. Гипотезы

- Наблюдение пользователя (из ручной работы с app8): точность резко падает,
  когда резко меняется масштабность прогнозируемого события. Гипотеза:
  причина — фиксированный порог T гарантирует только МИНИМУМ размера
  события (после подтверждения плечо может вырасти сколь угодно), а не
  верхнюю границу — события неоднородны по масштабу.
- Предложение: адаптивный порог `T[t] = k · vol[t]` (vol — каузальная
  скользящая волатильность), растягивающийся/сжимающийся вместе с текущим
  режимом рынка — ожидание, что подтверждённые события станут более
  однородны по масштабу ОТНОСИТЕЛЬНО момента.
- ⚠️ Не то же самое, что уже проваленная идея "волатильность как
  ПРИЗНАК/ВЕС готового прогноза" (эксп.19h, r≈0) — здесь волатильность
  определяет саму НАРЕЗКУ событий (сегментацию), до всякого прогноза.

## 2. Концепции, терминология, обозначения

- **vol[t]** — каузальное скользящее std дневных лог-доходностей, окно=60
  (тот же W, что vol60 в эксп.19h), `pandas.Series.rolling(60).std()`.
- **k** — новый калибруемый параметр, заменяющий T_big по смыслу
  ("сколько стандартных отклонений должно накопиться для подтверждения
  пивота").
- **T_frac-уровень** — тот же принцип: `k_frac = T_ratio × k_big`,
  применяется к ТОЙ ЖЕ волатильности (своей у каждого тикера/пира).

## 3. Методология и протокол

SBER, D_allpeers. Тот же протокол, что эксп.21/23/24: подбор k под
сопоставимое (73) число пивотов, независимая калибровка (m,θ,T_ratio).
Пиры считают СВОЮ волатильность (причинно), используют тот же k/T_ratio.

**Каузальность проверена явно** (по требованию пользователя — прошлые
баги были именно с протаскиванием ограничителей через функции): кэш
тикеров хранит ПОЛНЫЕ массивы, обрезка — прямым срезом `[:cutoff_idx]` на
месте использования (тот же паттерн, что exp17). `vol`, посчитанная на
всей истории и обрезанная срезом, эмпирически ИДЕНТИЧНА пересчитанной на
уже обрезанных данных (проверено на 7 точек обрезки, 0 расхождений) —
скользящее окно строго обратно во времени, обрезка после не может задеть
значения до точки обрезки.

## 4. Параметры

```
VOL_WINDOW=60, K_SEARCH_GRID=[1.0..12.0] шаг 0.25, N_TARGET=73 пивота
M_GRID=[2,3,4,5], THETA∈[0,32], T_ratio∈[0.50,0.95]
```

## 5. Критика постановки

- Только SBER, один способ измерения волатильности (std дневных
  доходностей, окно=60) — другие меры (ATR, EWMA) не проверялись.
- Подбор k под пивот-каунт (грубый критерий), не что-то более
  содержательное.
- Признаки S-map (сырые лог-разности между пивотами) остаются
  АБСОЛЮТНЫМИ — не нормируются по волатильности момента их формирования,
  хотя сам порог адаптивен. Это могло быть источником проблемы (см. §7).

**Калибровка НЕ сошлась** — θ/T_ratio колеблются между двумя состояниями

этой сессии (symmetric/asymmetric/SSA/logtrend).

## 7. Анализ и выводы

- **Адаптивный порог даёт rMAE хуже обоих эталонов** (+10.3% к symmetric,
  +13.1% к asymmetric), несмотря на точный подбор числа пивотов (73/73).
- **Осцилляция калибровки — самостоятельный тревожный сигнал**: покоорди-
  натный спуск обычно быстро находит устойчивую точку (весь эксп.17-24),
  здесь — не находит. Вероятная причина: k*vol[t] даёт РАЗНЫЙ фактический
  порог в разные периоды истории (в зависимости от локального режима
  волатильности) — плечи-признаки для S-map формировались под
  фактически разными "эффективными T" в разные эпохи, но сравниваются
  между собой S-map в АБСОЛЮТНЫХ (не нормированных по волатильности
  момента формирования) единицах. Цель "однородность ОТНОСИТЕЛЬНО
  момента" достигнута для порога, но не для признаков, которые потом
  сравниваются друг с другом.
- **Тот же паттерн, что SSA (21) и logtrend (24)**: попытка "улучшить"
  механизм формирования событий перед крупномасштабным зигзагом снова
  вредит. Три из трёх попыток такого рода в этой сессии — отрицательны.

## 8. Дальнейшие направления

- Если возвращаться к идее: нормировать САМИ ПРИЗНАКИ (лог-разности между
  пивотами) на волатильность момента их формирования, не только порог
  сегментации — это может устранить несостыковку, отмеченную в §7, но
  добавляет ещё один слой сложности.
- Другие меры волатильности (ATR, EWMA) и окна — не проверялись.
- Учитывая накопленный паттерн (3/3 отрицательных попытки "улучшить"
  вход зигзага для крупного масштаба) — приоритет этому направлению
  невысокий без нового веского аргумента.
