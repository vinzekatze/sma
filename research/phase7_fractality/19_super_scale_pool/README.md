# 19 — Пул крупнее T_big (гипотеза «нехватка больших плеч»)

## 1. Гипотезы

- **H1**: калиброванная S-map (эксп.17f) систематически недооценивает крупные
  движения (Stage 1g) из-за нехватки в пуле физических примеров с большими
  плечами — T_big-пивотов у одного тикера физически мало (то же H1 из
  эксп.17). Добавление в пул событий КРУПНЕЕ T_big (T_super, свой тикер +
  кросс-тикерные пиры, тот же D_allpeers) должно скорректировать это.
- Отличие от уже закрытой ветки (17i/17k/17l/17o, «Попытки исправить
  недооценку амплитуды — три раза отрицательный результат»): там правился
  ГОТОВЫЙ выход модели статистической коррекцией; здесь — физически новая
  информация в самом пуле, до регрессии.

## 2. Концепции, терминология, обозначения

- **T_super** — порог зигзага крупнее T_big. `T_super = T_big / T_ratio_super`
  (по аналогии с T_frac = T_ratio_frac × T_big).
- **«Зеркало»** — гипотеза, что T_ratio_super = T_ratio_frac = 0.8987
  (тот же принцип «ratio соседних масштабов ≈0.85-0.9», примененный вверх,
  а не вниз). Явно помечено пользователем как «математически красиво, но
  не обязано быть верным» — отсюда сетка, а не одна точка.
- **Дедуп** — единый проход по объединённому (после конкатенации всех
  источников и фильтра направления) пулу, `d_to_query < DUP_EPS` — тот же
  механизм, что в эксп.17/18, автоматически покрывает дубли из любого
  источника. n_dup считается отдельно по источнику (frac/super) для
  диагностики.
- **Фаза A** (этот прогон) — быстрый тест на ФИКСИРОВАННОЙ калибровке
  эксп.17f (m=3, θ=25.697, T_ratio_frac=0.8987), сетка T_ratio_super.
- **Фаза B** (следующий шаг, не запущена) — полная совместная калибровка
  (m, θ, T_ratio_frac, T_ratio_super) на объединённом пуле, только S-map.

## 3. Методология и протокол

SBER, T_big=20%, D_allpeers (45 тикеров). Каузальный контракт как в
эксп.17: физическая обрезка `arr[:cutoff_idx]` целевого ряда и каждого пира
на каждом шаге walk-forward. Пул на каждом origin = own_T_big (как в
эксп.17) + own_T_frac + peers_T_frac(D_allpeers, T_ratio_frac=0.8987,
ФИКСИРОВАНО) + **own_T_super + peers_T_super(D_allpeers, T_super из сетки)**.
Направление, дедуп, S-map прогноз (θ=25.697) — без изменений относительно
эксп.17.

## 4. Параметры

```
TARGET=SBER, T_BIG=0.20, ARM=D_allpeers
M=3, THETA=25.697, T_RATIO_FRAC=0.8987 (зафиксировано, калибровка 17f)
T_RATIO_SUPER_GRID = [0.60, 0.70, 0.80, 0.8987, 0.95]
```

## 5. Критика постановки

- Признаки (лог-диффы соседних пивотов) не нормированы порогом — T_super-
  строки физически крупнее по модулю, чем T_big-запрос; при фиксированном
  θ=25.697 (калиброванном под пул без них) это может искажать веса S-map
  независимо от того, несёт ли T_super полезный сигнал в принципе.
  Фаза A **не может отличить** «идея не работает» от «θ не подходит для
  нового пула» — для этого нужна Фаза B.
- Собственных T_super-пивотов у SBER мало (T_super=21-33% > T_big=20% —
  реже, чем T_big-пивоты) — вся практическая опора на кросс-тикерный пул.
- Сетка грубая (5 точек, шаг 0.05-0.1) — точный оптимум (если он есть)
  может быть между узлами; Фаза B (golden-section) даст точную оценку.

## 7. Анализ и выводы (предварительно, Фаза A)

- На фиксированной калибровке 17f добавление T_super-пула **везде хуже
  baseline**, монотонно: чем ближе T_super к T_big (ratio→1), тем меньше
  вред, без немонотонного оптимума в районе зеркального значения 0.8987.
  Зеркальная гипотеза **не подтвердилась** как есть — 0.95 (T_super=21.05%,
  почти T_big) даёт меньше вреда, чем 0.8987.
- Интерпретация неоднозначна: при ratio→1 T_super→T_big, добавка становится
  почти избыточной (дублирует own_big), поэтому «меньше вреда» там ожидаемо
  само по себе, а не обязательно сигнал в пользу гипотезы.
- Результат Фазы A **не опровергает и не подтверждает** H1 окончательно —
  старое θ калибровано под другой (меньший, без T_super) пул; вопрос,
  открыт ли потенциал при пересчёте θ/m под новый пул, остаётся для Фазы B.

## 8. Дальнейшие направления

- **Фаза B** — совместная калибровка (m, θ, T_ratio_frac, T_ratio_super)
  на объединённом пуле, только S-map — решение о запуске за пользователем,
  учитывая, что Фаза A пока не показывает многообещающего среднего сигнала
  (но см. стратификацию ниже).
- Если Фаза B тоже не даст выигрыша — ветка «добавить крупный масштаб»
  закрывается, аналогично «недооценке амплитуды» (17i/17k/17l/17o).

## 9. Стратифицированная проверка (19b_stratified.py) — уточнение Фазы A

Мотивация (пользователь, по 3D-визуализации): крупным движениям часто не
хватает крупных соседей — средний rMAE по всем 42 origin мог смазать эффект,
если он локализован в подмножестве «запрос уже крупный». Без нормировки
признаков (как и просили) — терции по норме вектора запроса `‖qvec‖` (размер
ПРОШЛЫХ известных плечей) и отдельно по размеру ФАКТИЧЕСКОГО следующего
плеча (то, что реально недооценивалось в Stage 1g). n≈14 на терцию —
экспериментально малая выборка, только ориентир.

**По ‖qvec‖ (прошлое)**: терция «крупное прошлое движение» и так лучший
случай для baseline (rMAE=0.408, лучше чем «типичное» 0.734-0.948) —
добавление T_super везде хуже baseline в этой терции. Размер прошлых
плечей слабо связан с размером будущего в этих данных.

**По фактическому будущему плечу (`actual_leg_abs`)**: терция «крупное
будущее движение» — худший случай baseline (rMAE=0.795, хуже, чем
«типичное» 0.230-0.518) — это и есть недооценка амплитуды из Stage 1g.
T_super-пул **улучшает именно эту терцию**: лучший результат при
T_ratio_super=0.70-0.80 (T_super=25-28.6%) — rMAE 0.762/0.721 против
baseline 0.795 (до −9%). Но те же T_ratio_super резко ухудшают «мелкую»
терцию (1.18-1.24 против baseline 0.518 — почти вдвое хуже), из-за чего
общий (по всем origin) rMAE проигрывает — ровно то, что видно в Фазе A.

**Вывод**: гипотеза частично подтверждена — механизм правдоподобен именно
там, где движение оказалось крупным. Но (а) n=14 на терцию — не
доказательство, (б) слепое подмешивание T_super вредит типичному
большинству сильнее, чем помогает редким крупным случаям, (в) нет
причинного (известного заранее) признака «наступает крупное движение»,
который позволил бы включать T_super пул только когда нужно — терция по
ПРОШЛЫМ плечам для этого не годится (слабая связь с будущим размером).

Результаты: `results/phaseA_stratified_wide.csv`,
`results/phaseA_stratified_rmae_qvec_norm_PAST.csv`,
`results/phaseA_stratified_rmae_actual_leg_FUTURE.csv`.

## 10. Дальнейшие направления (обновлено)

- Искать причинный ex-ante признак «крупное движение приближается» (не
  ‖qvec‖ прошлых плечей — не сработало) — кандидаты: волатильность/ATR
  последних баров, efficiency ratio (уже проверялся в 17o для коррекции
  амплитуды и не сработал, но не проверялся как гейт для ВКЛЮЧЕНИЯ
  T_super-пула — разные постановки), давность последнего крупного T_super
  события.
- Если такой признак найдётся — адаптивное включение T_super пула только
  при его срабатывании, а не блокировка.
- Фаза B (совместная калибровка) может частично смягчить компромисс
  small/mid vs large за счёт θ, но едва ли уберёт его полностью, если
  механизм действительно конфликтующий (типичные и крупные случаи требуют
  разного веса на T_super-соседей).

## 11. Фаза B — совместная калибровка (19c_calibrator.py) — РЕЗУЛЬТАТ

Покоординатный спуск (m → θ → T_ratio_frac → T_ratio_super), только S-map,
структура идентична 17f_calibrator.py с добавленным 4-м измерением. Сошёлся
за 4 внешних итерации, 166.6с.

```
Эксп.17f (без T_super, откалиброван):                  rMAE=0.6049  (m=3 θ=25.697 T_ratio=0.8987)
Эксп.19 старая калибровка + T_super:                   rMAE=0.6574  (не переоткалибровано)
Эксп.19 совместная калибровка (m,θ,T_frac,T_super):    rMAE=0.6542  (m=2 θ=28.384 T_ratio_frac=0.9046 T_ratio_super=0.7770 → T_super=25.74%)
```

**Гипотеза пользователя про меньший θ не подтвердилась** — оптимизатор
выбрал БОЛЬШЕЕ θ (28.4 против 25.7 у baseline), то есть более
локализованную, не более глобальную регрессию. При этом **T_ratio_super
сошёлся к 0.777 (T_super≈25.7%)** — это ровно диапазон 0.70-0.80,
показавший лучший результат для «крупной будущей» терции в стратификации
(19b); оптимизатор нашёл тот же компромисс эмпирически.

**Вывод**: полная совместная калибровка НЕ отыгрывает разрыв — 0.6542 всё
ещё хуже 0.6049 без T_super. H1 (T_super-пул улучшает среднее качество)
отклонена даже после честной перекалибровки под новый пул — компромисс
«помогает на крупных движениях (19b, до −9%), вредит на типичных»
структурный и не устраняется подбором m/θ/T_ratio. Блочное добавление
T_super-пула как замена текущего пайплайна — закрыто. Точечная польза на
подмножестве крупных движений (19b) остаётся валидной находкой, но требует
причинного ex-ante гейта, которого пока нет (см. §10).

Результат: `results/calibrator_super_SBER_T020.json`.

## 12. Усреднение прогноза по узкому диапазону θ (19d_theta_ensemble.py)

Идея пользователя: усреднение прогнозов S-map по нескольким θ в узком
диапазоне вокруг калиброванного оптимума может дать положительный эффект
(bagging-подобная регуляризация против переобучения θ). Проверено на двух
конфигурациях: A — baseline без T_super (m=3, T_ratio=0.8987, θ*=25.697),
B — с T_super (m=2, T_ratio_frac=0.9046, T_ratio_super=0.7770, θ*=28.384).
Пул строится один раз на конфигурацию, θ свипуется мелко (шаг 1.0) на
готовом пуле, прогноз усредняется (простое среднее lr) по всем θ в
`[θ*-Δ, θ*+Δ]` для набора полуширин Δ.

**Результат — везде хуже, монотонно с ростом Δ**, ни одной конфигурации/
терции с улучшением:

| Δ | rMAE (A, без T_super) | rMAE (B, с T_super) |
|---|---|---|
| 0 (одна точка θ*) | 0.6051 | 0.6543 |
| 3 | 0.6053 | 0.6543 |
| 8 | 0.6068 | 0.6545 |
| 18 | 0.6108 | 0.6563 |
| 24 | 0.6127 | 0.6584 |

По терциям будущего плеча — та же картина (small/mid/large везде
монотонно хуже или неизменно с ростом Δ, ни одного случая улучшения).

**Важная методическая оговорка**: θ* был найден golden-section поиском
именно НА ЭТОМ ЖЕ 42-origin наборе (нет отдельной train/calibrate и
test-выборки — общее ограничение всей ветки калибровки в фазе 7 при
такой малой выборке). Поэтому результат отчасти тавтологичен: θ*
по построению — точка МИНИМУМА rMAE на этой самой выборке, и никакая
точка по соседству не может её на этой же выборке превзойти. Тест здесь
проверяет только «не станет ли хуже вне точного оптимума» (ответ: да,
станет), но НЕ проверяет исходную мотивацию идеи — устойчивость к
переобучению θ на новых (не участвовавших в калибровке) данных. Для
честной проверки этой мотивации нужен out-of-sample тест (калибровка на
SBER → усреднение и одноточечный прогноз сравниваются на ДРУГОМ тикере,
например из Stage2-набора эксп.17b) — не выполнено в этом прогоне.

Результаты: `results/theta_sweep_A_baseline_no_super.csv`,
`results/theta_sweep_B_with_super.csv`, `results/theta_ensemble_results.csv`.

**Вывод**: в текущей (in-sample) постановке идея не подтвердилась. Открытый
вопрос — сохраняется ли эффект на out-of-sample тесте (другой тикер),
где эффект переобучения θ мог бы реально проявиться.

## 13. T_live — плавающий per-origin масштаб (19e_tlive_ensemble.py)

Идея пользователя: вместо фиксированного глобального T_super/ratio — для
каждого origin искать T_live = наибольший порог T', при котором ТЕКУЩИЙ
(ещё не подтверждённый) экстремум причинного зигзага всё ещё равен цене P
подтверждённого T_big-пивота (зигзаг «не сбросил» точку). Прогноз
T_live-масштаба — той же откалиброванной методологией (m=3, θ=25.697,
T_ratio_frac=0.8987), P трактуется как условно-подтверждённый последний
пивот. Усреднение (в лог-доходности) с обычным T_big-прогнозом.

**⚠️ Монотонность НЕ подтвердилась эмпирически**: при росте T' совпадение
`ext(T')==P` идёт «островами», не монотонно — сразу над T_big чаще всего
НЕ совпадает (зигзаг ещё в другой фазе). Причина — за сотни баров
накапливается много пороговых развилок, где размер хода почти точно равен
порогу; сколь угодно малое изменение T' может переключить одну из них
далеко в истории, меняя всю цепочку подтверждённых пивотов (эффект
бабочки). Бинарный поиск заменён на полный скан (шаг 0.001, потолок 100%),
T_live = верхняя граница ПОСЛЕДНЕГО найденного острова.

**Результаты** (`results/tlive_ensemble.csv`):

| | rMAE | n |
|---|---|---|
| baseline (T_big only) | 0.6049 | 42 |
| T_live only | 1.9959 | 29 (13 origin — вырожденный случай, остров не найден) |
| усреднённый (T_big+T_live) | 0.9547 | 42 |

mean t_live_excess=0.293, median=0.209 (типичный T_live заметно, не
чуть-чуть, больше T_big).

**Диагностика причины провала** — не (только) нехватка кросс-тикерных
данных как таковых: пул D_allpeers честно подключается (33-44 пира), но
его размер обрушивается с ростом T_frac_live=0.8987×T_live: 653→362→260→17
событий при T_frac_live=19.4%→28.8%→40.7%→89.8% (обычный T_frac для
T_big=20% даёт ~1474 — на порядок больше). Даже при excess=0.016 (T_live
почти равен T_big) пул уже вдвое меньше стандартного — количество крупных
событий падает гораздо быстрее, чем растёт порог. Фиксированный рецепт
(m=3, θ=25.697), откалиброванный на плотном пуле (тысячи событий), даёт
шумный/нестабильный прогноз на разреженных пулах (сотни или десятки
событий) — среди умеренно разреженных случаев (n=260-362) есть и очень
плохие прогнозы (ошибка 82-351₽ против 0.4-18₽ у T_big), то есть дело не
только в крайних случаях (n=17).

**Вывод**: идея в текущем виде (жёсткий рецепт, перенесённый на плавающий
масштаб) не работает — усреднение систематически хуже baseline из-за
нестабильности T_live-компоненты. Наблюдение: на МАЛОМ excess (<0.05)
усреднение иногда явно помогает (step31: 4.2→1.6, step35: 7.9→1.4,
step66: 6.3→1.3) — возможные уточнения для будущего захода: ограничить
excess потолком, брать первый (не последний) остров, взвешивать среднее не
50/50 в пользу T_big, или адаптировать θ/локальность под фактический
размер пула на найденном T_live. Не реализовано в этом прогоне.
