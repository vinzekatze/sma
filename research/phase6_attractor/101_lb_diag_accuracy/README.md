# 101 — диагностика Levina-Bickel каскада vs точность прогноза (функция d)

## 1. Гипотезы

- **H1.** Диагностика Levina-Bickel (LB) пула соседей каскада на каждом из 4 уровней
  (до/после локальной LP-очистки, для запроса и для соседей) связана с точностью
  прогноза (|error| на шаге h=1) — то есть является потенциальным индикатором
  надёжности прогноза на конкретном origin.
- **H2.** Есть значение d (а через него — m, k, p_fit, p_max, ξ_lwr), при котором
  диагностика наиболее «самосогласована» (LB после очистки близко к d, разброс LB
  между уровнями каскада минимален), и это значение совпадает или коррелирует
  с областью наилучшей точности прогноза (rMAE(d) минимально).
- **H3.** Дельта LB (после − до очистки) и разброс LB по уровням каскада несут
  дополнительную информацию о точности сверх самого значения LB.

## 2. Концепции, терминология, обозначения

- **att** — аттрактор-сигнал: результат LP-фильтра (Local Projective, Grassberger-Hegger)
  на `ratio = close/logtrend`, приведённый к разности (`diff`). LP-фильтр офлайн —
  не каузален внутри переданного ему окна (использует соседей по всему массиву),
  поэтому в этом эксперименте пересчитывается заново на `close[:origin+1]` под
  каждый origin — без утечки будущего относительно origin (как в `app3.py`).
- **m** — размерность вложения для LP-фильтра (скользящее окно длины m). Авто: `m=3·d`.
- **d** — целевая размерность локального касательного подпространства аттрактора
  (то, что LP-фильтр и LP-очистка пытаются «выпрямить»). Единственная свободная
  переменная эксперимента.
- **k** — число соседей для локальной PCA внутри LP-фильтра. Авто: `k=10·d`.
- **n_iter** — число итераций LP-фильтра (повторных проекций). Не путать с n_iter
  локальной LP-очистки диагностики (см. ниже) — это разные величины.
- **p_fit** — размерность LWR-регрессии = m (синхронизация «p = m (LP-фильтр)»).
- **p_max** — верхний уровень каскада = `p_fit × 2^(N-1)`, N=4 уровня (×2 octave).
- **levels** — уровни каскада: `[24d, 12d, 6d, 3d]` (нисходящие, последний = p_fit).
- **ξ_lwr** — размер финального пула соседей для LWR = `3·(p_fit+1) + 5`.
  В этой реализации ξ_search = ξ_lwr на всех уровнях каскада (стандарт проекта).
- **LB (Levina-Bickel)** — оценка локальной внутренней размерности множества точек
  по расстояниям до k ближайших соседей. Снимается отдельно для **запроса** (точка,
  для которой делается прогноз) и **соседей** (среднее по найденным кандидатам).
- **до / после LP** — LB на исходном (до) и на локально очищенном (после, через
  Local Projective на найденном пуле соседей этого уровня — отдельная, локальная
  процедура, не путать с LP-фильтром, который строит att) наборе векторов.
  Параметры локальной очистки: `d_lp=d, k_lp=10·d (=k фильтра), n_iter=1` (фиксировано).
- **origin** — последний известный бар на момент прогноза.
- **rMAE (h=1)** — `|pred_att − true_att| / std(att)`, агрегируется по origins.
  `pred_att` — LWR-прогноз следующего att; `true_att` — реализованное значение,
  посчитанное из `close[:origin+2]` (раскрытие одного бара вперёд, не утечка).

## 3. Методология и протокол

1. Для каждого тикера и каждой комбинации `(n_iter, d)` из сетки и каждого origin
   (walk-forward, 40 origins, шаг 5, последние ~200 баров истории):
   a. `att` строится из `close[:origin+1]` (без утечки).
   b. Каскад из 4 уровней `[24d,12d,6d,3d]`: на каждом уровне отбирается ξ_lwr
      ближайших по расстоянию на этом уровне кандидатов (как в `app3._cascade`,
      global_blend/acc_ang выключены).
   c. На каждом уровне (после отбора, до перехода на следующий) снимается LB
      до/после локальной очистки, для запроса и для соседей.
   d. Финальный пул → LWR (Гауссовы веса, p_fit измерений) → `pred_att`.
   e. `true_att` — последний элемент att, посчитанного из `close[:origin+2]`.
2. Все 45 комбинаций `(n_iter, d)` и все origins использует один и тот же набор
   тикеров и одинаковые origin-индексы (выравнено по тикеру) — для честного
   попарного сопоставления диагностика↔точность.
3. Анализ (`102_analyze.py`): развёртка long→wide по уровням, производные признаки
   (разброс LB по уровням, дельты после−до), корреляция Пирсона/Спирмена с |error|
   — пулом по всем origins/тикерам/d и в разбивке по d.

## 4. Параметры

| Параметр | Значение |
|---|---|
| Тикеры | CHMF, LKOH, MGNT, MRKP, NLMK, NVTK, SBER, VTBR (1d) |
| Сетка | n_iter=1→d∈[1,20], n_iter=2→d∈[1,15], n_iter=3→d∈[1,10] (45 комбинаций) |
| m, k | m=3d, k=10d |
| p_fit, p_max | p_fit=m, p_max=p_fit·8 |
| ξ_lwr | 3·(p_fit+1)+5 |
| Уровни каскада | 4, ×2 octave: [24d,12d,6d,3d] |
| global_blend / acc_ang / LP-коррекция | выключены |
| Локальная LP-очистка диагностики | d_lp=d, k_lp=10d, n_iter=1 |
| Origins | 40 на тикер, шаг 5 баров (walk-forward, последние ~200 баров) |
| Точность | rMAE на h=1 в att-пространстве |
| Всего задач | 8 тикеров × 45 комбинаций × 40 origins = 14400 |

## 5. Критика постановки

- **Совместный эффект параметров.** d одновременно определяет m, k, p_fit, p_max,
  ξ_lwr — любая найденная связь LB↔точность как функция d отражает совместный
  эффект всех пяти, а не «чистую» размерность. Постановка осознанно так устроена
  (по требованию задачи) — в выводах нельзя приписывать эффект конкретно d.
- **Несогласованность с прежним эталоном (scr.93).** `research/phase5_attractor/93_aligned_cascade.py`
  считал att-сигнал один раз на всей истории (без пересчёта под каждый origin) —
  числа rMAE из этого эксперимента **не сравнимы напрямую** с −12.41% rMAE из скр.93;
  здесь методология честнее (нет утечки), но это другая база отсчёта.
- **Деградация LB на малых p_lvl.** При d=1 финальный уровень p_lvl=3, k_lb≤8 —
  оценка Levina-Bickel в 3-мерном пространстве по ≤8 соседям статистически шумная,
  ожидаемо нестабильна; деградация роста d>8 — иная: k_lp=10d начинает превышать
  ξ_lwr−1=9d+7, локальная очистка вырождается в «почти весь пул», подмножество
  «локальных» соседей внутри очистки перестаёт быть локальным.
- **Двойной пересчёт LP-фильтра на origin.** Для честного rMAE нужны 2 прогона
  LP-фильтра на origin (`close[:origin+1]` и `close[:origin+2]`) — это удваивает
  стоимость по сравнению с «один прогон на тикер+комбинацию».
- **Множественные сравнения.** 45×8=360 ячеек × множество диагностических
  признаков — корреляции, прошедшие p<0.05 без поправки на множественные
  сравнения, нужно интерпретировать с осторожностью (см. Bonferroni/FDR в анализе,
  если корреляции окажутся погранично значимыми).
- **Walk-forward только на последних ~200 барах.** Не покрывает разные рыночные
  режимы (кризисы, боковики) — обобщаемость выводов ограничена этим окном истории.

## 6. Результаты

Полный прогон завершён: 14400/14400 задач (8 тикеров × 45 комбинаций
`(n_iter, d)` × 40 origins), `ok=1` у всех. Анализ — `102_analyze.py`,
выход в `results/analysis_summary.json`, `figures/*.png`.

**rMAE(n_iter, d)** — полная таблица в `analysis_summary.json["rmae_table"]`.
Лучшие и худшие комбинации:

| Ранг | n_iter | d | rMAE |
|---|---|---|---|
| лучший | 2 | 11 | 0.3274 |
| 2 | 2 | 13 | 0.3366 |
| 3 | 3 | 10 | 0.3399 |
| 4 | 2 | 10 | 0.3555 |
| 5 | 3 | 7 | 0.3566 |
| … | | | |
| худший | 1 | 1 | 0.6880 |
| | 1 | 5 | 0.6676 |
| | 1 | 2 | 0.6509 |

`n_iter=1` хуже `n_iter=2,3` почти везде (см. `figures/rmae_vs_d.png`);
минимум по d лежит в области **d≈9–13** для n_iter=2,3, при n_iter=1
кривая шумная, с локальным минимумом около d=7 и d=17, но систематически
выше n_iter=2,3.

**LB(после, финальный уровень) vs d** (`figures/lb_vs_d.png`): для всех
n_iter кривая идёт почти вплотную к диагонали LB=d до d≈5, а затем
**выходит на плато ≈6–7** и дальше не растёт вплоть до d=20. Это совпадает
с `K_LB_MAX=8` (см. §5) — оценка Levina-Bickel физически не может превысить
≈k_lb−2, поэтому плато выше d≈6 — артефакт ограничения k, а не сигнал о
насыщении реальной размерности аттрактора.

**Корреляция диагностики с |error|** (пулом по всем 14400 наблюдениям,
`correlations_pooled`): доминируют признаки **до очистки** —
`lb_before_q_mean` (r=0.378), `lb_before_n_mean` (r=0.361),
`lb_before_n_lvl1` (r=0.351); `delta_n_mean` (после−до) даёт r=−0.333.
Признаки **после очистки** заметно слабее (`lb_after_q_mean` r=0.259).
Все p-value ≪ 1e-100 (n=14400).

В разбивке по d (`correlations_by_d`) корреляция `lb_before_*_mean` с
|error| держится на уровне r≈0.35–0.46 во всём диапазоне d=7..13
(области наилучшей точности) — то есть это не артефакт пулинга по
разным d (где сам диапазон |error| и LB смещён), а воспроизводится
внутри фиксированного режима параметров.

## 7. Анализ и выводы

- **H1 — подтверждена.** LB до очистки (`lb_before_q_mean`,
  `lb_before_n_mean`) положительно и устойчиво коррелирует с |error|
  и пулом, и при фиксированном d (r≈0.35–0.46, p≪0.001 везде). Высокая
  «сырая» локальная размерность пула соседей до LP-очистки — рабочий
  индикатор ненадёжности конкретного origin-прогноза.
- **H2 — отклонена.** Точка самосогласованности (LB после ≈ d) лежит
  около d≈4–5, а минимум rMAE — в области d≈9–13. Эти две точки не
  совпадают и не коррелируют напрямую: самосогласованность диагностики
  и точность прогноза — разные оси, управляются конфигурацией не
  одинаково.
- **H3 — частично, но малоинформативно.** `delta_n_mean` коррелирует с
  |error| (r=−0.33 пулом, до r=−0.41 при d=13), однако delta построена
  как `after − before`, поэтому пересекается по информации с
  `lb_before` (которая сильнее сама по себе) — нет явного признака, что
  дельта добавляет независимый сигнал сверх «до очистки» (партиальная
  корреляция не считалась, корреляции близки по силе и одного знака
  с учётом вычитания).
- **Траектория LB по уровням каскада (lvl0→lvl3) зависит от d, а не
  монотонна универсально (`103_level_trajectory.py`).** Визуальное
  впечатление «размерность стабилизируется и становится мала по всем
  уровням» подтверждается только при **d≤4** — там LB(до, запрос) падает
  с ≈9.9 (lvl0) до ≈4.4 (lvl3), drop≈5.5, корреляция drop↔|error| на этом
  диапазоне положительна (r=+0.17, p≈1e-26) — то есть само падение здесь
  сопутствует *худшим*, а не лучшим прогнозам (видимо, маркер нестабильных
  origins, а не полезный сигнал). В зоне лучшей точности (d=9..13)
  траектория почти плоская (drop≈−0.3, т.е. слегка растёт), а при d≥16
  пуловая корреляция drop↔|error| сильная (r=−0.42, p≈1e-68), но
  **не воспроизводится по тикерам** (CHMF/LKOH/MGNT/NVTK/VTBR — r≈0,
  только MRKP r=−0.57 и SBER r=−0.33 значимы) — пуловый эффект driven
  двумя из 8 тикеров, обобщать на все инструменты нельзя. OLS-проверка
  (`abs_error ~ lvlfinal + drop + d`) подтверждает: при d≥16 добавление
  `drop` даёт ΔR²=0.0008 (drop избыточен относительно lvlfinal+d), при
  d=9..13 — ΔR²=0.049 (drop добавляет независимую информацию), но знак
  коэффициента при контроле за lvlfinal — **положительный** (больше
  падение → хуже прогноз при фиксированном финальном уровне), что
  противоречит наивной интуиции «стабилизация = надёжность» и говорит о
  более сложной, не аддитивной структуре взаимосвязи. По тикерам на
  d=9..13 знак корреляции drop↔|error| консистентен (отрицательный) у
  6 из 8 тикеров (значим у 4: CHMF, MRKP, NLMK, SBER) — сырая корреляция
  здесь надёжнее, чем при d≥16, но мала по модулю (|r|≤0.27).
- **`d ≥ lb_before_q` (финальный уровень) — самый сильный и устойчивый
  найденный индикатор (проверка по запросу пользователя).** Разбиение по
  этому бинарному признаку даёт mean|error|=0.00360 (d≥LB, n=9283) vs
  0.00552 (d<LB, n=5117) — улучшение **34.7%**, p≈4.5e-39 (Mann-Whitney).
  В отличие от находки про `drop` при d≥16 (см. выше), этот эффект
  **устойчив**: сохраняется внутри каждого фиксированного d=2..14 (p<0.01
  почти везде, эффект растёт с d), у 7 из 8 тикеров (значим везде кроме
  MGNT, p=0.34, но направление верное), и во всех 3 n_iter. Концептуально
  это переформулировка H1 (низкий LB↔низкая ошибка) в относительной форме
  — но именно относительная форма (сравнение с уже выбранным d, а не
  абсолютное значение LB) оказалась устойчивее к разбивкам. Практический
  смысл: `d≥LB` вычисляется на origin без утечки и может служить
  live-гейтом доверия к прогнозу или критерием адаптивного выбора d.
- **Пять дополнительных проверок вокруг `d≥LB` (по запросу пользователя,
  все — на уже собранных `diag_levels.csv`/`forecast_accuracy.csv`, без
  нового прогона):**
  1. *Временная кластеризация ошибки.* Lag-1 автокорреляция `abs_error` по
     origin (внутри фикс. тикер,n_iter,d) слабо положительна: mean=0.092,
     median=0.068, значимо отлична от нуля (p≈7e-20, n=360 групп) — ошибки
     немного «кучкуются» во времени, но эффект небольшой.
  2. *Волатильность тикера vs средняя ошибка.* Неинформативно: n=8 точек
     (по тикеру), r=0.306, p=0.46. MRKP — самый волатильный и с самой
     большой ошибкой, но MGNT — высокая волатильность при самой низкой
     ошибке. Простая волатильность не объясняет межтикерную гетерогенность.
  3. *Независимый вклад `div_before`* (`|lb_before_q − lb_before_n|`,
     расхождение запрос/соседи) сверх `lb_before_q` — избыточен: частная
     корреляция r=−0.059, ΔR²=0.0032 (0.0843→0.0875).
  4. *Взаимодействие `d≥LB` (финальный уровень) и `drop`* (траектория
     lvl0−lvl3) — практически отсутствует: внутри `d≥LB` `drop` не влияет
     (0.00360 vs 0.00360), внутри `d<LB` даёт небольшую разницу (0.00538 vs
     0.00566). `d≥LB` доминирует, `drop` не добавляет ценности ни в одной
     из страт.
  5. *На каком уровне каскада `d≥LB` разделяет точность сильнее* —
     монотонно растёт от грубого к финальному уровню: 24.8% (lvl0) →
     27.0% (lvl1) → 31.5% (lvl2) → **34.7%** (lvl3, финальный). Финальный
     уровень — не случайно самый информативный.
  **Вывод:** `d≥LB` на финальном уровне остаётся самым сильным и
  самодостаточным сигналом — альтернативные конструкции (`div_before`,
  `drop`, комбинации) либо избыточны, либо слабее и не добавляют поверх
  него независимой ценности.
- **Совместный пик (n_iter,d) × гейт `d≥LB` (по запросу пользователя).**
  Скомбинировал лучшую зону сетки с гейтом `d≥LB` на всех 4 уровнях каскада
  одновременно: устойчивый пик — **n_iter=2, d=11**, rMAE=0.291 среди origins,
  где гейт выполняется (n=285 из 320, покрытие 89%, представлены все 8
  тикеров, 21-40 наблюдений каждый). Соседние клетки (d=7..9, n_iter=2/3)
  дают похожий результат (rMAE 0.26-0.30) с покрытием 43-80%. Формально
  более низкий минимум (rMAE=0.226, n_iter=3,d=4) оказался **ложным пиком**:
  гейт там выполняется лишь в 9% случаев и исключительно у 4 из 8 тикеров
  (CHMF/NLMK/SBER/VTBR) — артефакт малой нерепрезентативной выборки, та же
  ловушка, что и с `d≥16` ранее. Вывод: гейт `d≥LB` почти вдвое усиливает
  эффект от выбора (n_iter,d) самого по себе (0.291 против 0.327 без гейта,
  против 0.673 — средний по всей сетке без фильтрации).
- **Артефакт K_LB_MAX=8 (не предсказанный заранее).** Главная
  методологическая находка прогона, не входившая в исходную критику
  (§5): ограничение `k_lb_max=8` для самой оценки LB задаёт потолок
  измеримой размерности ≈6–7, независимо от d. Это означает, что для
  d>8 диагностика «после очистки» вообще не способна различить
  d=10 vs d=20 — все такие точки технически насыщены. Любое
  использование LB как live-индикатора надёжности должно учитывать
  этот потолок (увеличить k_lb_max или интерпретировать LB только в
  относительном, не абсолютном масштабе).
- **Практический вывод для app3.** Лучшая точка по чистой точности —
  `n_iter=2, d=11` (rMAE=0.327) — заметно отличается от текущего
  стандарта проекта (`d=3, n_iter=1`, см. [[att_filter_standard]]).
  Прямой перенос этого результата в app3 не рекомендуется без отдельной
  проверки: здесь d одновременно меняет m/k/p_fit/p_max/ξ_lwr (см. §5,
  «совместный эффект параметров»), а окно walk-forward — всего
  ~200 баров на 8 тикерах.

## 8. Дальнейшие направления

- **Приоритетно**: проверить `d≥lb_before_q` как live-гейт надёжности
  или критерий адаптивного выбора d (например, на origin искать минимальное
  d, при котором d≥LB, вместо фиксированного d по сетке) — самый сильный
  и устойчивый сигнал из найденных, заслуживает отдельного эксперимента
  на полноценном app3-пайплайне. Конкретная цель, найденная как совместный
  пик: **n_iter=2, d≈9-11, гейт на всех 4 уровнях** (rMAE=0.29, покрытие 89%,
  устойчиво по тикерам) — стартовая точка для переноса в app3.
- Понять механизм положительного знака `drop` в OLS при d=9..13 (после
  контроля lvlfinal+d) — возможно нелинейность/взаимодействие с d или с
  лучшей метрикой "положения" пика на промежуточном уровне (lvl1/lvl2), а
  не просто lvl0−lvl3. **Деприоритизировано**: проверка взаимодействия
  `d≥LB`×`drop` (см. выше) показала, что `drop` не добавляет ценности ни
  в одной из страт `d≥LB` — мотивация разбираться в механизме знака слабее.
- Раздельные вклады m/k/p_fit/ξ_lwr — зафиксировать d, варьировать одну
  переменную, чтобы понять, действительно ли оптимум d≈10–13 связан с
  размерностью аттрактора или с побочным эффектом увеличения пула
  соседей (k, ξ_lwr) при росте d.
- Повторить с увеличенным `k_lb_max` (≥20), чтобы убрать потолок плато
  и проверить, сохраняется ли область d≈9–13 как оптимум для LB(после)≈d.
- FDR/Bonferroni-поправка по 45×8 ячейкам — корреляции пройдены с большим
  запасом (p≪1e-100), поправка вряд ли изменит выводы, но не сделана.
- Партиальная корреляция delta_n_mean | lb_before_n_mean, чтобы закрыть
  H3 явно (независимый вклад дельты или нет).
- Расширить walk-forward окно за пределы последних ~200 баров и/или
  больше тикеров — текущий результат может быть специфичен для
  выбранного рыночного режима.
- Если `n_iter=2, d=11` действительно лучше стандарта — отдельный
  эксперимент на полноценном app3-пайплайне (с acc_ang/global_blend
  включёнными) для проверки переноса результата.
- **Хвост origins с очень высоким LB (по запросу пользователя — контекст для
  будущего адаптивного алгоритма выбора d).** Распределение `lb_before_q`
  (финальный уровень) почти не растёт с d (mean/median ~7-9 на всём диапазоне
  1-20) — для ≥94-99% origins текущая сетка с запасом достаточна. Но
  максимум в каждом столбце сетки доходит до **30-60+** — редкий (0.92%,
  132/14400 точек данных) хвост origins, где d≥LB не достижим в пределах
  протестированной сетки никаким d≤20. Это **не шум сетки**: 57 уникальных
  (тикер,origin), 15 из них воспроизводятся на ≥3 разных (d,n_iter) —
  свойство конкретной исторической точки, не случайность выбора параметров.
  **64% хвоста (84/132) — один тикер, MRKP** (тот же тикер, что выделялся
  и в проверке drop при d≥16, и слабее — в анализе тикерной гетерогенности).
  Подтверждает ручное наблюдение пользователя: для части точек приличный
  прогноз действительно может требовать d>15-20 (перекликается со старой
  находкой TwoNN d∈[32..79] из скр.88/94, см. CLAUDE.md "Протокол
  экспериментов"). Implication для будущего алгоритма адаптивного выбора d:
  нужна дешёвая предварительная проверка («не один ли из редких сложных
  origins»), прежде чем коммититься к дорогому пересчёту LP-фильтра на
  большом d — грубая оценка сначала, уточнение потом (идея пользователя).
  Не тестировалось намеренно (экономия ресурсов) — d>20 целенаправленно не
  прогонялся.
- **Эскалация n_iter вместо роста d (ручная стратегия пользователя,
  подтверждена по данным).** Пользователь вручную при неудачном подборе на
  `n_iter=1` переходил на `n_iter=2`, затем `n_iter=3`, дальше — слишком
  ресурсозатратно. Проверка: для каждого (тикер,origin) нашёл минимальное d,
  при котором `d≥LB`, отдельно по n_iter. Среднее минимальное d падает
  систематически: 6.45 (n_iter=1) → 4.54 (n_iter=2) → 4.08 (n_iter=3).
  Только 1 origin из 320 не находит решения в сетке d=1..20 при n_iter=1 —
  и его «спасают» оба следующих n_iter. Для **трудных** origins (нужное
  d≥12 при n_iter=1, n=16) эскалация даёт явный выигрыш даже по грубой
  оценке стоимости (proxy=n_iter×d_min): 13.19 → 12.80 → 12.56 — то есть
  рост n_iter не просто «спасает» сложные точки, а делает это бесплатно
  или дешевле (падение нужного d компенсирует рост n_iter). Подтверждает
  стратегию пользователя как количественно обоснованную: для лёгких
  origins n_iter=1 дешевле, для трудных — выгоднее наращивать n_iter,
  чем гнаться за большим d.
- **Межтикерная гетерогенность не объяснена.** MGNT и MRKP систематически
  выбиваются в разных разрезах (drop при d≥16, d≥LB-эффект); простая
  волатильность close (см. проверку #2 выше) не коррелирует с этим
  (n=8, r=0.306, p=0.46, неубедительно). Нужна другая гипотеза (ликвидность,
  структурные разрывы, доля выходных/праздничных гэпов) или больше тикеров.
- **Слабая временная кластеризация ошибки** (lag-1 автокорреляция
  abs_error ≈0.09, см. проверку #1 выше) обнаружена, но не использована —
  потенциально можно скомбинировать с `d≥LB`-гейтом (после низкой точности
  на одном origin вероятность низкой точности на следующем чуть выше
  базовой) для дополнительного уточнения live-гейта надёжности.

### Скрин 108 — тонкая доводка m шагом 1 при избыточном p_fit=3d (ЗАВЕРШЁН — эффект неотличим от шума; нужна проверка при тонком p_fit=2d+1)

Контекст: пользователь предложил декаплинг ролей — `d`/`p_fit` грубые
(фиксированы после выбора), `m`/`k` (внутри LP-фильтра) — тонкая доводка.
Первая попытка (`107_decouple_m_k.py`, удалена из README) использовала
шаг ~5 по m (23/28/33) — это не тонкая доводка, а грубая сетка по другому
параметру; `m=33,k=110` там тривиально совпадало с уже известной ячейкой
эксп.101 (d=11,n_iter=2). `108_fine_tune_m.py` — корректная версия: d=11,
p_fit=33(=3·11), k_filter=110(=10d), n_iter=2 — все зафиксированы; варьируется
только m_filter∈[30..36] шагом 1 (±3 вокруг текущей конвенции 3d=33).
8 тикеров, 15 origins, 840 задач, ~17.5 мин.

**Результат:**

| m_filter | rMAE | %d≥LB | LB средн. |
|---|---|---|---|
| 30 | 0.2516 | 93.3% | 6.45 |
| 31 | 0.2029 | 94.2% | 6.33 |
| 32 | 0.2264 | 94.2% | 6.02 |
| 33 (baseline 3d) | 0.2203 | 94.2% | 6.00 |
| 34 | 0.2338 | 95.0% | 5.58 |
| 35 | 0.2405 | 95.8% | 5.39 |
| 36 | 0.2466 | 98.3% | 5.15 |

Диагностика (`lb_before_q`, доля `d≥LB`) реагирует на m **чисто
монотонно** (6.45→5.15, 93.3%→98.3%). Но rMAE — нет: разброс ~21% от
среднего, без тренда, минимум на m=31 (не на краю и не на baseline m=33).
По тикерам пуловый минимум на m=31 **не воспроизводится**: m=31 лучше
только у 3 из 8 тикеров (CHMF, MRKP, NLMK), m=33 — у 5 из 8 (LKOH, MGNT,
NVTK, SBER, VTBR) — то есть это шум, не реальный локальный оптимум (та же
ловушка, что с пуловыми пиками ранее в этом эксперименте).

**Вывод (предупреждение пользователя подтвердилось): не «m не важен»,
а «при избыточном p_fit=3d влияние тонкой доводки m неотличимо от
межтикерного шума на этой выборке»** — большой запас лагов в LWR-регрессии
маскирует эффект качества очистки att. Гипотеза для проверки: при **тонком**
p_fit=2d+1 (вместо 3d) регрессия менее избыточна, и тот же диапазон m
может дать чёткий, воспроизводимый по тикерам эффект на rMAE, а не только
на диагностику.

**Отложено пользователем** (2026-06-16, конец сессии): для p_fit=2d+1
нужен отдельный полный сбор данных, сравнимый с тем, что накоплено в этой
сессии (108, и через него — 107/106/104) — не запускать без явного
запроса.

### Скрин 106 — мягкое перевзвешивание (идея 1) и PCA-отбор (идея 3) (ЗАВЕРШЁН — обе нейтральны/отрицательны)

После отрицательного результата пилота 104 (жёсткий greedy-отбор по
изоляции не улучшил точность) пользователь предложил две альтернативы и
явно отклонил третью (ансамбль/блендинг — риск накопления ошибок при
резкой смене оптимальных параметров между соседними origins):

- **Идея 1** — мягкое перевзвешивание (аналог `acc_ang` из фазы 5):
  `d_total = d_pos + λ·s`, где `s` — изоляция соседа (расстояние до его
  k_lb-го соседа) внутри ОБЫЧНОГО финального пула эксп.101 (без
  расширения — согласовано с пользователем, дешевле пилота 104).
- **Идея 3** — отбор по PCA/Махаланобис-расстоянию: на естественно широком
  пуле, входящем в финальный уровень каскада, локальный PCA (как
  `lp_clean_set`, но для самого отбора), проекция на top-d компонент
  (d = размерность LP-фильтра, согласовано), отбор xi_lwr по расстоянию
  в проекции. Вес LWR — по сырому расстоянию отобранных точек (меняется
  только отбор, не взвешивание — изолирует эффект).

`106_soft_reweight_pca.py` — урезанный скрининг перед длинными расчётами:
n_iter=2 (фикс.), d∈{8,10,11,13}, 8 тикеров, 15 origins (480 задач,
~10 мин на 6 ядрах — дешевле пилота 104, без широкого пула/жадной
итерации для идеи 1). При первом прогоне упал на `LinAlgError: SVD did
not converge` в `lp_proj_signal` (LP-фильтр, унаследованный баг из
101_lb_diag_accuracy.py, не проявлявшийся на сетке эксп.101) — исправлено
локальным monkey-patch внутри 106 (fallback на `scipy.linalg.svd(...,
lapack_driver="gesvd")`, без изменения зафиксированного кода эксп.101).

**Результаты (пулом и парно, n=480):**
- Идея 1 (λ=2 vs base): rMAE 0.260028→0.259850 (улучшение 0.07%,
  в пределах шума), Wilcoxon p=0.085 (не значимо), лучше лишь в 44.2%
  origins. По d разнонаправленно, нет устойчивого тренда силы эффекта.
- Идея 3 (pca vs base): rMAE 0.260028→0.261428 (хуже на 0.5%), Wilcoxon
  p=0.967 (практически идентично baseline), лучше лишь в 41.5% origins.

**Вывод: обе идеи в протестированном виде не показывают потенциала**,
оправдывающего длинные расчёты. У идеи 1 есть едва заметный монотонный
тренд в сторону улучшения с ростом λ, но эффект на 2 порядка меньше, чем
у `d≥LB`-гейта — неочевидно, стоит ли тестировать большие λ. Идея 3
выглядит полностью нейтральной (p≈0.97).

### Пилот 104/105 — отбор финального пула по изоляции (ЗАВЕРШЁН — H4 отклонена)

По итогам обсуждения траектории LB по уровням каскада (см. выше) возникла
гипотеза H4: финальный пул соседей, отобранный с учётом локальной
самооценки размерности (`lb_before_n`), а не только расстояния, даёт ниже
rMAE в зоне d=7..13. `104_lb_greedy_select.py` — пилот: на каждом origin
вычисляет **два** прогноза (baseline = top-xi_lwr по расстоянию = метод
эксп.101; new = жадное сужение естественно широкого промежуточного пула
каскада [~1.9-2.6×xi_lwr] до xi_lwr, на каждом шаге убирая самую
изолированную точку — дешёвая аппроксимация минимизации LB без
пересчёта формулы на каждом шаге). `105_analyze_pilot.py` — парное
сравнение (Wilcoxon, по тикерам, проверка что `lb_n_new < lb_n_base`
действительно выполняется).

Сетка: n_iter∈{2,3}, d=7..13 (14 комбинаций), 8 тикеров, 40 origins —
4480 задач. Полный прогон выполнен пользователем на хосте (не на kali-VM,
~2.5ч оценка на 6 ядрах), результат — `results/pilot_greedy_select.csv`
(4480/4480, ok=1 везде).

#### Результаты (`105_analyze_pilot.py`)

- **Sanity-check пройден**: отбор действительно снижает диагностику —
  `lb_n_new < lb_n_base` в 92.5% origins (mean reduction −0.68). Механизм
  работает как задумано.
- **H4 ОТКЛОНЕНА — точность не улучшается, в среднем чуть хуже.** Среднее
  изменение rMAE по 14 ячейкам (n_iter,d): **−7.12%** (отрицательное =
  новый метод хуже). При d=7..10 деградация существенная (например d=7,
  n_iter=2: rMAE 0.401→0.509, на четверть хуже). Только у d=11 методы
  почти сходятся (n_iter=3: 0.305→0.302, в пределах шума).
- **Парный Wilcoxon** (n=4480): p=0.027 — значимо, но в сторону худшего
  результата у нового метода (mean diff +0.00024); новый метод лучше
  лишь в 48.9% origins (меньше половины).
- **По тикерам**: только NVTK значимо в пользу нового метода (p=0.028);
  LKOH, MRKP, NLMK значимо **против**; CHMF/MGNT/SBER/VTBR не значимы.
  См. `figures/pilot_rmae_base_vs_new.png`, `figures/pilot_paired_diff_hist.png`.

#### Интерпретация

H1 (низкий LB ↔ низкая ошибка) была установлена *между естественно
различающимися origins* — это диагностический индикатор сложности момента,
а не рычаг, который можно потянуть для одного и того же origin через
curацию пула. Жадное удаление «изолированных» точек снижает LB-диагностику
успешно, но по критерию изоляции относительно ПУЛА, а не релевантности
к ЗАПРОСУ — судя по результату, это убирает из пула точки, нужные LWR для
устойчивой локальной регрессии, в обмен на формально более «опрятную»
диагностику. Содержательный негативный результат: подтверждает, что
`d≥LB` полезен как *гейт надёжности* (см. выше), но не как *цель для
оптимизации отбора соседей* — это разные роли одной и той же диагностики.

```bash
source /home/kali/.venvs/sma/bin/activate
TEST_MODE=1 python research/phase6_attractor/101_lb_diag_accuracy/101_lb_diag_accuracy.py
```

### Docker (тест + полный прогон, ~2-3 часа на 6 ядрах)

```bash
cd /home/kali/workspace/apps/sma
docker build -f research/phase6_attractor/101_lb_diag_accuracy/Dockerfile \
             -t lb-diag-101 .
docker run --rm \
    -v "$(pwd)/research/phase6_attractor/101_lb_diag_accuracy/results:/output" \
```

Контейнер при старте печатает ID эксперимента и версию образа, затем
автоматически прогоняет тест (2 тикера, 5 origins, урезанная сетка, ~15 сек) и,
если он не упал, полный прогон (8 тикеров, 45 комбинаций, 40 origins, 14400 задач).
Результаты пишутся в `/output` (= `results/` на хосте) онлайн, построчно — после
каждой завершённой задачи, так что частичные результаты переживут краш контейнера.

Параллелизм — `ProcessPoolExecutor`, `WORKERS` воркеров (по умолчанию
`os.cpu_count()`). BLAS внутри каждого воркера явно ограничен одним потоком
(`OMP_NUM_THREADS=1` и аналоги) — без этого многопоточный OpenBLAS в каждом из
N процессов даёт oversubscription и резко всё замедляет (проверено эмпирически:
на 6-ядерной машине без ограничения 4 воркера были медленнее одного).

Оценка стоимости (замерено на SBER, реальные данные): один прогон LP-фильтра по
всей сетке 45 комбинаций — 92 сек; полный эксперимент с честным per-origin
пересчётом (×2 вызова на origin, ×40 origins, ×8 тикеров) — ориентировочно
~16 часов в один поток, ~2-3 часа на 6 ядрах.
