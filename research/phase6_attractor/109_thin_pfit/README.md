# 109 — диагностика Levina-Bickel каскада vs точность прогноза при тонком p_fit=2d+1

## 1. Гипотезы

Прямое продолжение эксп.101 (`research/phase6_attractor/101_lb_diag_accuracy/`),
с единственным изменением — формула m (а через неё p_fit) переопределена с
«избыточной» `m=3d` на «тонкую» `m=2d+1`. Гипотезы переформулированы как
проверка воспроизводимости находок эксп.101 на новой точке дизайна:

- **H1.** LB до очистки (`lb_before_q_mean`, `lb_before_n_mean`) положительно
  коррелирует с |error|, как и в эксп.101 (там r≈0.35-0.46 при фиксированном d).
- **H2.** Минимум rMAE(d) лежит в области, отличной от точки самосогласованности
  LB (LB после ≈ d) — повторение находки «эти две оси не совпадают».
- **H3.** Гейт `d≥LB` (финальный уровень, до очистки) даёт устойчивое улучшение
  mean|error| (в эксп.101 — 34.7% пулом), сопоставимое по порядку величины при
  тонком p_fit.
- **H4 (новая).** При тонком p_fit=2d+1 минимум rMAE(d) смещён относительно
  эксп.101 **по оси p_fit** (не по оси d) — то есть оптимальный *абсолютный*
  размер регрессии (p_fit≈30-40?) воспроизводится независимо от того, каким d
  он получен, либо смещён в другую сторону (тонкая регрессия при том же p_fit
  работает иначе, т.к. d/p_fit — это ещё и неявный параметр степени сглаживания
  LP-фильтра).

## 2. Концепции, терминология, обозначения

Все термины идентичны README эксп.101 (att, m, d, k, n_iter, p_fit, p_max,
levels, ξ_lwr, LB, до/после LP, origin, rMAE) — см.
`research/phase6_attractor/101_lb_diag_accuracy/README.md` §2. Единственное
изменение:

- **m** — теперь `m = 2d + 1` (было `m = 3d` в эксп.101). k остаётся на прежней
  авто-формуле `k = 10d` — **не привязан к m**, привязан к d напрямую.
- **k_lb_d** (новое поле в `diag_levels.csv`) — фактическое k, использованное
  в формуле Levina-Bickel на данном уровне: `max(3, min(K_LB_MAX, n_neigh-2))`.
  Добавлено для прямой диагностики артефакта плато `K_LB_MAX=8`, найденного в
  эксп.101 (§5/§7 там), без пересчёта из `n_neigh`.
- **p_fit** здесь численно отличается от p_fit в эксп.101 при одном и том же
  d (там `p_fit=3d`, здесь `p_fit=2d+1`) — **d не является общей осью сравнения
  между двумя экспериментами**, общая ось — p_fit (см. критику §5).

## 3. Методология и протокол

Идентична эксп.101 (см. README там, §3), без изменений:

1. Для каждого тикера и каждой комбинации `(n_iter, d)` из сетки и каждого
   origin (walk-forward, 40 origins, шаг 5):
   a. `att` строится из `close[:origin+1]` (без утечки — проверено явно,
      см. §5 ниже).
   b. Каскад из 4 уровней `[16d+8, 8d+4, 4d+2, 2d+1]`: на каждом уровне
      отбирается ξ_lwr ближайших по расстоянию кандидатов (global_blend/
      acc_ang выключены).
   c. На каждом уровне снимается LB до/после локальной очистки, для запроса
      и для соседей (плюс `k_lb_d` — новое поле).
   d. Финальный пул → LWR → `pred_att`.
   e. `true_att` — последний элемент att из `close[:origin+2]` (раскрытие
      одного бара вперёд, не утечка — см. §5).
2. Анализ (`110_analyze.py`): то же, что `102_analyze.py` эксп.101
   (rMAE-таблица, корреляции пулом/по d, LB-vs-d), плюс явный гейт `d≥LB`
   (повтор находки §7 эксп.101, не было отдельным скриптом там) и
   сопоставление с зафиксированными числами эксп.101 по оси p_fit.

## 5. Критика постановки

- **Совместный эффект параметров** (как в эксп.101) — d одновременно
  определяет m, k, p_fit, p_max, ξ_lwr; любая найденная связь LB↔точность как
  функция d отражает совместный эффект всех пяти величин.
- **d не сопоставим между эксп.101 и эксп.109 напрямую.** При одном и том же
  d здесь p_fit≈2d+1 заметно меньше, чем в эксп.101 (p_fit=3d). Например d=11:
  эксп.101 → p_fit=33, здесь → p_fit=23. Корректная ось сравнения двух
  экспериментов — **p_fit (или m)**, не d (учтено в `110_analyze.py` —
  `rmae_vs_pfit.png`, `ref_101_rmae_best` в сводке).
- **K_LB_MAX=8 плато ещё заметнее.** Диапазон d расширен (до 30 vs 20 в
  эксп.101) специально под более тонкий m — артефакт «диагностика после
  очистки не может превысить ≈6-7», найденный в эксп.101, здесь покроет
  большую долю сетки. K_LB_MAX оставлен фиксированным ради сопоставимости с
  эксп.101, а не потому что артефакт устранён.
- **Проверка утечки из будущего выполнена явно** (по запросу пользователя)
  перед запуском: `att` (входит во весь каскад/LWR — `X_full`, `y_base`,
  `vec_full0`) строится исключительно из `close[:origin+1]`. `att_ext`
  (`close[:origin+2]`) используется только для `true_val = att_ext[-1]` —
  не входит в каскад/LWR ни в одном месте (проверено grep по использованиям
  переменной). Граница `origins_for` (`last = n_total-2`) гарантирует, что
  `close[:origin+2]` не выходит за пределы истории. Архитектура идентична
  уже проверенной в эксп.101.
- **Стоимость прогона измерена, не только оценена.** Прямой замер (один
  тикер, один origin, все 65 комбинаций сетки) дал 261.5 сек однопотока →
  оценка полного прогона ≈23.2ч в один поток, ≈3.9ч на 6 ядрах (без учёта
  накладных расходов ProcessPoolExecutor) — что выше, чем у эксп.101
  (14400 задач, ~2-3ч на 6 ядрах), при том что задач здесь на 44% больше —
  рост стоимости объясняется тем, что сетка продлена в зону больших d
  (d=21..30 для n_iter=1, d=16..20 для n_iter=2 и т.д.), которых не было
  в эксп.101.
- **Walk-forward только на ~200 последних барах** — то же ограничение, что
  в эксп.101.
- **Множественные сравнения** — 65×8=520 ячеек, больше чем в эксп.101
  (45×8=360); та же оговорка по p-value без поправки на множественность.
- **Первый прогон без подстройки** (по требованию пользователя) — выводы
  ниже описательные/корреляционные, не предписывающие конкретный
  оптимальный (n_iter,d) для переноса в app3 без отдельной проверки.

## 7. Анализ и выводы

### H1 — ПОДТВЕРЖДЕНА

LB до очистки положительно коррелирует с |error|: lb_before_q_mean Pearson r=0.394 (пул,
p=0.000). Это совпадает с диапазоном эксп.101 (r≈0.35-0.46 при фиксированном d). Корреляция
воспроизводится независимо от формулы m — это устойчивый сигнал.

Важное уточнение: в отличие от эксп.101, где корреляция нарастала к последнему уровню
каскада, здесь лучший сигнал — lb_before на уровне 1 (не финальный 3). Возможно, при тонком
m=2d+1 каскад менее эффективно «рафинирует» соседей, и ранний уровень уже несёт полный
сигнал.

### H2 — НЕ ПОДТВЕРЖДЕНА

В эксп.101 (m=3d) минимум rMAE(d) находился при d=11 — за пределами самосогласованного
диапазона (d≤6 там). В эксп.109 (m=2d+1) минимум rMAE при d=3 совпадает с центром
самосогласованного диапазона (d=1..7, lb_after ≈ d). Две оси **совпали**.

Интерпретация: с тонким m=2d+1 размерность шума (m−d = d+1) близка к размерности сигнала
(d). LP-фильтр слабо меняет структуру пространства — lb_after плавно следует за d без
резкого излома. В итоге самосогласованность теряет диагностическую ценность как
самостоятельная ось: оба критерия указывают на d=3 по одной причине — малый d=3 является
единственно возможным «незашумлённым» режимом при такой геометрии.

### H3 — ПОДТВЕРЖДЕНА (ослабленная форма)

Гейт d≥LB даёт statistically significant улучшение −23.3% (p=4.5×10⁻¹⁰), против 34.7% в
эксп.101. Эффект воспроизводится, но ослаблен.

Примечательный паттерн: при больших d (где рMAE плох) гейт становится **сильнее** (50–58%
улучшение при d=13..20), не слабее. Это подтверждает, что LB измеряет настоящее геометрическое
качество локальной окрестности, а не является просто прокси d. При тонком m LP-фильтр хуже
«рафинирует» соседей, и LB-сигнал становится единственным надёжным индикатором качества.

Гетерогенность по тикерам: только MRKP (+19.2%) и SBER (+11.1%) дают уверенно
положительный эффект; CHMF, NLMK, NVTK дают отрицательный. Это объясняет, почему пулируемое
улучшение меньше, чем в эксп.101 (там, судя по всему, гетерогенность была меньше). Гейт
может работать по-разному для тикеров с разными режимами волатильности.

### H4 — ПОДТВЕРЖДЕНА (смещение к малым p_fit)

Оптимальный p_fit=7 при тонком m=2d+1 резко смещён относительно p_fit=33 в эксп.101.
Гипотеза об «инвариантном оптимальном размере регрессии ≈30-40» **отклонена**.

Сравнение по оси p_fit (правильная ось между экспериментами):

| p_fit | rMAE эксп.101 (m=3d) | rMAE эксп.109 (m=2d+1) | Разница |
|-------|----------------------|------------------------|---------|
| 7 | — | **0.393** (n_iter=3, d=3) | — |
| 23 | 0.622 (n_iter=1,d=11) | 0.462 (n_iter=2,d=11) | −26% |
| 33 | **0.327** (n_iter=2,d=11) | 0.569 (n_iter=2,d=16) | +74% |

При одном и том же p_fit=33 экп.109 в 1.74 раза хуже эксп.101. Тонкая формула m=2d+1
принципиально невыгодна при больших d: отношение d/m = d/(2d+1) ≈ 0.5 означает, что
пространство шума (m−d = d+1) лишь ненамного превышает пространство сигнала (d). LP-фильтр
имеет недостаточно «места» для шумоподавления.

Оптимум m=2d+1 достигается в режиме (n_iter=3, d=3, p_fit=7) — минимально возможная
регрессия с максимальным числом итераций LP. Это компенсационная стратегия: три слабых
прохода LP вместо двух нормальных. По итогу — более слабый сигнал.

### Сводный сравнительный вывод

| | Эксп.101 (m=3d) | Эксп.109 (m=2d+1) |
|---|---|---|
| Лучший rMAE | **0.3274** | 0.3930 (+16.8%) |
| Оптимум (n\_iter, d) | 2, 11 | 3, 3 |
| Оптимальный p\_fit | 33 | 7 |
| LB↔\|error\| (Pearson) | ≈0.35–0.46 | 0.394 |
| Гейт d≥LB улучшение | **34.7%** | 23.3% |
| H1 (LB коррел.) | ✓ | ✓ |
| H2 (min ≠ self-consist.) | ✓ | ✗ |
| H3 (гейт значим) | ✓ | ✓ (ослаблен) |
| H4 (p\_fit оптимум) | — | ✗ (смещён к 7) |

**Итоговый вывод:** m=2d+1 — субоптимальная формула. Стандарт m=3d обеспечивает лучшее
rMAE на всей сетке. Формула m=2d+1 не является перспективной заменой для app3.

Единственная ценность эксп.109 — **воспроизводимость H1 и H3**: LB-диагностика работает
как индикатор качества при разных формулах m, что подтверждает её принципиальную применимость
для адаптивного контроля прогноза.

## 8. Дальнейшие направления

1. **Гейт в app3 на стандартном m=3d.** Результаты эксп.101 (−34.7%) и эксп.109 (−23.3%)
   обоих подтверждают: условие `d ≥ lb_before_q` на финальном уровне каскада — надёжный
   фильтр origins. Следующий шаг — реализовать этот гейт в интерфейсе app3 как «индикатор
   надёжности» (сигнал «плохой» прогноз без отклонения самого прогноза).

2. **Тикерная гетерогенность гейта.** CHMF, NLMK, NVTK дают отрицательный эффект гейта.
   Гипотеза: у «трендовых» тикеров lb_before высокий структурно (аттрактор шире), и условие
   d≥lb неверно классифицирует «хорошие» origins как плохие. Исследовать per-ticker lb
   baseline.

3. **n_iter=4 при m=3d.** В эксп.101 не проверялся n_iter=3 при n_iter∈{1,2}. Здесь видно,
   что переход 2→3 даёт существенное улучшение при m=2d+1. Проверить n_iter=3 и n_iter=4
   при m=3d — возможно, там тоже есть gain (но для m=3d фильтр уже сильный, поэтому gain
   может быть мал).

4. **Диагностика K_LB_MAX.** Артефакт плато K_LB_MAX=8 скрывает истинные LB-значения при
   d≥8 в обоих экспериментах. При увеличении K_LB_MAX коэффициенты корреляции и gate
   improvement могут вырасти — это стоит проверить отдельно (изменить только K_LB_MAX, не
   весь дизайн).

5. **Per-origin адаптивный выбор d (LB-guided).** Сочетание эксп.101 и эксп.109 указывает:
   оптимальный d зависит от локальной геометрии origin, а не от тикера. LB до очистки
   (lb_before_q) — возможный предиктор оптимального d per-origin. Этот вопрос поставлен
   в `ideas_neighbor_selection.md` и остаётся открытым.

## Запуск

### Локально (тест, 2 тикера, ~15 сек)

```bash
source /home/kali/.venvs/sma/bin/activate
TEST_MODE=1 python research/phase6_attractor/109_thin_pfit/109_thin_pfit.py
```

### Docker (тест + полный прогон, измерено ~3.9ч на 6 ядрах)

```bash
cd /home/kali/workspace/apps/sma
docker build -f research/phase6_attractor/109_thin_pfit/Dockerfile \
             -t thin-pfit-109 .
docker run --rm \
    -v "$(pwd)/research/phase6_attractor/109_thin_pfit/results:/output" \
    -e WORKERS=6 \
    thin-pfit-109
```

Контейнер при старте печатает ID эксперимента и версию образа, затем
автоматически прогоняет тест (2 тикера, 5 origins, урезанная сетка, ~15 сек) и,
если он не упал, полный прогон (8 тикеров, 65 комбинаций, 40 origins, 20800
задач). Результаты пишутся в `/output` (= `results/` на хосте) онлайн,
построчно — после каждой завершённой задачи.

python research/phase6_attractor/109_thin_pfit/110_analyze.py --test
