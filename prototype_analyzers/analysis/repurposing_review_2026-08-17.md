# Обзор: перенос механик не по назначению + новые идеи (2026-08-17)

Документ самодостаточен — рассчитан на чтение без контекста конкретного диалога, в
котором он был написан. Составлен по результатам сплошного прочтения `CLAUDE.md`,
всех ~104 файлов памяти проекта (`/home/kali/.claude/projects/-home-kali-workspace-apps-sma/memory/`)
и ключевых исходников в `research/`, `prototype/forcaster/`, `prototype_analyzers/`,
`sma/core/`.

Контекст задачи: проект — Python-инструмент прогнозирования котировок MOEX,
развивающийся в двух параллельных направлениях (A — LP-аттрактор/LWR-прогноз att,
B — событийная фрактальность зигзага) плюс теоретическая ветка. Накоплено больше
100 исследовательских экспериментов (скрипты 01–113+, фазы 1–7). Владелец —
пентестер по профессии, не трейдер; ценит математическую/аналитическую
любознательность не меньше прогностической точности, прямо сформулировал:
«не гонимся за кнопкой заработать денег».

Документ отвечает на два вопроса:

1. **Угол 1** — какие уже built алгоритмы/техники, придуманные для одной задачи
   (обычно прогноз), структурно годятся для другой (диагностика, визуализация,
   другой масштаб, портфельная аналитика), но никогда не пробовались там.
2. **Угол 2** — какие новые идеи (не обязательно перенос существующего) стоит
   попробовать, с явной сверкой против уже отклонённых в прошлом гипотез.

В конце — приоритизированный шорт-лист на 5–8 пунктов.

## Угол 1 — неочевидные механики не по назначению

### 1. LB-гейт (`d ≥ lb_before_q`) — самый сильный неиспользуемый диагностический сигнал проекта

**Откуда:** `research/phase6_attractor/101_lb_diag_accuracy/`, экспы 101/104/106/108/109
(память `lb_diag_accuracy_101.md`). LB — геометрическая величина: локальная
размерность окрестности запроса в delay-пространстве att, оцениваемая через SVD
топ-K соседей ДО LP-очистки, на финальном уровне каскада.

**Для чего использовалась:** как кандидат в критерий отбора/фильтрации соседей
внутри каскада направления A (несколько попыток curation пула — все нейтральны
или отрицательны, см. эксп.104/106).

**Что не пробовали:** LB считается на любом origin **без выполнения самого
прогноза** — это чисто геометрическая диагностика конкретной точки истории.
Бинарный признак `d ≥ LB` — самый сильный и воспроизводимый индикатор во всём
датасете эксп.101: улучшение mean|error| на 34.7% (p≈4.5e-39), устойчив по 7 из 8
тикеров, по всем n_iter, усиливается к финальному уровню каскада (24.8%→34.7%).
Для сравнения — Hurst как гейт качества прогноза дал r≈0 (фаза 1, отклонён
полностью). LB — рабочая замена Hurst-зон, но никогда не выводилась в UI как
самостоятельный индикатор.

**Конкретная идея другого применения:** живой оверлей на графике (аналог
`unpredictable_zones` из `hurst.py`, но с реально работающим сигналом вместо
отклонённого) — для каждого origin вычислять LB и закрашивать бар/зону
зелёным/красным по `d ≥ LB` на финальном уровне каскада, ПОЛНОСТЬЮ независимо
от того, запускается ли сам LWR-прогноз. Это превращает диагностику надёжности
в самостоятельный аналитический продукт («геометрическое здоровье» текущего
участка ряда), которым можно пользоваться даже не глядя на прогноз — ровно то,
что не сработало у Hurst, но здесь подтверждено экспериментально.

### 2. Каскадный поиск соседей — уже один раз перенесён (`prototype_analyzers/`), можно перенести ещё раз

**Откуда:** `research/cascade_algorithm.md` (строгий алгоритм, зафиксирован
пользователем, никакой самодеятельности), `prototype/forcaster/ui/app3.py`.

**Для чего использовалась:** исключительно LWR-прогноз att (направление A).

**Уже сделанный перенос (сегодняшняя сессия, для контекста):**
`prototype_analyzers/analyzers/lwr_cascade.py` — прямой перенос
`levels_aligned`/`_cascade_filter`/`lwr_predict` на произвольный каузальный 1D-ряд
(`predict_cascade`, `predict_no_cascade`), применённый к `slope`/`accel` из
`trend_variance.py`. Это уже случившийся пример нужного паттерна — стоит явно
зафиксировать, что каскад как аппарат «поиск похожих исторических паттернов
произвольного скалярного ряда» полностью общий, не привязан к att.

**Что ещё не пробовали:** сам каскад сейчас используется только чтобы получить
ЧИСЛО (точечный прогноз). Не пробовали использовать его как **браузер
исторических аналогов** — чисто аналитический инструмент: для текущего состояния
показать N ближайших исторических паттернов (даты, что произошло дальше,
разброс исходов) без обязательного усреднения в один прогноз. Это ближе к тому,
как пользователь фактически смотрит на LWR-предсказания в текущем UI (проверяет
себя визуально по соседям), но как отдельная функция — «what happened after
situations like this» — она нигде не выведена явно.

### 3. S-map с локализацией θ — калиброванное значение θ как диагностика режима, а не только параметр прогноза

**Откуда:** фаза 7, `research/phase7_fractality/17_large_scale_pooled/17f_calibrator.py`,
`17r_multiticker_calibrator.py` (память `research_multiticker_calibration_17r.md`,
`research_fan_density_28.md`).

**Для чего использовалась:** локализация пула соседей при прогнозе зигзаг-события.

**Что не пробовали:** сама ВЕЛИЧИНА откалиброванной θ по разным тикерам сильно
разбросана (0.73 у VTBR — почти глобальная OLS, до 25.7 у SBER — сильная
локализация) — это уже наблюдалось (эксп.17r), но интерпретировалось только как
факт «нужна индивидуальная калибровка», не как САМОСТОЯТЕЛЬНАЯ характеристика
инструмента. Гипотеза: θ* — это количественная мера того, насколько поведение
тикера определяется небольшим числом «архетипов» ситуаций (высокая θ → рынок
ведёт себя как переключение между дискретными режимами-аналогами) против
непрерывного континуума исходов (низкая θ → сглаженная регрессия работает
одинаково хорошо везде). Конкретная идея: посчитать θ* для широкого набора
тикеров/масштабов T и использовать это число как **классификатор структуры
рынка** (аналитическая таблица «какие тикеры MOEX ведут себя дискретно, какие —
гладко») — независимо от того, используется ли S-map для реального прогноза.

### 4. Filter bank (Butterworth C0–C5) — энергетический профиль компонент как метрика отбора пула, не только визуализация

**Откуда:** `research/phase3_filterbank/`, `sma/core/analysis/spectrogram.py`
(спектрограмма Δratio уже реализована как визуальный анализатор вкладки «Анализ»).

**Для чего использовалась:** (а) спектральное разложение перед LWR-прогнозом
медленных компонент (фаза 3-4, отклонено в пользу LP), (б) визуализация STFT в
`sma/ui/analysis.js`.

**Что не пробовали:** доля энергии, приходящейся на C0+C1 (шум) против C2-C5
(аттрактор) — уже вычисляется механически при построении filter bank — никогда
не использовалась как **критерий ранжирования тикеров для отбора кросс-тикерного
пула** (`sma/core/forecast/pool_selection.py` сейчас ранжирует ТОЛЬКО по
ликвидности — объём/оборот). Конкретная идея: посчитать энергетическую долю
C2-C5 для каждого кандидата пула и добавить её как второй, независимый критерий
отбора («не только ликвидный, но и структурно похожий по соотношению шум/сигнал
на целевой тикер») — до сих пор не проверялось, есть ли связь между спектральным
профилем тикера и тем, насколько он полезен как донор пула для другого тикера.

### 5. SSA (Singular Spectrum Analysis) — остаток SSA-очистки как самостоятельный индикатор микроструктуры, а не то, что выбрасывается

**Откуда:** `research/phase7_fractality/21_ssa_denoising/`,
`prototype/forcaster/ui/app6.py` (`_ssa_smooth_ratio`), память
`research_ssa_denoising_21.md`, `research_ssa_preprocessing.md`.

**Для чего использовалась:** предобработка/шумоподавление перед зигзагом или
перед LP-фильтром направления A.

**Ключевая находка, которая делает эту идею НЕ дублем отклонённых:** SSA-очистка
СИСТЕМАТИЧЕСКИ убирает вместе с шумом полезную структуру (эксп.21: raw
предсказуемее ssa_k2 предсказуемее ssa_k1, монотонно, на зигзаге). Это означает,
что убранная SSA часть сигнала (`raw − ssa_reconstruction`) сама несёт
предсказательную ценность — то, что сейчас просто выбрасывается. Конкретная
идея: не использовать SSA как фильтр входа, а вычислять **остаток SSA
(микроструктурный компонент)** как отдельный, самостоятельный ряд и смотреть на
его собственную структуру (амплитуду, автокорреляцию, кластеризацию) — как
диагностический сигнал «сколько содержательной микроструктуры выброшено бы при
сглаживании», без цели улучшить сам прогноз зигзага.

### 6. KF2D (Kalman filter 2D) — сейчас только эталон сравнения, никогда не использовался как альтернативный сглаживатель для UI

**Откуда:** упомянут в `research_cascade_search.md`, `empirical_findings.md`
(«KF2D q=0.4 как эталон траектории»).

**Для чего использовалась:** референсная сглаженная траектория att БЕЗ фазовой
задержки — визуальный ориентир при ручном сравнении методов прогноза в фазе 4-6.

**Что не пробовали:** `prototype_analyzers/app.py` сейчас строит линию тренда
через каузальную OLS-регрессию окна (`trend_variance.py`). KF2D — принципиально
другой сглаживатель (state-space, без фазовой задержки в отличие от скользящего
OLS-окна с задержкой на половину окна). Никогда не пробовался как альтернативная
линия тренда в самом простом, «не про прогноз» анализаторе — чисто визуальный
эксперимент: заменить/добавить рядом с OLS-линией KF2D-сглаженную линию и
посмотреть, насколько по-другому она подсвечивает текущее состояние тренда.
Дёшево, ортогонально уже отклонённым идеям (SSA-предобработка отклонена для
ДРУГОЙ задачи — входа в зигзаг, не для визуализации тренда).

### 7. Геодезические расстояния (T03b) — как самостоятельный индикатор «складчатости» многообразия, не только альтернативная метрика LWR

**Откуда:** `research/phase_theory/03_cascade_geometry/`, память
`research_geodesic_T03b.md`.

**Для чего использовалась:** альтернатива Евклидовой метрике при поиске соседей
в LWR (не доведено до форкастингового эксперимента, отложено).

**Что не пробовали:** сама величина `ratio_med = D_geo/D_euc` (для непрямых
соседей) уже посчитана по 4 тикерам и растёт с p (1.38 при p=9 → 1.96 при
p=144) — интерпретируется как мера «изгиба/складки» локального многообразия.
Никогда не пробовали превратить эту величину в **скользящий по времени
индикатор** (не статический снимок по 4 тикерам, а `ratio_med[t]`, посчитанный
в окне вокруг каждого origin) — потенциальный маркер моментов, когда
геометрия аттрактора локально «складывается» (Евклид и геодезика расходятся
сильнее обычного) — гипотетически совпадает с моментами смены режима. Это
чисто диагностическая, не прогнозная идея — не требует замены метрики в LWR,
только вычисления и визуализации самого расхождения во времени.

### 8. band_lambda / weighted_quantile движок — общий каузальный квантильный регрессор, привязанный только к цене по историческим причинам

**Откуда:** `sma/core/forecast/band_lambda.py`, `band_lambda_calibrator.py`.

**Для чего использовалась:** полоса неопределённости (h=1/h=2) для цены
следующего зигзаг-события, взвешенный пул по 6 ранговым признакам
(volume/trend/leg_age/velocity/acceleration/volatility).

**Что не пробовали:** вся машинерия (`build_causal_pool_with_mixed_ranks`,
`weighted_quantile`, многопроходный координатный спуск по λ) не знает про то,
что таргет — именно `log_pivot_prices[valid+horizon] - log_pivot_prices[valid]`
(строка `build_pool_vectors_with_ranks`). Замена ЦЕЛЕВОЙ переменной на **время
до следующего пивота** (bar-индекс следующего пивота минус текущий, вместо
ценового приращения) даёт готовый прогноз-полосу «когда» вместо «куда» — с тем
же откалиброванным λ-механизмом, без единой новой строчки инфраструктуры. Прямо
отвечает на явную потребность пользователя из `project_app9_use_case.md`:
«оповещения о новых событиях нужны для расстановки стопов» — полоса неопределён-
ности по ВРЕМЕНИ ожидания следующего события — практический, ранее не
пробованный продукт из уже существующих деталей.

### 9. acc_ang (взвешивание по угловому ускорению траектории) — детектор точек разворота, а не только вес соседей

**Откуда:** `research/phase4_components/78_angular_velocity.py`,
`79_acceleration_search.py`, память `research_neighbor_quality.md`.

**Для чего использовалась:** финальный отбор соседей в каскаде LWR-прогноза att
— близкие по «кривизне» траектории (насколько похоже гнётся аттрактор) соседи
дают лучший прогноз (−10.8% rMAE).

**Что не пробовали:** `d_ang(acc)` (косинусное расстояние между векторами
углового ускорения) само по себе — мера того, насколько РЕЗКО меняется
направление изгиба траектории att в конкретной точке. Никогда не выводилась как
самостоятельная величина `|acc_ang[t]|` (не расстояние до соседа, а собственное
угловое ускорение траектории в момент t) — потенциальный **безнадзорный
детектор разворотных точек** аттрактора (аналог «пика кривизны» на фазовом
портрете), полностью независимый от прогноза — можно накладывать на график att
как маркеры «моментов резкого изгиба» без всякого LWR.

### 10. logtrend (каузальный OLS-тренд по всей истории) — долгосрочный индикатор силы тренда, а не только нормализация

**Откуда:** `sma/core/forecast/normalize.py`, ключевое методическое решение
CLAUDE.md.

**Для чего использовалась:** нормализация цены перед прогнозом (`ratio =
close/exp(logtrend)`), убирает нужду в окне MA.

**Что не пробовали:** logtrend вычисляется через инкрементальные суммы —
дёшево пересчитывается для ЛЮБОЙ длины истории. Наклон `b` этой регрессии на
всей доступной истории — по сути «структурный бета» инструмента за весь срок
наблюдений — никогда не визуализировался и не использовался как самостоятельный
индикатор (в отличие от `slope` в `trend_variance.py`, который считается на
скользящем window=200 и уже используется как осциллятор). Идея: второй,
существенно более медленный осциллятор «logtrend slope за всю историю» рядом с
уже существующим коротким — не для прогноза, а как контекст «на каком фоне
долгосрочного тренда сейчас находится короткая динамика» (аналог long-term vs
short-term momentum divergence, но выведенный из уже посчитанной, а не новой
величины).

### 11. Permutation Entropy — как самостоятельный «оscillator упорядоченности», не фильтр соседей

**Откуда:** `prototype/forcaster/forecast/pe.py`, экспы 21-27 (память
`research_chaos_analysis.md`, `ideas_neighbor_selection.md`).

**Для чего использовалась:** мягкий/жёсткий вес соседей в пуле LWR по близости
PE — эффект скромный (до −10.5% при p=20, α=0.5, статистически незначим на
одном тикере).

**Что не пробовали:** `rolling_pe(series, win)` уже реализована и вычисляет
локальную PE-кривую вдоль всего ряда — но используется только как маска для
пула. Никогда не выводилась как самостоятельный осциллятор на графике (по
аналогии с Hurst-зонами, но PE — принципиально другая величина: не
персистентность, а «упорядоченность локальных паттернов»). Низкая PE
исторически коррелирует с меньшим числом ложных соседей по FNN — потенциально
информативна как ВИЗУАЛЬНЫЙ индикатор «участок ряда сейчас структурирован vs
хаотичен», отдельно от того, помогает ли она прогнозу количественно.

### 12. D₂ / корреляционная размерность (`research/tools/d2_embedding.py`) — как кросс-тикерный «отпечаток сложности», а не параметр одного прогноза

**Откуда:** `research/tools/d2_embedding.py`, теоретическая ветка
(`research/phase_theory/`).

**Для чего использовалась:** оценка размерности вложения зигзаг-пивотов для
выбора p в конкретном прогнозе; как компонент диагностики аттрактора att в
фазе 5 (оба раза как предиктор качества прогноза — везде r≈0, отклонено).

**Что не пробовали:** сама D₂ (не как предиктор точности, а как ХАРАКТЕРИСТИКА
инструмента) никогда не сравнивалась систематически МЕЖДУ тикерами/масштабами
T как самостоятельная классификация. Конкретная идея: посчитать D₂ облака
зигзаг-пивотов для широкого набора (тикер × T) комбинаций и построить
рейтинг/кластеризацию «какие инструменты MOEX структурно ближе к
низкоразмерному процессу, какие — к чистому шуму» — чисто описательная
аналитика рынка, без привязки к тому, что D₂ уже дискредитирована как predictor
для КОНКРЕТНОГО прогноза (это другая роль величины — не gate одного прогноза,
а сравнительная классификация множества инструментов).

### 13. Объёмная плотность пивотов (density_rank, эксп.20b) — готовый visual volume profile, а не только неудавшийся предиктор коррекции

**Откуда:** `research/phase7_fractality/20_price_levels/20b_volume_profile_check.py`,
`sma/core/forecast/band_lambda.py::compute_density_rank_series` (уже
production-код, используется как один из 6 λ-признаков band_lambda).

**Для чего использовалась:** (а) ретроспективная проверка — пивоты зигзага
статистически падают в зоны низкой объёмной плотности (p<0.0001, воспроизведено
на всех 7 тикерах) — сильная и надёжная находка; (б) три попытки конвертировать

все три провалились (`research_price_levels_20.md`).

**Что не пробовали:** сама функция `compute_density_rank_series` уже считает
классический каузальный volume profile — но выводилась только как скрытый
входной признак калибратора, никогда как САМОСТОЯТЕЛЬНЫЙ визуальный слой на
графике (горизонтальная гистограмма объёма по ценовым уровням в скользящем
окне — то, что трейдеры называют volume profile / HVN-LVN карта). Учитывая, что
единственная воспроизводимая находка про уровни во всём проекте — именно это
(п. `research_price_level_analysis_2608.md`: «если возвращаться — смотреть
именно туда»), чисто визуальная выкладка этой уже посчитанной величины —
низкозатратный, идейно обоснованный шаг, не требующий одобрения LOO-теста
(это не прогноз, просто карта того, что уже произошло).

### 14. Simplex projection (Sugihara) — как инструмент проверки причинности между тикерами (CCM), а не только метод-кандидат для точечного прогноза

**Откуда:** `research/reference/simplex_ref.py`, использовался в 4-way
ансамбле (`zigzag_forecast_ref.py`) и в сравнении методов (эксп.15) — везде как
рядовой конкурент LWR/S-map/RBF для прогноза цены зигзаг-события; LA0 неизменно
обходит его (память `research_method_sweep_15.md`).

**Для чего использовалась:** точечный прогноз следующего плеча зигзага.

**Что не пробовали:** Simplex projection — базовый строительный блок метода
Convergent Cross Mapping (CCM, тот же Sugihara), который отвечает на
принципиально другой вопрос: не «какое следующее значение», а «есть ли
нелинейная причинная связь между двумя временны́ми рядами» (в отличие от
линейной корреляции доходностей, которая многократно проверялась в проекте и
неизменно давала слабый сигнал — H3 в эксп.17, `research_swing_efficiency_22.md`,
20i). CCM — качественно другой инструмент (нелинейное динамическое сцепление,
не линейная синхронность), раскрыт подробнее в Угле 2, п. 1.

## Угол 2 — новые идеи (прогностические и аналитические)

Сверено с памятью на предмет уже отклонённых направлений: круглые числа,
сырой объём в векторе признаков, корреляция доходностей пиров как вес/фильтр,
простая экстраполяция ускорения slope на цену, статичный split истории для
уровней, HVN-расстояние как предиктор величины хода, ATR/волатильность как
ex-ante гейт крупного движения, Efficiency Ratio (оба варианта), адаптивный
vol-нормированный порог зигзага, SSA/logtrend перед крупномасштабным зигзагом,
level-crossing сетки (R=1 и R>1), постфактум-коррекция амплитуды (5 разных
форм), усреднение по θ/T/m без пересчёта, раздельная калибровка по направлению,
Хёрст как гейт качества прогноза, per-ticker in-sample калибровка
коррекционных параметров — ничего из перечисленного ниже это не повторяет.

### 1. Convergent Cross Mapping (CCM) между тикерами MOEX — причинность вместо корреляции

Корреляция доходностей пиров как признак/вес проверена и отклонена дважды
(H3 в эксп.17 — слабо и метод-зависимо; 20i — 0/7 тикеров с улучшением). Но
корреляция — линейная, симметричная мера. CCM (Sugihara et al., тот же
формализм, что уже частично используется через Simplex projection в проекте)
измеряет НЕЛИНЕЙНОЕ динамическое сцепление и умеет быть **асимметричным**:
«att(GAZP) предсказывает att(SBER) лучше, чем наоборот» — принципиально
недоступно линейной корреляции. Конкретный план: для набора пар тикеров MOEX
(уже собранный пул из `pool_selection.py`) построить delay-embedding каждого
ряда att, скрёстно предсказать один по библиотеке другого (simplex projection,
уже есть готовая реализация в `simplex_ref.py`) и посмотреть на сходимость
кросс-предсказания с ростом длины библиотеки — признак настоящей causal
coupling. Аналитический продукт: карта направленных связей между российскими
голубыми фишками («что реально ведёт, а не просто ходит вместе») — самоценна
независимо от того, даст ли она прирост в прогнозе.

### 2. Мультифрактальный DFA (ширина спектра Δα) вместо/вместе с одиночным Хёрстом

Хёрст как гейт качества ЕДИНИЧНОГО прогноза уже дважды отклонён (фаза 1, r≈0).
Но это была проверка ОДНОГО числа (среднего показателя персистентности) как
предиктора точности. Мультифрактальный спектр (MF-DFA) даёт качественно другую
величину — не «средняя персистентность», а «насколько сильно локальная
персистентность варьируется по масштабам» (ширина Δα = мера гетерогенности
волатильности во времени, связана с кластеризацией волатильности). Это другая
информация, не переиспользование отклонённой. Конкретная идея: посчитать
Δα в скользящем окне для нескольких тикеров, проверить (а) стабильность оценки,
(б) связь ширины спектра с последующим режимом волатильности (не с точностью
прогноза — с самим фактом кластеризации). Чисто описательный первый шаг,
прогностическое применение — вторым.

### 3. Recurrence Plots — визуальный, не сводимый к DET

DET (Recurrence Quantification Analysis) как СВОДНОЕ ЧИСЛО-гейт для качества
прогноза уже проверялся и отклонён (r≈0.13, фаза 2, слабый гейт). Но сам
recurrence plot — двумерная визуализация, а не число — никогда не строился как
самостоятельный инструмент для глаз аналитика. Идея (низкий риск, чисто
разведочная): построить recurrence plot для att нескольких тикеров/периодов и
визуально поискать ламинарные зоны (диагональные полосы = детерминированные
периоды), белый шум (отсутствие структуры) и резкие переходы (смена режима) —
качественный инструмент «посмотреть глазами на структуру», который не пытается
конкурировать с уже провалившимся DET-как-числом.

### 4. Полоса ожидания времени до следующего пивота (реализация п.8 Угла 1)

Уже описано в Угле 1 как перенос существующей инфраструктуры band_lambda на
новую целевую переменную (bar-индекс следующего пивота вместо цены). Отмечаю
здесь отдельно как ПРОГНОСТИЧЕСКИЙ продукт, а не диагностику: даёт полосу
[q10..q90] «через сколько баров ожидать следующее подтверждённое событие»,
калибруемую тем же λ-механизмом. Прямой ответ на зафиксированную потребность
пользователя (алерты для стопов, `project_app9_use_case.md`).

### 5. Anomaly-алерт по остатку LP-фильтра (noise-компонента)

Направление A явно постулирует разложение `ratio_smooth (att) + noise`, где
noise помечен как «TBD» для прогноза (GARCH/AR/zero, ни один не реализован).
Вместо попытки ПРОГНОЗИРОВАТЬ noise — использовать амплитуду `|noise[t]|`
напрямую как **детектор аномального бара**: скользящий перцентильный порог
(без прогноза, чисто дескриптивно) — бар, где LP-фильтр не смог «переварить»
движение в рамках локальной геометрии аттрактора, помечается как структурно
необычный. Дёшево (noise уже вычисляется как побочный продукт LP), не требует
решения нерешённой задачи прогноза noise.

### 6. Кросс-секционный индекс дисперсии тренда по всему отслеживаемому пулу тикеров

`trend_variance.py` (скользящий slope + resid_var) сейчас — чисто one-ticker
анализатор. Идея: для ВСЕХ тикеров пользователя одновременно посчитать текущий
`slope[origin]`, свести в единое распределение и построить простой
макро-индикатор «разброс наклонов по рынку сейчас» — узкое распределение
(все тикеры трендуют в одну сторону) vs широкое (разнонаправленное движение,
«рынок выбора акций», а не общий тренд). Синтез существующего инструмента на
новом, портфельном уровне агрегации — не новый метод, но новая ГРАНУЛЯРНОСТЬ
применения, которой сейчас нет нигде в проекте (всё исследуется per-ticker).

### 7. Символическая динамика: полная матрица переходов ординальных паттернов

Скалярная PE как ВЕС уже проверена (эксп.21-24) — эффект слабый и незначим на
одном тикере. Но PE — это ЭНТРОПИЯ распределения ординальных паттернов, теряет
информацию о ПОРЯДКЕ переходов между ними. Идея качественно другая: построить
Марковскую матрицу переходов между ординальными символами (какой паттерн длины
p сменяется каким) в скользящем окне и смотреть на энтропийную СКОРОСТЬ
(entropy rate) — насколько предсказуем СЛЕДУЮЩИЙ паттерн, зная текущий, а не
просто насколько равномерно распределены паттерны сами по себе. Не пересечение
с уже проверенной гипотезой (PE weight), другая математическая конструкция.

### 8. Кросс-вейвлет когерентность между парами рядов

Корреляция доходностей пиров (глобальный скаляр по всему окну) — многократно
проверена и слаба. Кросс-вейвлет когерентность — локализованная по времени И
по частоте мера синхронности фазы между двумя рядами: возможно, пары тикеров
(или тикер против курса рубля/нефти) когерентны НЕ везде и не на всех
масштабах, а в конкретных полосах частот и периодах — то, что единый
корреляционный коэффициент по определению не увидит. Дороже в реализации, чем
остальные пункты списка — кандидат на отдельное согласование по протоколу
(шаг 1 CLAUDE.md) при заинтересованности.

### 9. Кривизна графа ближайших соседей (Оливье-Риччи) в delay-пространстве att

Теоретическая ветка (`research/phase_theory/`) имеет явный карт-бланш на
математику. LB (SVD-плоскость) и геодезическое/евклидово соотношение (T03b) —
уже опробованные геометрические диагностики этого пространства. Кривизна
Оливье-Риччи на k-NN графе — третий, качественно иной геометрический
инструмент: измеряет, «расширяются» ли локальные окрестности вдоль рёбер графа
(положительная кривизна — устойчивая, хорошо перемешанная геометрия) или
«схлопываются» (отрицательная — нестабильность, потенциальный признак редкого/
непредсказуемого кармана аттрактора, в духе уже найденного различия между
origin 4772 и 4657 в `research_T04_cascade_observations.md`). Спекулятивный,
дорогой, но прямо в духе заявленного пользователем «полного карт-бланша» на
теоретической ветке.

### 10. Перенос событийной фрактальности на нефинансовый ряд

Пользователь сам явно заявил намерение проверить метод на нефинансовых данных
(`research_event_scale_invariance.md`: «Пользователь планирует проверить на
нефинансовых рядах (научное любопытство)»). Метод (zigzag threshold + k-NN /
S-map в событийном времени) не использует ничего специфичного для биржи — три
требования: непрерывный ряд, определение «значимого разворота», иерархическая
фрактальная структура. Конкретный шаг для следующей сессии — выбрать один
доступный нефинансовый ряд (сейсмичность, солнечная активность, любой
длинный временной ряд, до которого есть доступ) и прогнать тот же пайплайн
(`build_zigzag` + `band_lambda`/`smap_band_weighted_ref.py`) без переделки
алгоритма — прямая проверка гипотезы «фрактальность зигзага — не биржевой
артефакт».

### 11. «Пульт управления рынком» — синтез уже готовых диагностик на уровне всего портфеля тикеров

Не новый метод, а явный ответ на сформулированное пользователем видение
(«комбинация уже сделанных необычных анализаторов/прогнозаторов даёт свежий
взгляд на биржевую кухню»): единая страница/вкладка, сводящая по ВСЕМ
отслеживаемым тикерам одновременно: (а) LB-гейт направления A (п.1 Угла 1,
светофор надёжности), (б) ширину калиброванной band_lambda-полосы направления
B относительно цены (узкая = уверенность), (в) кросс-секционный индекс
дисперсии тренда (п.6 выше). Каждый компонент уже существует по отдельности —
работа здесь чисто интеграционная (агрегация + один экран), не исследовательская,
но именно такого сведения сейчас нигде нет — все инструменты живут
per-ticker/per-эксперимент.

### 12. Суррогатный тест как переиспользуемый инструмент, не разовый скрипт

Суррогатный тест T01 (shuffle/FT/AAFT/block-shuffle сравнение против оригинала
по LWR) был написан один раз для конкретной теоретической проверки
(`research_surrogate_T01.md`) и никогда не оформлялся как переиспользуемый
модуль. Учитывая, что протокол экспериментов (шаг 3 CLAUDE.md, «критика
постановки») требует явно проверять, не артефакт ли найденный сигнал — упаковка
T01 в `research/tools/surrogate_test.py` (по аналогии с уже существующими
`fnn.py`, `sanity_check_forecast.py`) как первый шаг любого НОВОГО эксперимента
Угла 2 из этого списка — малозатратная методологическая инвестиция, снижающая
шанс повторить историю эксп.28 (accuracy/rMAE расхождение) или эксп.24/25/26/27
(серия ложных находок про уровни, которые пришлось откатывать одну за другой).

## Приоритизированный шорт-лист — с чего начать

1. **LB-гейт как живой UI-индикатор (Угол 1, п.1).** Уже полностью
   исследован и статистически подтверждён (34.7%, p≈4.5e-39) — единственный
   пункт списка, не требующий НИКАКОГО нового эксперимента, только перенос
   готовой формулы в интерфейс. Самый дешёвый и самый обоснованный шаг.
2. **Volume profile как визуальный слой (Угол 1, п.13).** Единственная
   воспроизводимая находка про уровни во всём проекте, функция уже написана
   и работает в production (`compute_density_rank_series`) — не хватает
   только визуализации самой по себе, не как скрытого признака.
3. **Полоса времени до следующего пивота (Угол 1 п.8 / Угол 2 п.4).**
   Прямой ответ на явно сформулированную пользователем потребность (алерты
   для стопов), реализуется поверх существующего band_lambda без новой
   инфраструктуры — только новая целевая переменная.
4. **CCM между тикерами MOEX (Угол 2, п.1).** Качественно новый вопрос
   (причинность вместо корреляции), не пересекается ни с одним отклонённым
   выводом, использует уже написанный `simplex_ref.py` как строительный
   блок — хорошее соотношение новизны/усилий, прямое попадание в интерес
   пользователя к нелинейной динамике.
5. **Anomaly-алерт по LP-noise (Угол 2, п.5).** Использует уже вычисляемую
   величину (noise-компонента), не требует решения нерешённой задачи
   прогноза noise, чисто дескриптивный — низкий риск, быстрая проверка.
6. **θ* как классификатор структуры рынка (Угол 1, п.3).** Данные по 7
   тикерам уже собраны (эксп.17r) — не нужен новый прогон, только
   переинтерпретация и расширение на больше тикеров/масштабов T.
7. **Перенос на нефинансовый ряд (Угол 2, п.10).** Явно заявленное
   пользователем намерение, никакой переделки алгоритма не требует — вопрос
   выбора конкретного датасета и одного прогона.
8. **«Пульт управления рынком» (Угол 2, п.11).** Самый крупный по объёму
   работы пункт списка, но прямой и явный ответ на сформулированное видение
   проекта («свежий взгляд на биржевую кухню» через комбинацию уже
   существующих инструментов) — имеет смысл держать в очереди после того,
   как накопится 2-3 готовых компонента из пунктов 1-6.

Все пункты 1–8 совместимы с протоколом экспериментов CLAUDE.md (шаг 1 —
согласование параметров и критика перед запуском) и ни один не повторяет
явно отклонённые направления, зафиксированные в памяти проекта.
