# План: перенос анализатора «скользящий тренд + дисперсия» в основное приложение (sma/)

Статус: план написан 2026-08-17, **реализовано 2026-08-18** (backend + frontend,
см. §4 — все пункты выполнены; §6 «Визуальная сверка с прототипом» и ручная
проверка origin/persistence в живом UI — за пользователем, браузерное
расширение было недоступно в сессии переноса).

Прототип: `prototype_analyzers/` (app.py + analyzers/trend_variance.py) — рабочая,
проверенная на реальных данных версия, от которой этот план отталкивается. Скрипты
предсказуемости (`slope_predictability_*.py`, `accel_predictability_sweep.py`,
`price_forecast_*.py`) и вся ветка про уровни (`level_*.py`) в перенос НЕ входят —
это была разведка, результат которой — понимание, что показывать в UI можно только
измеренные величины (тренд, дисперсия, ускорение), не прогноз.

## 1. Контекст и обоснование

CLAUDE.md фиксирует модульность: «новые анализаторы — в `sma/core/analysis/`, свой
файл на анализатор». Сейчас там один анализатор — спектрограмма
(`sma/core/analysis/spectrogram.py`, `research/reference` не при чём, портирован из
прототипа в 2026-08). Его же докстринг явно говорит: «add a second analyzer by
adding a second module + route branch, not by building the abstraction preemptively»
— т.е. общей инфраструктуры под несколько анализаторов пока нет, наш перенос будет
первым прецедентом добавления ВТОРОГО анализатора, и одновременно проверкой того,
насколько текущий YAGNI-подход выдерживает это добавление.

## 2. Требования пользователя (дословно, 2026-08-17)

Из сессии разработки прототипа:

- Скользящее окно (по умолчанию 200, диапазон расширен до 2000) + OLS-тренд +
  НЕСКОЛЬКО вложенных полос `±k·std(остатков)`.
- **Полос можно добавить произвольное количество**, добавляются в порядке убывания
  (сначала крупные). По умолчанию — **1 полоса**.
- Границы полос можно **продлить пунктиром на n шагов вперёд** (линейная
  экстраполяция текущего slope, без ускорения, ширина полосы постоянна) — по
  умолчанию **выключено**.
- Осциллятор: переключатель наклон (slope, гистограмма зелёный/красный по знаку) /
  дисперсия (resid_var, area). **Опционален** — отдельная галочка «Показать
  осциллятор», по умолчанию **выключена** (правка 2026-08-18): полный проход
  `rolling_trend_variance` по всей истории считается только при включённой
  галочке (не только экономия расчёта — не занимает/не сбивает автоматом
  подпанель `S.subpanel`, которая может быть занята другим осциллятором,
  напр. спектрограммой). Локальный наклон для продления полос (см. ниже)
  берётся из уже посчитанного `single_window_trend` окна
  (`(fitted[-1]-fitted[0])/(window-1)`), НЕ из `slope_series[origin]` — значит
  продление полос не тянет за собой полный rolling-расчёт, даже если
  осциллятор выключен.
- «Веер ускорения» — вспомогательная аналитика (треугольник из начала окна: текущий
  тренд vs тренд с учётом усреднённого по m точкам ускорения на n_accel шагов) — по
  умолчанию **выключен**.
- **При изменении любых настроек анализатор должен «держать» точку отсчёта**, не
  сбрасывать её (баг прототипа: Streamlit-виджеты не гарантируют сохранение
  состояния между settings-change reruns).
- **Последние настройки (кроме точки отсчёта) сохраняются per-тикер** — «в целом
  уже по стандарту у нас».

## 3. Разведка текущей архитектуры (сделана 2026-08-17, актуальна на момент написания)

### 3.1 Персистентность настроек — уже есть, без изменений схемы

`analysis_settings` таблица (`sma/core/db.py`) уже универсальна:
`(instrument_id, interval, analyzer_type, params_json)`. Роуты уже есть
(`sma/api/routes/series.py:66-90`, `GET/POST /series/analysis-settings`).
Спектрограмма её использует как готовый паттерн (`sma/ui/analysis.js`):

- `loadSpectrogramDefaults()` — на смену тикера/интервала (вызывается из
  `app.js:loadCandles`), подтягивает последние параметры для
  `(instrument_id, interval, analyzer_type='spectrogram')`, либо оставляет
  хардкод-дефолты формы, если ничего не сохранено.
- `saveSpectrogramSettings()` — debounce 500мс, POST fire-and-forget после
  успешного расчёта / любого визуального изменения.

**Требование п.2/«уже по стандарту» закрывается ПОЛНОСТЬЮ переиспользованием этого
механизма** с `analyzer_type='trend_variance'` — новых таблиц/роутов не нужно,
только зеркальные `loadTrendVarianceDefaults()` / `saveTrendVarianceSettings()` в
новом JS-модуле.

### 3.2 Точка отсчёта («держать», не сбрасывать) — открытый архитектурный вопрос

В Streamlit-прототипе баг («переносится в ноль») — следствие модели Streamlit:
скрипт перевыполняется целиком на каждое изменение виджета, значение слайдера
origin не гарантированно переживает пересчёт `min_value`, если тот меняется от
других виджетов (окно/m_accel).

В `sma/ui/` этой проблемы структурно нет — состояние живёт в объекте `S`
(`sma/ui/state.js`), не пересчитывается заново при каждом рендере.
`renderChart({preserveRange:true})` — единственная точка входа для перерисовки,
вызывается после ЛЮБОГО изменения состояния и сохраняет пользовательский зум
(`getCurrentRanges()`), не сбрасывая его. Значит «держать точку отсчёта» здесь
получаем почти бесплатно, ЕСЛИ origin анализатора живёт в `S` и не пересчитывается
по умолчанию при рендере — но нужно решить, ЧТО такое «точка отсчёта» в проде:

- **Вариант A (проще, как у спектрограммы)**: точки отсчёта нет вовсе — анализатор
  всегда считается «вживую», от последнего доступного бара (аналог
  `spectrogram-depth`: N последних баров). Тривиально удовлетворяет требованию
  (нечему сбрасываться). Теряется прототипная возможность разглядывать
  ИСТОРИЧЕСКИЙ снимок тренда (origin в середине истории).
- **Вариант B (богаче)**: переиспользовать уже существующий `S.originTs`
  (`sma/ui/state.js:6`) — точку, которую сейчас устанавливает клик по свече
  (`sma/ui/chart.js:_onCandleClick` → `setOrigin`), используемую для позиционирования
  НОВОГО прогноза. `S.originTs` уже персистентен между рендерами и переживает любые
  settings-change по конструкции `S`. Риск — семантическая путаница: один клик по
  свече будет одновременно значить «сюда прогноз» и «отсюда анализатор», если не
  развести явно (например, отдельный `S.trendVarianceOriginTs`, устанавливаемый
  своим кликом/тумблером «выбрать точку для анализатора»).

**Рекомендация**: начинать с варианта A (без выбора origin, всегда последний бар) —
закрывает 90% ценности («что происходит с трендом/дисперсией прямо сейчас»),
architecturally проще, и его тривиально не сломать в духе «держит точку отсчёта».
Вариант B — отдельная итерация, если понадобится смотреть на исторические срезы;
явно обсудить с пользователем перед стартом реализации, не решать по умолчанию.

### 3.3 Основной график — новый тип интеграции (не подходит ни один существующий)

Два существующих способа рисовать поверх графика:
- `buildSubpanelTraces()` (`chart.js:185`) — heatmap во ВТОРОЙ (`yaxis2`) панели,
  переключается через `S.subpanel` (`'none' | 'spectrogram'`). Подходит для
  ОСЦИЛЛЯТОРА нашего анализатора (slope/var — обычные line/bar трейсы, не heatmap,
  но тот же `y2`-слот и тот же `S.subpanel` переключатель, только добавить третье
  значение `'trend_variance'`). **`S.subpanel` переключается в `'trend_variance'`
  ТОЛЬКО когда включена галочка «показать осциллятор»** (см. п.2, правка
  2026-08-18) — сам факт выбора анализатора `trend_variance` в
  `#analyzer-type-select` не должен автоматически занимать/сбрасывать
  подпанель, если пользователь осциллятор не запросил (иначе при переключении
  между анализаторами подпанель непредсказуемо перескакивает между
  spectrogram/trend_variance).
- `MODEL_DISPLAY` реестр (`chart.js:481-501`) + `buildVisibleOverlays()` — оверлеи
  ПРОГНОЗОВ (band_lambda/simplex_ensemble), завязаны на `S.renderedForecasts`
  (конкретный `forecast_id` из БД). Наш тренд+полосы — НЕ прогноз-объект с id,
  это live-результат текущих настроек анализатора, этот механизм не подходит
  напрямую.

**Нужна третья точка встраивания**: `buildTrendVarianceMainTraces()` — обычная
функция, как `buildZigzagTrace()` (chart.js:280), вызывается напрямую из
`renderChart()` (добавить в список `allTraces`, не через `buildVisibleOverlays`).
Полосы — тот же паттерн invisible-line + `fill:'tonexty'`, что уже используется трижды
в прототипе и один раз в `buildSimplexMeanBandTraces` (chart.js:698) — переносится
почти дословно. Порядок отрисовки полос (крупные под мелкими) — тот же принцип,
что уже задокументирован для `buildBandZoneShapes` (chart.js:394-396,
«Widest first / narrowest last»), просто переиспользуется идея, не код напрямую
(разные структуры данных).

### 3.4 Core-модуль и API

`analyzers/trend_variance.py` (прототип) → почти без изменений в
`sma/core/analysis/trend_variance.py`:
- `rolling_trend_variance(y, window)` — переносится как есть (уже протестирована
  против `np.polyfit`, см. прототип).
- `single_window_trend(y, origin, window)` — тоже как есть.
- Веер ускорения (`analyzers/lwr_cascade.py` НЕ переносится — это была
  research-инфраструктура для проверки предсказуемости, в проде не нужна; сама
  формула ускорения — наклон OLS `slope_series` по последним `m` точкам — тривиально
  переносится через повторный вызов `single_window_trend`, без каскада).

Роут — по образцу `POST /series/spectrogram` (`sma/api/routes/series.py:31-63`):
синхронный (не через TaskManager — вычисление O(N), доли секунды даже на
многотысячных сериях, тот же класс стоимости, что у спектрограммы). Новый
Pydantic-класс `TrendVarianceRequest` (ticker, data_source, interval, window,
bands: list[float], show_extension: bool, n_future: int, show_oscillator: bool,
show_accel_fan: bool, m_accel: int, n_accel: int). Возвращает одним ответом:
- `trend_price`, `band_hi_price[]`/`band_lo_price[]` на каждый k из `bands`
  (для текущего/последнего origin — см. §3.2); экстраполяция при
  `show_extension` использует локальный наклон текущего окна (из фита
  `single_window_trend`, НЕ полный `rolling_trend_variance`);
- `slope_series`, `var_series` (полные, для осциллятора) — **вычисляются и
  включаются в ответ ТОЛЬКО при `show_oscillator=true`** (правка 2026-08-18,
  см. п.2) — не тратим O(N) rolling-проход, если панель осциллятора не
  запрошена;
- при `show_accel_fan` — координаты веера.

## 4. Детальный план

### 4.1 Backend

1. `sma/core/analysis/trend_variance.py` — порт `rolling_trend_variance` +
   `single_window_trend` + тонкий compute-слой (аналог `compute_spectrogram`),
   возвращающий словарь под ответ роута (см. §3.4).
2. `sma/api/routes/series.py` — добавить `TrendVarianceRequest` +
   `POST /series/trend-variance` (использует уже существующий `get_analysis_settings`/
   `upsert_analysis_settings` — без изменений).
3. Проверка каузальности — как и для остальных модулей: `rolling_trend_variance`
   уже каузальна по построению (окно `[t-window+1, t]`), формальный тест по
   образцу `causality_check*.py` не обязателен, но стоит явно прогнать (обрезка+
   пересчёт = префикс) перед мержем — дёшево, соответствует общему стандарту
   проекта (`feedback_causality_enforcement`).

### 4.2 Frontend

1. `sma/ui/state.js` — добавить `trendVarianceData: null`,
   `trendVarianceSettings: { window: 200, bands: [2.0], showExtension: false,
   nFuture: 50, showOscillator: false, oscMode: 'slope', showAccelFan: false,
   mAccel: 50, nAccel: 50 }` (дефолты — ровно как в прототипе после правок
   2026-08-18: 1 полоса, продление/осциллятор/веер выключены).
   `S.subpanel` — добавить третье значение `'trend_variance'`, но
   выставляется оно ТОЛЬКО когда `trendVarianceSettings.showOscillator===true`
   (см. §3.3) — выключение галочки должно возвращать `S.subpanel` в
   `'none'` (или в то, что было выбрано до), не оставлять «повисший» третий
   режим.
2. `sma/ui/analysis.js` (или новый `sma/ui/trend_variance.js`, если файл спектрограммы
   разрастётся при добавлении — см. CLAUDE.md «модульность», порог ~300-400 строк) —
   `loadTrendVarianceDefaults()` / `saveTrendVarianceSettings()` (зеркало
   спектрограммных, §3.1), `calculateTrendVariance()`, `toggleTrendVarianceDisplay()`.
   `calculateTrendVariance()` шлёт `show_oscillator: trendVarianceSettings.showOscillator`
   в запрос (§3.4) — эндпоинт не считает/не возвращает `slope_series`/`var_series`,
   если галочка выключена.
3. `sma/ui/chart.js` — `buildTrendVarianceMainTraces()` (тренд + N полос + опц.
   продление, §3.3), расширить `buildSubpanelTraces()` веткой
   `S.subpanel === 'trend_variance'` (bar для slope / area для var — переносится
   из прототипа как есть, просто в Plotly.js вместо `go.Bar`/`go.Scatter`); эта
   ветка не должна рендериться, если `showOscillator===false` — при выключенной
   галочке график однопанельный, как без осциллятора (ср. прототип: `rows=1`
   вместо `rows=2` в `make_subplots`).
4. `sma/ui/index.html` — второй `<option value="trend_variance">` в
   `#analyzer-type-select`; новый блок контролов (окно, список полос — см. §4.3,
   переключатель осциллятора, чекбокс+слайдер продления, чекбокс+слайдеры веера);
   `onchange` на `#analyzer-type-select`, переключающий видимость блоков
   спектрограммы/тренда (сейчас там только один блок — этой развилки ещё нет
   нигде, будет ПЕРВЫЙ прецедент).

### 4.3 UI для «произвольного количества полос»

Простейший вариант (YAGNI, соответствует духу текущего кода — ср. докстринг
`spectrogram.py` §1): текстовое поле, значения через запятую (`"2, 3.5"`), парсится
и сортируется по убыванию на клиенте перед отправкой/рендером — эквивалент
прототипных `k1/k2/k3`, но без ограничения в три штуки и без фиксированных
слайдеров на каждую полосу. Динамический список с кнопками добавить/удалить —
более полированный вариант, не обязателен для первой итерации, можно отложить.

## 5. Порядок выполнения

1. Core-модуль + роут (backend можно проверить curl'ом/pytest независимо от UI).
2. `state.js` + `chart.js` (главный график: тренд+полосы, без осциллятора и без
   продления — самый ценный кусок, проверяем на реальном тикере).
3. Осциллятор (`buildSubpanelTraces` ветка + переключатель).
4. Продление полос пунктиром.
5. Веер ускорения (самое вспомогательное — последним, если время останется).
6. Персистентность настроек (`analysis.js` load/save) — технически может идти
   параллельно с 2-5, т.к. не зависит от них.

## 6. Проверка

- Визуальная сверка с прототипом на одном тикере (SBER 1d) — совпадение линии
  тренда/полос/осциллятора на одинаковых параметрах (window/k).
- Каузальность core-модуля (обрезка+пересчёт=префикс, §4.1).
- Ручная проверка требования «держит origin» — покрутить все настройки, origin
  (при выбранном варианте B) не должен прыгать.
- Ручная проверка persistence — сменить тикер и обратно, настройки должны
  восстановиться.

## 7. Границы этой итерации (явно НЕ переносится)

- Вся research-инфраструктура предсказуемости (`slope_predictability_*.py`,
  `accel_predictability_sweep.py`, `lwr_cascade.py`, `predictability.py`,
  `price_forecast*.py`) — она проверяла ГИПОТЕЗЫ, не нужна как рантайм-код.
  Вывод из неё (slope/accel — не прогноз, не бить персистенцию цены) уже
  отражён в том, что анализатор показывает только измеренные величины.
- Ветка про уровни (`level_*.py`) — не дала воспроизводимого сигнала, в
  анализатор не переносится ничего (см. память `research_price_level_analysis_2608`).
- Вариант B точки отсчёта (исторический origin) — только если явно попросят
  после того, как вариант A обкатается.
