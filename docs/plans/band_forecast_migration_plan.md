## 1. Контекст и обоснование

Направление B фазы 7 (событийная фрактальность зигзага) довело прогноз **полосы неопределённости** (не точки) до рабочего, одобренного пользователем состояния. Старая модель прогноза в `sma/` (LA1/LWR, «Направление A») признана пользователем нерабочей и подлежит полному удалению вместе с накопленными в БД старыми прогнозами.

Итог исследовательской сессии 2026-07-08, который переносится в приложение:

- **Многопроходная λ-калибровка** веса пула по 6 признакам (координатный спуск до сходимости): `research/reference/band_lambda_calibrator_ref.py`.
- **Живой прогноз полосы** с уже откалиброванными λ: `research/reference/smap_band_weighted_ref.py`.
- **Причинностная проверка**: `research/reference/causality_check_band_lambda_ref.py` — 4/4 origin'ов бит-в-бит между полными и обрезанными данными, подтверждено.
- **Работающий прототип интеграции** (образец для переноса паттерна): `prototype/forcaster/ui/app9.py` — Streamlit UI с зонами вероятности, калиброванные λ для SBER подключены через словарь `CALIBRATED_LAMBDAS` (см. файл, раздел после импортов).

### Результат калибровки SBER (эталон для сверки после портирования)

T=20%, 3 прохода координатного спуска (max_passes=3, tol=0.5 — сходимость формально не достигнута, но последнее изменение = 1 шаг сетки, это шум дискретизации, не реальная нестабильность):

```
λ = {"volume": 0.0, "trend": 10.0, "leg_age": 8.0,
     "velocity": 0.0, "acceleration": 0.0, "volatility": 2.0}
pinball_rel = 0.9497  (-5.0% к равномерному baseline)
width_rel   = 0.9814  (полоса УЖЕ на 1.9%, не шире — честный эффект, не размазывание)
```

Пользовательская оценка результата (важно для калибровки ожиданий при будущей работе): *«Чудес, конечно, не показывает — российский рынок то ещё молодое и безумное нечто — но выглядит информативнее значительной части индикаторов»*. Скромный, но честный эффект — не повод искать более сильный результат любой ценой; важнее держать метрики честными (см. память `feedback-uncertainty-field-width-control`, `project-phase7-band-calibrator-objective-fix`).

### Ключевые константы алгоритма (для сверки при портировании)

```
M = 6                    # размерность вложения
MIN_BARS = 5             # мин. баров между пивотами (Depth-аналог)
THETA = 0                # локализация S-map — калибровка не пережила OOS ни на одном из 7 тикеров
Q_LEVELS = (0.1,0.25,0.5,0.75,0.9)
FEATURE_ORDER = ["volume","trend","leg_age","velocity","acceleration","volatility"]
                          # leg_amplitude ИСКЛЮЧЁН — скрининг дал λ*=0 на 2/2 тикерах
K_LEG = 10                # окно перцентильного ранга для pivot-нативных признаков (плечи)
WINDOW_VOL = 20           # окно волатильности (bar-нативный признак)
RANK_WINDOW = 252         # окно перцентильного ранга для bar-нативных признаков
objective = pinball_norm_avg   # НЕ cov_err_avg! (см. ниже)
```

**⚠️ Критично при портировании**: objective калибровки — **pinball_norm_avg** (pinball/T, proper scoring rule), НЕ `cov_err_avg`. Ранняя версия калибратора (research/phase7_fractality/29_band_calibration/29g-29i) использовала `cov_err_avg` и давала **размазывание полосы без реальной точности** (GAZP «-60%», CHMF «-13%» — полностью артефакт метрики: улучшение объяснялось ОДНИМ из 6 покрытий, при этом полоса становилась ШИРЕ, не уже). Подробности — память `project-phase7-band-calibrator-objective-fix`. `cov_err_avg` и явная ширина полосы (`width_avg = band[0.9]-band[0.1]`) допустимы только как диагностика в выводе, никогда как критерий отбора λ.

Признаки: `volume` (объёмная плотность, bar-нативный), `trend` (дистанция от SMA100, bar-нативный), `velocity`/`acceleration` (bar-нативные), `volatility` (bar-нативный, окно 20), `leg_age` (число баров на формирование последнего плеча, **pivot-нативный, T-зависимый** — считается заново на каждый вызов построения пула, не предзагружается). Признаки bar-нативные считаются один раз по OHLC(+volume) всей истории тикера; `leg_age` — зависит от конкретного T зигзага, отдельная архитектура (см. докстринг `band_lambda_calibrator_ref.py`).

## 2. Требования пользователя (дословно, 2026-07-08)

> 1. Выбор значений T «на лету» среди откалиброванных — это легкодоступная настройка, остальные должны быть в контекстном меню
> 2. Калибратор и прогнозатор разные системы. Прогнозатор точно должен работать с жёсткой каузальностью, чтобы пользователь не получал ложную информацию при интерпретации результатов прогнозирования на предыдущих значениях. Калибратору в этом отношении не очень доверяю (хотя тоже должен быть каузален)
> 3. Корректное автопостроение зигзага на графике с выбранным T — как перед прогнозом, так и при просмотре уже сделанных прогнозов (результаты прогнозов пишем в БД как прежде) — отмечаю корректность, так как сейчас точки ставятся в момент обнаружения события, что не очень корректно и путает.
> 4. Точка прогноза для этой модели — именно событие и должна отображаться на графике в его дате.
> 5. Поля готовых прогнозов строятся от события и их можно растягивать по горизонтали — например, тянешь влево первый шаг, поле растягивается, а поле второго шага отодвигается. Растяжение должно также писаться в БД для каждого прогноза — это нужно, так как мы не прогнозируем время и придётся «подтягивать» прогноз под нынешнее время, чтобы чётко увидеть, в какой зоне сейчас цена.
> 6. Предыдущую модель прогнозирования, что уже есть в основном приложении, нужно полностью убрать — она не рабочая.
> 7. Также нужно предусмотреть сразу, что это не единственная модель прогнозирования, скорее всего, какая будет в приложении

**Контекстное меню подробных настроек:**
> 1. Выбор тикеров пула — по умолчанию все, но пусть будет возможность выбрать. Реализуем после создания полноценного менеджера тикеров в самом приложении.

**[Обновление 2026-07-31] Менеджер тикеров готов — выбор пула больше не заглушка.** Источник пула — таблица `instruments` через уже существующий `GET /instruments`. По умолчанию — все добавленные (или только избранные, см. UI-решение в п.5.2a). См. п.5.2a за деталями и за тем, почему это прямо влияет на объём данных, которые нужно держать в БД к моменту калибровки.
> 2. Нужна возможность самостоятельно задавать T, под которые будет производиться калибровка и которые станут доступны в быстром выборе (скорее всего 20%, 15%, 10%). Тут же нужна настройка минимальной продолжительности события для каждого T (по умолчанию 5). Автозапуск калибровки не нужен — пользователь задаёт необходимые уровни детализации событий и их количество и запускает калибратор для них. Результаты калибровки сохраняются в БД в качестве настроек для прогнозатора индивидуально для тикера/масштаба данных (дальше 1d вряд ли буду заглядывать, но пусть будет).
> 3. Настройки m и θ пусть будут доступны, просто имеют значение по умолчанию 6 и 0.

**Отображение зон**: как в app9, но подробнее — произвольные значения процентов, произвольное количество уровней, настройка прозрачности (сейчас используются 25/50/60/75). Постнастройка отображения, не должна требовать пересчёта прогноза. Нужна система пресетов визуальных настроек (для этой и будущих систем), чтобы подтягивались при открытии без ручной перенастройки каждый раз.

## 3. Уточнённые архитектурные решения (Q&A, зафиксировано с пользователем)

| Вопрос | Решение |
|---|---|
| Схема БД под прогнозы | **Одна обобщённая таблица** `forecasts` с дискриминатором `model_type` + расширяемый JSON — не отдельная таблица на модель |

| Растяжение полей прогноза мышью | **Независимые края каждого поля** — у шага 1 и шага 2 свои левый/правый край, тянутся по отдельности |

## 5. Детальный план

### 5.1 Схема БД (`sma/core/db.py`)

**DROP** старую `forecasts`, пересоздать:
```sql
CREATE TABLE forecasts (
    id                 INTEGER PRIMARY KEY,
    instrument_id      INTEGER NOT NULL REFERENCES instruments(id),
    interval           TEXT    NOT NULL,
    model_type         TEXT    NOT NULL,           -- 'band_lambda', далее другие модели
    origin_candle_id   INTEGER NOT NULL REFERENCES candles(id),  -- бар ПОДТВЕРЖДЕНИЯ (каузальная точка)
    created_at         TEXT    NOT NULL,
    params_json        TEXT    NOT NULL,   -- {t_query, lambda:{...}, m, theta, min_bars, forecast_settings_id}
    -- forecast_settings_id — какая именно калибровка (со своим pool_config) использована
    result_json        TEXT    NOT NULL,   -- {origin_price, origin_direction, steps:{1:{band,pool_size},2:{...}}} — ИММУТАБЕЛЕН
    zone_geometry_json TEXT,               -- NULL до первой растяжки; {"step1":{"x0":date,"x1":date},"step2":{...}}
    is_stale           INTEGER NOT NULL DEFAULT 0
);
```
`result_json` — сам прогноз, не редактируется после создания (жёсткая каузальность, п.2 требований — пользователь не должен видеть задним числом изменённый прогноз). `zone_geometry_json` — единственное редактируемое поле, чисто визуальный оверрайд. Зигзаг для отображения (ВСЕ пивоты на графике, не только origin) пересчитывается на лету из `params_json.t_query`/`min_bars` при каждом рендере — отдельно даты экстремумов не хранятся (см. build_zigzag ниже).

Новая таблица `forecast_settings` (результаты калибровки — замена захардкоженного `CALIBRATED_LAMBDAS` из app9.py):
```sql
CREATE TABLE forecast_settings (
    id                    INTEGER PRIMARY KEY,
    instrument_id         INTEGER NOT NULL REFERENCES instruments(id),
    interval              TEXT    NOT NULL,
    model_type            TEXT    NOT NULL,
    t_query               REAL    NOT NULL,
    min_bars              INTEGER NOT NULL DEFAULT 5,
    lambda_json           TEXT    NOT NULL,   -- {"volume":0,"trend":10,...}
    m                     INTEGER NOT NULL DEFAULT 6,
    theta                 REAL    NOT NULL DEFAULT 0,
    pool_config_json      TEXT    NOT NULL,   -- {"categories":["stock"],"n":25,"resolved_instrument_ids":[...]}
    pool_key              TEXT    NOT NULL,   -- детерминированная строка из pool_config, напр. "stock:25" или "metal+stock:25" — часть уникальности
    is_active             INTEGER NOT NULL DEFAULT 1,
    calibration_meta_json TEXT    NOT NULL,   -- {n_passes, pinball_rel, width_rel, converged, calibrated_at}
    UNIQUE(instrument_id, interval, model_type, t_query, pool_key)
);
```
**Зачем `pool_config_json`/`pool_key`/`is_active` — это прямой ответ на «не переделывать
после эксперимента со смесью категорий».** Без этого поля вторая калибровка того же
(тикер, интервал, T) с другим набором категорий **молча перезаписала бы** первую
(старый UNIQUE был только `(instrument_id, interval, model_type, t_query)`) — не
осталось бы возможности держать «пул=металлы» и «пул=металлы+акции» рядом и
сравнить `pinball_rel`/`width_rel` из `calibration_meta_json`. Теперь оба
сосуществуют как разные строки (`pool_key` в UNIQUE), `is_active` — какая из них
используется при построении live-прогноза по умолчанию для этого T (переключается
пользователем вручную после сравнения, не автоматически по метрике — метрика может
быть искажена по тем же причинам, что objective калибратора, см. п.1). Быстрый
T-селектор (5.5) при нескольких `pool_key` на один T показывает лучший/активный,
остальные — в развёрнутом виде контекстного меню.

Новая таблица `display_presets` (визуальные настройки — не про прогноз, для этой и будущих моделей):

```sql
CREATE TABLE display_presets (

```

`tasks`: добавить `kind TEXT NOT NULL DEFAULT 'forecast'` (`'forecast' | 'calibration' | 'pretest'`) — калибратор и претест идут через ту же очередь/WS-прогресс, что и прогноз (TaskManager уже умеет это generic).

`instruments`, `candles`, `series_settings` — без изменений.

### 5.2 Новый движок

`sma/core/forecast/band_lambda.py` (форкастер) + `sma/core/forecast/band_lambda_calibrator.py` (калибратор) — **портирование** (не импорт) из `research/reference/band_lambda_calibrator_ref.py` + `smap_band_weighted_ref.py`. Отличия от референса:

1. Свечи читаются через `sma.core.db.get_candles` (не JSON-файлы из `data/candles/`).
2. **`build_zigzag` расширяется** до 4-tuple: `(log_pivot_prices, extreme_dates, confirm_dates, pivot_directions)` — сейчас в референсе только `confirm_dates`. `extreme_dates[i]` — дата бара реального экстремума (для отрисовки зигзага на графике, п.3/п.4 требований), `confirm_dates[i]` — дата подтверждения (для origin прогноза, каузальная точка). Это правка «баг с некорректной отрисовкой», подтверждённая пользователем.
3. Пул тикеров — берётся из реального менеджера, см. 5.2a ниже (раньше был захардкоженный `UNIVERSE`, `research/reference/smap_band_ref.py:262-268`, теперь референс только для дефолтного состава).

**Дозагрузка пула — отдельные задачи `candle_fetch` в очереди перед основной
задачей, не инлайн-шаг внутри неё** (уточнено 2026-07-31, см.
`docs/plans/task_manager_plan.md`). Очередь строго FIFO с одним
последовательным воркером (см. task-manager план) — этого уже достаточно,
чтобы гарантировать порядок «сначала все догрузки, потом сама калибровка/
прогноз», без какого-либо механизма зависимостей между задачами: воркер
просто дойдёт до задач в порядке постановки. Никакая задача не «ждёт»
другую изнутри себя — это и убирает риск дедлока (единственный воркер не
может одновременно выполнять калибровку и обрабатывать задачи, от которых
она бы зависела, если бы ждала их находясь в очереди сама).

- **`POST /forecast-settings/calibrate`** (5.4) при создании задачи:
  резолвит `pool_config={categories, n}` в список инструментов через
  `pool_selection.py` (см. ниже) **синхронно, в момент запроса** (дёшево —
  несколько запросов к MOEX ISS, не считает λ) → для **каждого** тикера
  пула, без предфильтрации по покрытию, создаёт и ставит в очередь задачу
  `kind='candle_fetch'` → затем создаёт и ставит в очередь саму задачу
  `kind='calibration'`. Пользователь в списке задач видит их все — ровно
  тот «список задач», который и предполагался. **Уточнено 2026-07-31**:
  никакой предварительной проверки «нужно ли этому тикеру докачивание» на
  уровне роута нет и не нужна — так же, как уже устроен реальный
  `POST /candles/fetch` (`sma/api/routes/candles.py`): задача создаётся
  всегда, а решение full/incremental/«почти нечего качать» принимает
  `resolve_fetch_plan` (`sma/core/candle_fetch.py`) уже внутри самой задачи
  в момент выполнения. Для тикера с уже свежими данными такая задача — это
  секундный no-op инкремент, не повод городить отдельную предфильтрацию —
  проще следовать уже проверенному паттерну, чем изобретать новый.
- **`run_calibration_task(instrument, interval, t_list, min_bars_by_t, m, theta, pool_config, progress_cb)`**
  — порт `calibrate_combined_multipass`. К моменту своего запуска пул уже
  должен быть скачан (предыдущие задачи в очереди это гарантируют — штатный
  путь). Если данных всё же не хватает (редкий случай — например,
  возобновление после сбоя ровно между догрузкой и калибровкой, или
  калибровка запущена напрямую в обход роута) — падает с понятной ошибкой
  («не хватает данных по тикеру X, дозагрузите через менеджер тикеров или
  пересоздайте задачу калибровки»), **не скачивает молча сама** — это
  сохраняет принцип «задачи сырые, без скрытой композиции»
  (`task_manager_plan.md`, раздел 3.2): если задаче нужны данные — их
  обеспечивает вызывающая сторона явными `candle_fetch`-задачами, а не сама
  задача исподтишка. По каждому T из списка (задаёт
  пользователь, автозапуска нет) считает λ, **пишет в `forecast_settings`
  онлайн после каждого T** (частичный результат не теряется при сбое —
  принцип проекта для долгих расчётов, см. память
  `feedback-docker-long-compute`). Параллелизм по T через
  `ProcessPoolExecutor` (паттерн из старого `runner.py`, `max(1,
  cpu_count()//4)` воркеров, `OMP_NUM_THREADS=1`/`OPENBLAS_NUM_THREADS=1` —
  см. память `blas-oversubscription-multiprocessing`).
- **`POST /forecasts`** (5.4) — та же схема: пул уже зафиксирован
  (`forecast_settings.pool_config_json.resolved_instrument_ids`, состав НЕ
  переотбирается заново по категориям — иначе он мог бы незаметно
  сместиться между калибровкой и прогнозом, если рынок ликвидности
  изменился) → создаёт `candle_fetch` задачи (**инкрементальные**, не
  полные — данные уже есть с калибровки, только дозагрузить хвост) для
  каждого тикера пула → затем задачу `kind='forecast'`. **Это отдельно от
  вопроса пула-состава: данные пула должны быть свежими на каждый прогноз,
  даже если сам список тикеров не меняется** — иначе поиск соседей в пуле
  работает на данных, замороженных на момент калибровки, и не видит
  структурно похожих событий, случившихся после неё.
- `run_forecast_task(instrument, interval, origin, forecast_settings_id)` —
  обёртка над `pool_values_and_weights`/`forecast_live_band` для сохранения
  в `forecasts`. Принимает id конкретной строки `forecast_settings`,
  читает оттуда `pool_config_json.resolved_instrument_ids`.
  **⚠️ Каузальность — обрезка данных к `origin` применяется И к целевому
  инструменту, И к КАЖДОМУ тикеру пула**, не только к целевому — иначе при
  прогнозе на историческом `origin` (не «сегодня», просмотр уже сделанного
  прогноза) в пул просочатся события ПОСЛЕ `origin`, и модель неявно
  подсмотрит будущее через соседей. Это именно то, что проверяет
  `causality_check_band_lambda_ref.py` в референсе («4/4 origin'ов
  бит-в-бит между полными и обрезанными данными») — но в реализации это
  нужно явно закладывать как требование к `pool_values_and_weights`/
  `build_zigzag`, вызываемым для пула, не полагаться на то, что перенесётся
  само по себе вместе с портированием кода.

**`sma/core/forecast/pool_selection.py` (новый, общий для калибровки И претеста)**:
- `resolve_pool_candidates(categories: list[str], n: int) -> list[dict]` — категория(и)
  → `search_securities(group=...)` (union+дедуп при нескольких категориях) → ранжирование
  по подходящей для engine метрике (`value`/`VALTODAY` для `stock`, `volume` для
  `futures`, полнота покрытия барами для `currency`, см. 5.2a п.2) → топ-N с учётом
  порога ликвидности → `min(n, прошедших порог)`, без принудительного добора мусором.
  Возвращает список инструментов (secid+engine+market+asset_type), **не скачивает
  данные сама** — это теперь ответственность роута (создание `candle_fetch` задач,
  см. выше), не `pool_selection.py`.
- Используется из роута `/forecast-settings/calibrate` (резолв при создании задачи,
  не внутри `run_calibration_task`) и из `run_pretest_task` (5.2b, тот же резолв +
  либо history_from/till, либо build_zigzag-подсчёт событий, без λ-оптимизации) —
  **один источник правды**, не дублируется между задачами.

### 5.2a Пул калибровки: автоотбор по категориям + разделение pool/manual (обновлено 2026-07-31)

Пул больше не хардкод. Механизм отбора обсуждён и зафиксирован отдельно от общей
архитектуры менеджера (детали обсуждения — сессия 2026-07-31, не в этом файле):

**Отбор кандидатов — общий каркас, но метрика ликвидности per-engine (не единая
`value`, см. находки ниже) и допустимый размер пула зависит от категории:**

1. Одна или несколько категорий (`stock`/`fund`/`bond`/`index`/`currency`/`metal`/
   `futures` — `option` исключена, см. отдельный пункт ниже; ключи как в
   `_SEARCH_CATEGORIES` из `sma/api/routes/instruments.py`) — пользователь может
   смешивать (например «фонды+акции+индексы» для акций, или «металлы+акции»,
   если металлов одних не хватает по глубине, см. 5.2b) → кандидаты каждой
   категории через `search_securities(query="", group=<moex_group>)`
   (`sma/data/moex/securities.py`, `group_by`/`group_by_filter`), объединяются
   (дедуп по secid — механически то же самое, что уже делает хардкод-мердж
   `fund`→`stock_etf`+`stock_ppif` в текущем `_SEARCH_CATEGORIES` для обычного
   поиска тикеров, только явно по выбору пользователя. **Для отбора именно
   пула** категория `fund` не должна включать `stock_etf` — см. находку по
   этой категории в п.4 ниже; общий поиск тикеров (не пул) эта находка не
   касается, там ETF по-прежнему полезно показывать, даже если он неликвиден
   — пользователь может добавлять любой конкретный тикер вручную).
2. Обогащение ликвидностью — **метрика зависит от engine кандидата**, проверено
   реальными запросами 2026-07-31 (`from=2026-06-25`, ~месяц):
   - `stock` (акции/облигации/ПИФ/индекс, market меняется, но engine один) —
     поле `value` из candles (₽ оборот) или `VALTODAY` из marketdata борда —
     оба варианта рабочие, значения реальные.
   - `futures` (фьючерсы/опционы) — **`value` всегда `0`, не `None`** (не
     репортится вовсе), нужно ранжировать по `volume` (число контрактов).
     Подтверждено на `SiZ6`/`RIZ6`/`GZZ6`: `value=0`, `volume` реальный
     (77058/1683/5918 контрактов).
   - `currency` (валюта/металлы) — **и `value`, и `volume` всегда `None`**
     (FX-котировки не репортят лотовый оборот в принципе). Единственный
     рабочий прокси ликвидности — **полнота покрытия барами** за окно (сколько
     торговых дней из ожидаемых реально есть свечи), не размер оборота.
3. Топ-N по подходящей метрике, **N=25 по умолчанию, но не гарантирован** —
   алгоритм возвращает `min(N, число_кандидатов_прошедших_порог_ликвидности)`,
   не пытается силой набрать N мусорными хвостовыми инструментами. Порог
   ликвидности (например «бары есть ≥15 из последних ~20 торговых дней») —
   параметр, дефолт по данным ниже.
4. **Реальная глубина по категориям (снимок 2026-07-31, может меняться со
   временем — переизмерить перед финальной реализацией, не считать константой)**:

   | Категория | Проверено | Прошли порог ликвидности | Комментарий |
   |---|---|---|---|
   | `stock` (акции) | TQBR, 502 | ≫25 | без проблем, топ по `value` работает как задумано |
   | `bond` (облигации) | 400 из 2100+ | 101 | с запасом хватает на 25 |
   | `index` (индексы) | 400 из 915 | 359 формально, но... | **группа замусорена техническими суб-индексами** (облигационные, target-date — `MXTDFI2036` и т.п.), а не тем, что людям нужно (IMOEX/RTSI/MOEXBC). Ранжирование по обороту тут вводит в заблуждение — **нужен курируемый allowlist** (IMOEX, RTSI, MOEXBC + десяток отраслевых MOEX-индексов), не автоотбор по группе. |
   | `fund` (фонды) | ETF 54, ППИФ ~1000+ | ETF: **0**, ППИФ: не проверено, но `LQDT`/`TMOS` живые (see выше по сессии) | **`stock_etf` практически мёртв** — топ по «обороту» оказался замороженными иностранными ETF (`BOTZ-RM`,`EEM-RM`,`ICLN-RM` — BlackRock/iShares, заморожены санкциями 2022, реально не торгуются). Категория «фонды» должна означать **только `stock_ppif`**, не merge с `stock_etf`, как планировалось раньше. |
   | `currency` (валюта) | 217 | 15 | не набрать 25, это потолок рынка |
   | `metal` (металлы) | 61 | 6 | не набрать 25 и близко — по факту это 4-5 металлов×несколько тенoров, из которых торгуется в основном TOM-вариант |
   | `futures` (фьючерсы) | 400 из 2100+ | 325 | достаточно, если ранжировать по `volume` (см. п.2) |

5. **`option` (опционы) исключена из категорий пула, не только из-за низкой
   ликвидности (0/400 прошли порог), а структурно**: опционы оцениваются по
   страйку/времени до экспирации/волатильности (Greeks), их ценовой ряд не
   sравним по природе с зигзагом на споте — как источник пула для band_lambda
   (который строится на зигзаге ценового ряда) вряд ли осмыслен в принципе,
   не только сейчас с этими данными. Если понадобится в будущем — отдельное
   исследование, не автоматическое включение в общий механизм.
6. **IMOEX/индексный состав НЕ используется** как механизм отбора акций —
   пересечение с топ-20 по обороту всего 70% (14/20), часть расхождений —
   вообще не акции (фонды денежного рынка `LQDT`/`SBMM`/`AKMM` торгуются на
   том же борде TQBR и не должны были попасть в сравнение — но это не меняет
   вывод: раз `group`-фильтрация уже отсекает такое на шаге 1, а обычные акции
   типа `SMLT`/`SGZH`/`MTLR` из топ-20 по обороту, но не входящие в IMOEX —
   реальный, не мусорный кейс несовпадения). Один универсальный механизм проще.
7. **N=25 по умолчанию — не круглое число, эмпирически обосновано** (для акций,
   где глубина позволяет): `research_large_scale_pooled_17` (эксп.17, Stage 1b)
   показал, что расширение универсума блю-чипов MOEX с 25 до 45 тикеров
   практически не изменило результат (rMAE та же точка ±0.01 п.п.), а
   корреляционный отбор соседей стал даже слабее (второй эшелон добавил шума).
   Референсный `smap_band_ref.py:262-268` до сих пор хардкодит `UNIVERSE` из
   44 тикеров — **при портировании дефолт нужно взять 25, не копировать 44 как
   есть**. Оговорка: эксп.17 — смежный (кросс-тикерный T_big-пул), не прогон
   именно band_lambda с pinball/width метрикой; уверенность высокая (то же
   семейство метода, тот же пул MOEX блю-чипов), но не 1:1 доказательство. Для
   категорий с потолком ниже 25 (валюта, металлы) N естественно урезается
   алгоритмом до фактической глубины (п.3) — это ожидаемо, не баг.

**Выбор категории пула независим от категории прогнозируемого инструмента**
(явно проверено пользователем на кейсе «фьючерс на акцию — пул из акций
базового актива») — в механизме выше категория пула ничем не завязана на
инструмент, для которого строится прогноз, никакой доп. работы не требуется.

**Разделение «слежу» vs «пул» — новая колонка в `instruments` (не в новых
band_lambda-таблицах — это общая правка существующей схемы менеджера тикеров):**
```sql
ALTER TABLE instruments ADD COLUMN added_via TEXT NOT NULL DEFAULT 'manual';
-- 'manual' | 'pool'
```
Тикеры, добавленные автоотбором пула (шаги 1-3 выше) и которых ещё не было в
`instruments`, получают `added_via='pool'`. `GET /instruments` по умолчанию
отдаёт только `added_via='manual'` (параметр `include_pool=true` — показать все,
для отладки/ручного управления). Если пользователь позже сам находит такой
тикер через обычный поиск/добавление — `upsert_instrument` переключает на
`'manual'` (это уже штатный upsert-путь, доп. логики не требует).

**Автозагрузка данных пула — не отдельный вопрос, часть того же шага.**
`run_calibration_task` при формировании пула: для каждого отобранного secid без
свечей на нужном `interval` — тот же путь, что и `POST /candles/fetch`
(`sma/api/routes/candles.py`, уже сам решает full/incremental), вызванный
программно (`download_candles`+`upsert_candles` напрямую, не HTTP). Это и есть
причина, по которой понадобилось разделение pool/manual выше — без него «Мои
тикеры» после первой калибровки заполнился бы 25+ строками, не относящимися к
тому, что пользователь реально отслеживает. Пагинация (20/страница) и общий с
быстрым переключателем текстовый фильтр в «Мои тикеры» (`sma/ui/tickers.js`,
`MANAGER_PAGE_SIZE=20`) уже реализованы независимо от этого пункта и остаются
полезны для `include_pool=true` вида и для случая, когда сам пользователь
вручную ведёт много тикеров.

**Снят прежний открытый вопрос про bulk-add UI**: он был актуален только при
идее ручного мультиселекта тикеров пула. При автоотборе по категории+обороту
пользователю вообще не нужно вручную выбирать/добавлять тикеры пула — весь
конвейер (категория → кандидаты → ранжирование → топ-N → автозагрузка свечей)
происходит внутри `run_calibration_task` без похода в «Добавить тикер». UI
выбора пула (контекстное меню калибровки, п.5.5) — это выбор **категории и N**,
не выбор конкретных тикеров.

### 5.2b Претест пула перед калибровкой (новое, 2026-07-31)

Обосновано находками 5.2a: глубина ликвидного пула сильно варьируется по
категориям (6 для металлов, 15 для валюты, 25+ для акций/облигаций/фьючерсов).
Нужно видеть потенциальное качество пула **до** запуска дорогой многопроходной
калибровки, а не узнавать постфактум, что пул оказался тонким.

**Ключевой нюанс**: «качество» пула для band_lambda — не число тикеров, а
число **зигзаг-событий** (T_frac пивотов), которые из них извлекаются — модель
строится на пуле событий, не тикеров. Тикер с долгой волатильной историей даёт
кратно больше событий, чем короткий/спокойный ряд. Претест обязан считать
именно это, а не просто «сколько тикеров прошло отбор».

**Смешение категорий (например «металлы + акции», обсуждалось пользователем
как вероятная необходимость для металлов из-за их малой глубины) — открытый
эмпирический вопрос, не решённое заранее допущение.** Из `research_large_scale_pooled_17`
известно, что акции MOEX уже сильно скоррелированы между собой (общий
бета-фактор) — это ограничивало пользу расширения ЧИСТО акционерного пула.
Смесь металл+акции — качественно другой, неисследованный случай: непонятно,
добавляет ли она реальный сигнал соседям (больше структурно похожих событий)
или размывает его шумом другой природы динамики (золото/металлы движутся
макро/risk-off потоками, акции — своей отраслевой спецификой). Претест
(число событий) не отвечает на этот вопрос напрямую — отвечает только реальное
качество прогноза (pinball/width, как в 5.2a) — но не дать пулу быть тонким
по числу событий ещё до этой проверки уже полезно само по себе.

**Двухуровневая реализация (баланс скорость / точность):**
- **Уровень 1 — мгновенный, без скачивания свечей.** После отбора кандидатов
  (5.2a: категория → ликвидность → топ-N) — по каждому кандидату запрос
  `/securities/{secid}.json` (`boards[].history_from/history_till`, тот же
  вызов, что уже использовался в разведке 2026-07-31 для верификации
  engine/market) → грубая оценка суммарного охвата (лет истории на пул).
  N запросов по числу кандидатов (обычно ≤25-50) — дёшево, доли секунды.
- **Уровень 2 — точный, требует скачивания.** Тот же путь, что и реальная
  автозагрузка данных пула (`download_candles`+`upsert_candles`,
  `added_via='pool'`) + прогон `build_zigzag` **без** многопроходной
  λ-оптимизации (это самая дорогая часть калибровки, претест её намеренно
  пропускает) → реальное число событий на кандидата/на пул при заданном T.
  Скачанные данные не выбрасываются — если пользователь после претеста
  запускает полноценную калибровку на том же пуле, повторной загрузки не
  происходит (тот же incremental-путь `/candles/fetch` уже это гарантирует).
- Оба уровня — через тот же `TaskManager` (`kind='pretest'`), прогресс по WS
  как у калибровки. Результат — сводка (число тикеров, событий/лет истории,
  разбивка по категориям при смешении), не запись в `forecast_settings`.

**API**: `POST /forecast-settings/pretest` —
`{categories: [...], n, t_query, min_bars, level: 1|2}` → задача в очередь,
WS-прогресс, результат — диагностическая сводка.

**UI** (контекстное меню калибровки, п.5.5): кнопка «Претест» рядом с
«Калибровать» — показывает сводку до принятия решения о полноценном запуске.

**⚠️ Уточнение 2026-07-31 (после сверки плана с реализацией)**: диспетчер в
`_run_task()` — **не** словарь-registry `{model_type: engine_fn}`, как было
написано здесь изначально. Реально это плоский `if/elif` по `task["kind"]`:
```python
kind = task["kind"]
if kind == "forecast":
    await self._run_forecast(task_id, task)
elif kind == "candle_fetch":
    await self._run_candle_fetch(task_id, task)
else:
    raise ValueError(f"Unknown task kind: {kind!r}")
```
Подключение band_lambda — это правка того же `if/elif`, не заполнение
существующего словаря:
- `elif kind == "calibration": await self._run_calibration(task_id, task)`
  и `elif kind == "pretest": await self._run_pretest(task_id, task)` —
  новые ветки, новые приватные методы (по образцу `_run_candle_fetch`).
- `elif kind == "forecast":` — **существующая** ветка, `_run_forecast`
  сейчас вызывает старый `sma.core.pipeline.run_forecast` (импорт в шапке
  файла, строка 51) — заменить тело на вызов `band_lambda.run_forecast_task`
  и убрать этот импорт **в том же шаге**, что и удаление `pipeline.py`
  (см. правку в разведке 4.2 выше — иначе `ImportError` при старте).
- Диспетч по `model_type` внутри одного `kind` (то, что описывал словарь
  `FORECAST_ENGINES` и т.п.) — **не нужен сейчас**, при одной модели
  (`band_lambda`) на `kind`. Понадобится только если появится вторая
  модель, делящая тот же `kind` (`forecast`/`calibration`/`pretest`) — тогда
  внутри соответствующей ветки `if/elif` добавляется проверка
  `task["params"]["model_type"]`. Не строить эту прослойку заранее ради
  одной модели — YAGNI, к тому же реальный TaskManager её не содержит,
  вводить её именно этим планом означало бы расхождение с уже проверенным
  кодом.

`_run_calibration`/`_run_pretest` пишутся сразу с поддержкой `should_cancel`
(тот же паттерн, что `progress_cb` в реальном `_run_forecast` — замыкание,
прокидываемое в `loop.run_in_executor`, см. task_manager_plan.md 3.2) — не
отдельной правкой потом.
