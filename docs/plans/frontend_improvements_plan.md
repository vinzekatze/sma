## 0. Поправка к вводным

Модуль, который в памяти проекта называется `analyzers.js`, был переименован в

- `S.activeMainTool` / `S.activeOscillatorTool` — два **независимых** слота
  эксклюзивности (`state.js:12-13`) для основного графика и осциллятора —
  требование «выбираются независимо» (раздел «Осциллятор», п.1) уже выполнено;
- три визуальные секции тулбара (Курсор/Анализ/Прогноз) через `renderToolbarButtons()`
  (`tools.js:160-189`, `index.html:260-314`);
- один прецедент eye-иконки для pin/show уже есть: `#object-select-pin-btn`
  (`index.html:337-338`, класс `.hist-eye-btn`, `toggleSelectedForecastPin()`) —
  на неё и нужно равнять остальные инструменты, а не изобретать заново.

Это меняет объём работы в лучшую сторону: пункты «политика видимости» и
«независимость осциллятора» — это **унификация существующего паттерна**, а не
новая архитектура.

Второе уточнение: персистентность настроек анализатора **уже существует** как
серверный механизм — таблица `analysis_settings` (`instrument_id, interval,
analyzer_type, params_json`), роуты `GET/POST /series/analysis-settings`
(`sma/api/routes/series.py:66-90`), и рабочий паттерн `loadXDefaults()` /
`saveXSettings()` с debounce 500мс fire-and-forget (использован спектрограммой,
недавно скопирован для trend_variance — см.
`docs/plans/trend_variance_analyzer_migration_plan.md`). Это **не то же самое**,
что просимое браузерное хранилище: тот механизм — per-тикер параметры анализа
на сервере; локальное хранилище нужно для **клиентских UI-состояний**, которые
не должны ни зависеть от тикера, ни гонять сеть. Разграничение — в §1.

Проект **не находится под git** (подтверждено окружением). Учитывая объём этого
рефакторинга (≈10 файлов, 12 пунктов), см. открытый вопрос в §7.

## 1. Оптимизация

### 1.1 Локальное хранилище визуальных настроек и состояний

**Разграничение (важно не смешать два уже существующих/нужных механизма):**

| Что | Где хранить | Почему |
|---|---|---|
| Параметры анализатора конкретного тикера (окно тренд-линейки, полосы, spectrogram fmin/fmax) | **как сейчас** — `analysis_settings` в БД, debounce 500мс | уже работает, per-тикер, синхронизируется между вкладками/устройствами |
| UI-состояние сессии, не привязанное к тикеру: активный инструмент, `pinnedForecastIds`, `objectsHidden`, лог-масштаб, `priceLevels`, **цвета инструментов** (новые — MA/zigzag_tool/price_level серии, см. §2.2-2.3; цвет+закрепление прогноз-зигзага по T, см. §2.4) | **новое** — `localStorage`, единый модуль `sma/ui/local_prefs.js` | не требует сети, восстанавливает вид графика мгновенно при открытии страницы, не должно засорять БД |

Цвета инструментов — глобальные (не per-тикер), поэтому логично живут в
localStorage, а не в `analysis_settings`.

**Механизм**: один модуль `local_prefs.js` с API вида
`getPref(key, default)` / `setPref(key, value)` (debounce ~300-500мс на запись,
чтение — синхронно при старте `app.js`). Не сохранять на каждое изменение слайдера
в реальном времени — только после паузы взаимодействия (тот же принцип debounce,
что уже применяется к `analysis_settings`).

**Защита от разрастания**:
- Явный whitelist полей (не сериализовать весь `S` целиком) — состав списка
  нужно зафиксировать заранее (см. §7, вопрос 3).
- `pinnedForecastIds` — держать разумный потолок (например, последние N), не
  накапливать бесконечно.
- Версионировать формат (`{v: 1, ...}`) — чтобы при изменении схемы не падать на
  устаревших данных, а тихо сбрасывать к дефолту.
- Обернуть чтение/запись в try/catch — `localStorage` может быть недоступен
  (приватный режим, квота) — деградация к дефолтам, не к ошибке.

### 1.2 Подтормаживание графика при взаимодействии

Собранные факты:

- `chart.js` рендерит через Plotly; при каждом обновлении (клик, WS-событие,
  смена настроек инструмента) traces/shapes для свечей + всех активных/закреплённых
  инструментов + прогнозов + осциллятора собираются заново и передаются в Plotly.
- Маркеры прогнозов рисуются **всегда** (`buildForecastMarkerTraces()`,
  `chart.js:599-658`), независимо от того, активен ли инструмент прогноза — это и
  лишняя отрисовка, и путаница по UX (см. §2.7).
- Жёлтые origin-линии плодятся без переиспользования на каждый закреплённый
  прогноз (`buildVisibleOverlays()`, `chart.js:664-681`) — рост числа shapes
  прямо пропорционален числу закреплённых прогнозов.
- Готовой агрегации/ресемплинга свечей при большом количестве баров нет — все
  бары интервала передаются в Plotly as-is.

**Причины тормозов — вероятно комбинация**:
1. Количество shapes/traces растёт неограниченно с числом активных инструментов
   и закреплённых объектов (фикс в §2.1 частично снимает).
2. Полный пересбор данных при каждом чиха-событии (нужно проверить: `Plotly.react`
   используется или `Plotly.newPlot` — если newPlot, это дороже, т.к. пересоздаёт
   DOM/WebGL-контекст, а не диффит).
3. Количество точек на свечном графике (потенциально тысячи баров на 1d/10m
   интервалах) без LOD.

**Предлагаемый подход к LOD (гибкая автоматика, не ползунок)**:
Агрегация свечей по **плотности пикселей**, а не по фиксированному порогу баров:
на каждое изменение видимого диапазона (`relayout`/zoom) вычислять
`видимых_баров / ширина_графика_в_пикселях`; если один бар занимает меньше
разумного минимума (например ~2-3px), агрегировать N соседних баров в один
OHLC-бар (open первого, close последнего, high/low — max/min группы) прямо на
клиенте, без похода на бэкенд. При достаточном приближении (плотность падает
ниже порога) возвращаться к исходным барам. Это то самое «пересборка свечей в
больший масштаб», которую пользователь предложил, но управляемая автоматически
по факту зума/панорамирования, а не статичным параметром.

Открытый вопрос по реализации — точный алгоритм биннинга и пороги — см. §7.

## 2. Доработки инструментов (основной график)

### 2.1 Жёлтые пунктирные линии при множественном выборе (решение 2026-08-19)

Сейчас: `buildVisibleOverlays()` (`chart.js:664-681`) для каждого id из
`pinnedForecastIds ∪ {selectedForecastId}` добавляет `originLineShape` +
`originPriceLineShape` (`#ffd600`, dash dot) — без дедупликации, N закреплённых
= N полноширинных линий.

**Решение**: полноширинные горизонтальные линии вообще убираются у
закреплённых, но не выбранных прогнозов — путаются с другими инструментами на
графике. Полноширинная origin-линия остаётся **только у активно выбранного**
(`selectedForecastId`) — она же служит визуальной точкой отсчёта. У прочих
закреплённых — только маркер, без линии, но **ярче**, чем у незакреплённых/
невыбранных (эта часть уже частично реализована: `opacity: selected||pinned
?0.95:0.55`, `chart.js:636` — нужно лишь перепроверить, что после удаления
линий разница в яркости осталась достаточно заметной без неё).

**Смежное требование — точность выбора при клике (magnet-логика)**:
пользователь отметил, что сейчас выбор прогноза кликом уже не требует
попадания строго в маркер (есть допуск/толеранс) — это поведение нужно
**сохранить и формализовать**, раз полноширинная линия перестаёт быть
визуальным якорем для выбора:
- В режиме «выбор объектов» и для прогноза simplex — точка отсчёта
  (горизонтальная линия) может «магнититься» к ближайшему маркеру при клике
  рядом с ним.
- В режиме прогнозирования полос (band_lambda) — магнититься к событиям
  зигзага выбранного T, а не к произвольной ближайшей точке.
- **Приоритет точного клика**: если на соседних барах расположены несколько
  прогнозов, точное попадание в конкретный маркер должно выигрывать у магнита
  к любому другому более близкому по каким-то другим критериям объекту —
  иначе легко выбрать не тот прогноз при плотной группе.

Точный текущий механизм клика/допуска нужно сверить с кодом при реализации
(`initChartEvents`/обработчик `plotly_click` в `chart.js`, см. граф зависимостей
в CLAUDE.md) — в разведке этого плана детали hit-testing не проверялись,
факт «допуск уже есть» — со слов пользователя, не подтверждён file:line.

### 2.4 Прогноз-зигзаг: расширенные настройки отображения (решение 2026-08-19: без слияния с zigzag_tool)

Изначально рассматривалось слияние с `zigzag_tool.js` (калиброванные T-зигзаги
как неизменяемый набор серий внутри инструмента-зигзага). **Отклонено**: это
создавало бы двустороннюю связь между двумя ранее независимыми модулями —
`zigzag_tool.js` пришлось бы читать состояние выбранного T из `forecast.js`
(для «жирного» выделения), а `forecast.js` — знать про палитру `zigzag_tool`
(для цвета маркеров). Разные жизненные циклы данных (пользовательские серии —
мутируемые, калиброванные — иммутабельные, привязаны к конкретной
`forecast_settings` записи с `pool_key`/`is_active`) плюс разная инвалидация
при смене тикера. Решение пользователя: **оставить зигзаг прогноза внутри
`forecast.js`/`chart.js` как отдельную фичу**, но расширить её настройки
отображения.

Текущее состояние остаётся as-is по механике данных:
- `S.zigzagPivots` (`state.js:119`), грузится `loadZigzag()`
  (`forecast.js:191-217`), рисуется `buildZigzagTrace()` (`chart.js:353-364`,
  сейчас фиксированный цвет `#d29922`).
- Чекбокс «Зигзаг на графике» (`#bl-show-zigzag`, `index.html:540`,
  `toggleZigzagDisplay()`) сейчас не переключает видимость, а **перезапрашивает**
  данные (`forecast.js:219-221`) — это отдельно чинится в §2.5 (реактивное
  применение вместо кнопки).

**Расширение настроек отображения** (новое, в панели прогноза):
- **Выбор цвета** линии зигзага — per T (или per активная запись
  `forecast_settings`, см. вопрос ниже), дефолт — текущий `#d29922`.
- **Перманентность на графике** — переключатель уровня «закрепить», по смыслу
  аналогичный `pinnedForecastIds` (§2.1/§2.6): закреплённый зигзаг остаётся
  видимым на графике, даже когда инструмент прогноза не активен или выбран
  другой T. Без закрепления — виден только зигзаг текущего выбранного T, пока
  активен инструмент прогноза (общая политика видимости §2.6).
- Хранение: цвет + флаг закрепления — **UI/session-состояние**, значит через
  `local_prefs.js` (§1.1), не через `analysis_settings`/`display_presets` в БД
  (это не геометрия зон, а чисто визуальная настройка отображения).
- Цвет маркеров прогноза на графике = цвет зигзага **этого же T** (та же
  логическая связь, что и в исходном требовании, только реализуется внутри
  одного модуля `forecast.js`/`chart.js`, без выхода в `zigzag_tool`).

Открытый нюанс для реализации: ключ, по которому хранится цвет/закрепление —
по T (`t_query`) или по конкретной активной калибровке (T + pool_key)? Если
у одного T несколько pool_key может быть активным поочерёдно, логичнее по T
(пользователь настраивает «как выглядит зигзаг для этого горизонта», а не
привязывается к конкретной калибровке) — предлагается взять это по умолчанию,
без отдельного вопроса, скорректируем при реализации если не подойдёт.

## 3. Доработки инструментов (осциллятор)

Факт: `S.activeMainTool` / `S.activeOscillatorTool` уже независимы
(`state.js:12-13`), взаимного влияния между основным графиком и осциллятором
нет (`tools.js:204-213` ветвится по `surfaceOf()`). Требование «выбираются
независимо» уже выполнено кодом — доработка нужна только в пп. 1-3 ниже.

### 3.1 Заменить «показать на графике» на «выбранный инструмент = отображается»

Сейчас каждый осцилляторный инструмент (спектрограмма, variance_osc) владеет
собственным чекбоксом `showCheckboxId`, который через `claimSubpanel()` /
`releaseSubpanel()` (`tools.js:122-134`) обеспечивает единоличное владение
слотом `S.subpanel`. По факту это уже почти нужная модель (эксклюзивность уже
есть), но семантически это «включить осциллятор», а не «выбрать инструмент,
чтобы он отобразился» — нужно унифицировать с логикой выбора инструмента на
основном графике (клик по иконке в тулбаре = выбор = отображение, без
отдельного чекбокса). В отличие от основного графика, здесь **нет** pin-логики
— осцилляторы плохо накладываются друг на друга, поэтому один активный слот
без закрепления, как и просил пользователь.

### 3.2 Иконка «отключить осциллятор»

Добавить в тулбар осциллятора инструмент-заглушку (условный «нет инструмента»),
выбор которого очищает `S.subpanel`/`S.activeOscillatorTool` и скрывает
подпанель целиком.

### 3.3 Центрирование графиков осциллятора — per-tool политика

Сейчас все осцилляторы делят один `yaxis2` (`buildLayout()`, `chart.js:194-222`)
с одинаковым поведением `fixedrange: false` — ни авторейнджа, ни
zero-centering нет ни у кого; единственная кастомизация — `type:'log'` для
спектрограммы. Бэкенд спектрограммы уже отдаёт `freqs`, обрезанные по
`fmin/fmax` (`spectrogram.py:96,100`) — то есть содержательный диапазон
частот уже фиксирован на сервере, фронту остаётся только не позволять зум/пан
поверх этого.

План — развести `yaxis2`-конфигурацию по типу активного осцилляторного
инструмента (не единая конфигурация на всех):
- **Спектрограмма**: `fixedrange: true`, `autorange` выключен, диапазон = ровно
  то, что вернул бэкенд (zoom/pan/scroll по оси Y отключены полностью — двигать
  action незачем).
- **Осциллятор дисперсии, режим slope (тренд)**: 0-уровень зафиксирован строго
  посередине панели (симметричный диапазон `[-max(|slope|), +max(|slope|)]`
  вокруг 0), зум по Y доступен (амплитуды сильно отличаются между тикерами).
- **Осциллятор дисперсии, режим var (дисперсия)**: нижняя граница зафиксирована
  строго на 0 (дисперсия ≥0 всегда), верхняя — авто по данным, зум не нужен
  (аналогично volume-паттерну, если/когда появится).

Реализация: `buildLayout()` должен читать активный инструмент осциллятора и
выбирать одну из трёх (или больше, при добавлении новых осцилляторов) заранее
описанных `yaxis2`-политик вместо единой захардкоженной конфигурации.
