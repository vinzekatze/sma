# План: менеджер задач (TaskManager — персистентность, отмена, восстановление после сбоя)

Статус: **реализовано 2026-07-31**, тем же вечером, что и согласовано.
Проверено живым сервером — последовательная очередь, отмена, `resume-all`,
честная симуляция `kill -9` с восстановлением, регрессия `kind='forecast'`
не обнаружена. Документ остаётся самодостаточным описанием архитектуры.
Непосредственный повод: массовая калибровка band_lambda для нескольких
инструментов «запустил и ушёл», но это общая инфраструктура, нужна и дальше
для любых будущих долгих фоновых задач, не только band_lambda —
band_lambda (`docs/plans/band_forecast_migration_plan.md`) при портировании
только регистрирует новые `kind` в уже готовом `_run_task`, доп. работы
над самим TaskManager не требуется.

## 1. Контекст и обоснование

Пользователь описал сценарий: запускает калибровку сразу для нескольких
инструментов, расставляет точки прогноза, уходит заниматься другими делами.
Если приложение (сервер) резко остановится — задачи не должны потеряться;
по возвращении нажимается кнопка вида «Запустить всё», и обработка
возобновляется. Нужен UI-менеджер задач (список активных задач, статус,
пауза/запуск/отмена), размещённый **в левой панели сразу после «Менеджер
тикеров»** (тот же аккордеон-контейнер, уже спроектированный расширяемым —
см. sma/ui/tickers.js, реализовано в сессии 2026-07-30/31).

Согласовано с пользователем (2026-07-31):
- **Выполнение последовательное, не параллельное** — одна задача в моменте,
  безо всяких исключений («пускай последовательно всё идёт, чтобы не
  заморачиваться» — дословно). Так безопаснее по CPU (калибровка уже сама
  использует `ProcessPoolExecutor` внутри себя — параллельные задачи означали
  бы вложенный оверсабскрипшн, см. память `blas-oversubscription-multiprocessing`),
  и медленнее по общему времени не критично для сценария «запустил и ушёл».
- **Только отмена, без отдельной «паузы»** — отмена останавливает выполнение
  после текущего чек-пойнта (например, текущего T в калибровке; частичный
  результат уже в БД, см. `forecast_settings` в band-plan), не начиная
  следующий шаг. Возобновление позже — тот же task_id запускается заново,
  задача сама пропускает уже сделанное (по факту в БД: уже посчитанные T,
  уже скачанные свечи), не разбираться отдельным состоянием «пауза».
- **Дозагрузка/обновление свечей тоже идёт через очередь, не отдельным
  синхронным путём** (уточнение пользователя, добавлено в этот же день) —
  `POST /candles/fetch` (уже реализован и используется в менеджере тикеров,
  `sma/ui/tickers.js`, сессия 2026-07-30/31) сейчас **блокирующий** — ждёт
  скачивания внутри HTTP-запроса. Меняется на ту же схему, что уже есть у `/forecasts`
  (202 + `task_id`, дальше WS/список задач). Это не гипотетическое
  расширение на будущее — существующий код (`sma/api/routes/candles.py`,
  `sma/ui/tickers.js`) меняется прямо в рамках этого плана, см. 3.5.
  **Осознанный побочный эффект**, который стоит держать в уме: раз очередь
  строго последовательная, то пока выполняется что-то долгое (например,
  многочасовая калибровка) — обычное «Обновить» на одном тикере из
  «Мои тикеры» тоже встанет в очередь и будет ждать, а не выполнится сразу,
  как сейчас. Это прямое следствие явного выбора пользователя (простота
  важнее скорости отклика в этом случае), не недосмотр.

## 2. Разведка текущего кода (сделана 2026-07-31)

`sma/api/task_manager.py` (146 строк, читан целиком):

- **Очередь — только in-memory** (`asyncio.Queue[int]`), не персистентна.
  Единственный `_worker_loop()` — один воркер, строго последовательно (уже
  соответствует решению «без параллелизма» — не нужно менять модель
  выполнения, только сделать её переживающей рестарт).
- **`list_pending_tasks()` в `sma/core/db.py:573` существует, но НИГДЕ не
  вызывается** — явный недоделанный кусок, судя по всему задуманный именно
  под восстановление, но так и не подключенный.
- **`.submit()` вызывается только один раз** — из `POST /forecasts`
  (`sma/api/routes/forecasts.py:50`), в момент создания свежей задачи. Нет
  ни одного пути повторной постановки в очередь существующей задачи.
- **Отмены/паузы нет вообще** — `_worker_loop` либо доводит задачу до конца,
  либо ловит исключение → `status='error'`. Нет проверки флага отмены нигде.
- `sma/api/app.py` (`lifespan()`) поднимает `TaskManager` и просто стартует
  воркер — не восстанавливает `pending`/`running` задачи из БД при старте.
- `sma/api/routes/tasks.py` — только `GET /tasks/{id}` и WS
  `/tasks/{id}/ws`. **Нет `GET /tasks` (список всех)** — для UI-менеджера
  обязателен, сейчас физически нечем получить список.
- Схема `tasks` (`sma/core/db.py`, `_SCHEMA`): `id, created_at, status,
  instrument_id, interval, origin_ts, params_json, forecast_id, error,
  progress_done, progress_total`. Нет `kind` (уже запланирован в
  band-forecast плане, 5.1), нет человекочитаемого `label`, нет флага
  отмены, нет `updated_at`.

**Вывод разведки**: инфраструктура персистентности задач (таблица `tasks`)
уже есть и достаточна как хранилище, но ни разу не была доведена до конца —
восстановление после рестарта не реализовано, список/отмена отсутствуют.
Это не «добавить фичу с нуля», а «доделать то, что явно было задумано, но
брошено на середине» (`list_pending_tasks` — прямая улика).

## 3. Детальный план

### 3.1 Схема БД (`sma/core/db.py`)

Расширить `tasks` (миграция в `_MIGRATIONS`, тот же паттерн `ALTER TABLE`,
что уже используется для остальных таблиц):

```sql
ALTER TABLE tasks ADD COLUMN kind             TEXT NOT NULL DEFAULT 'forecast';
-- 'forecast' | 'calibration' | 'pretest' | ... (расширяемо, см. band-plan 5.3)
ALTER TABLE tasks ADD COLUMN label            TEXT NOT NULL DEFAULT '';
-- человекочитаемое описание для UI, например
-- "Калибровка SBER 1d — T:20%,15%,10%, пул: акции×25"
-- составляется роутом при создании задачи (каждый kind знает свой формат),
-- не пытаемся генерически рендерить params_json на фронте
ALTER TABLE tasks ADD COLUMN cancel_requested INTEGER NOT NULL DEFAULT 0;
ALTER TABLE tasks ADD COLUMN updated_at       TEXT NOT NULL DEFAULT '';
-- обновляется при каждом update_task(), для сортировки «последние активные» отдельно от created_at
```

Статусы `tasks.status` расширяются: `'pending' | 'running' | 'done' |
'error' | 'cancelled' | 'interrupted'`. `'interrupted'` — специально для
восстановления: задача была `'running'`, когда процесс приложения
оборвался (см. 3.2). Отличается от `'cancelled'` — это не намерение
пользователя, а факт «никто её сейчас не выполняет», UI показывает иначе
(нейтральный статус, не «ты отменил», а «прервалась не по твоей воле»).

### 3.2 `TaskManager` (`sma/api/task_manager.py`)

**Восстановление при старте** — новый метод, вызывается в конце `start()`
до входа в воркер-луп:
```python
async def _reconcile_after_restart(self) -> None:
    """Задачи, застрявшие в 'running' с прошлого запуска процесса —
    никто их сейчас не выполняет (очередь была только в памяти) —
    пометить 'interrupted'. НЕ ставить в очередь автоматически —
    пользователь возобновляет явно (кнопка «Запустить всё»/по одной)."""
    async with open_db(self._db_path) as db:
        stale = await list_tasks(db, status="running")
        for t in stale:
            await update_task(db, t["id"], status="interrupted")
```
`'pending'` задачи (были в очереди на момент сбоя, до выполнения не
дошли — частичного результата ещё нет, полностью безопасно перезапустить)
**тоже не ресабмитятся автоматически** — по прямому требованию пользователя
(явная кнопка, не тихий автозапуск при каждом старте процесса, включая
случаи разработки/частых перезапусков).

**Отмена** — кооперативная, не настоящий kill:
```python
def request_cancel(self, task_id: int) -> None:
    self._cancelled.add(task_id)  # in-memory set, дёшево проверять
    # + запись cancel_requested=1 в БД (персистентность + видно в UI сразу,
    #   не дожидаясь следующего чек-пойнта задачи)

def is_cancel_requested(self, task_id: int) -> bool:
    return task_id in self._cancelled
```
Функции движка (в первую очередь `run_calibration_task` из band-plan —
там уже есть естественные чек-пойнты по T) получают доп. колбэк
`should_cancel: Callable[[], bool]` (тем же путём, что уже сейчас
прокидывается `progress_cb`) и проверяют его между шагами (после каждого
T — не начинать следующий, выйти со `status='cancelled'`). Для
одношаговых задач (обычный live-прогноз, единичная закачка тикера) —
отмена, запрошенная пока задача уже выполняется, не гарантированно
прерывает на середине (нет безопасной точки останова внутри одного
numpy-вызова) — начнёт действовать на СЛЕДУЮЩЕЙ проверке или просто не
успеет, если задача короткая. Если задача ещё `'pending'` (не начата) —
отмена всегда мгновенная, просто не ставится в очередь на выполнение
(и/или отбрасывается воркером, если уже вытащена из очереди но выполнение
ещё не начато).

**Возобновление** — не новая задача, тот же `task_id`:
```python
async def resume(self, task_id: int) -> None:
    """Разрешено для status in ('cancelled','interrupted','error')."""
    async with open_db(self._db_path) as db:
        await update_task(db, task_id, status="pending", cancel_requested=0)
    self._cancelled.discard(task_id)
    await self.submit(task_id)

async def resume_all(self) -> list[int]:
    """Кнопка «Запустить всё» — возобновляет все cancelled/interrupted/
    pending разом, по порядку created_at (не одновременно — см. 3.1,
    воркер всё равно последовательный, просто наполняет очередь целиком)."""
```
Задача при повторном запуске **сама** определяет, что уже сделано (для
калибровки — какие T уже есть в `forecast_settings` для этого `pool_key`,
пропустить; для закачки пула — какие тикеры уже имеют покрытие на нужный
интервал, тот же принцип, что уже реализован в `/candles/fetch`
full/incremental). TaskManager не хранит и не восстанавливает
промежуточное состояние сам — вся идемпотентность на стороне движка,
через уже существующие в БД чек-пойнты. Это следствие решения «без
настоящей паузы»: не нужно сериализовывать состояние выполнения отдельно,
достаточно того, что уже пишется по ходу дела.

**Регистр движков** — по паттерну band-plan 5.3, здесь не дублируется
(см. тот документ, раздел 5.3, который теперь ссылается сюда за деталями
персистентности/отмены/восстановления — это две части одной и той же
переделки `TaskManager`, разнесены по документам только потому что второй
документ нужен куда шире одного band_lambda).

**Принципиальное решение (2026-07-31): `TaskManager` работает только с
«сырыми», независимыми задачами — никакой композиции/групп/зависимостей
между задачами он не знает и не хранит.** Когда band-forecast плану
понадобилось «сначала догрузить тикеры пула, потом посчитать калибровку»
(`docs/plans/band_forecast_migration_plan.md`, раздел 5.2) — это решается
**целиком на стороне вызывающего роута**: он создаёт N задач `candle_fetch`
и следом задачу `calibration`, кладёт их в очередь в этом порядке. Очередь
строго FIFO с одним воркером (3.1/3.2) — этого достаточно, чтобы порядок
выполнения совпал с порядком постановки, никакой отдельный механизм
«задача A блокирует задачу B» не нужен и сознательно не строится. Для
`TaskManager` это просто N+1 независимых строк в `tasks`, он не знает, что
они как-то связаны — простота модели (одна задача — самодостаточная
единица) важнее, чем экономия числа задач в списке или визуальная
группировка. Если позже понадобится группировка в UI — это решается на
уровне отображения (например, общий префикс в `label`), не на уровне
модели данных/очереди.

### 3.3 API-роуты (`sma/api/routes/tasks.py`)

- `GET /tasks?status=&kind=&limit=` (новый) — список задач, дефолт
  сортировка `updated_at DESC`. Питает UI-менеджер.
- `POST /tasks/{id}/cancel` (новый) — `tm.request_cancel(task_id)`,

- `POST /tasks/{id}/resume` (новый) — `tm.resume(task_id)`, разрешено для

- `POST /tasks/resume-all` (новый) — `tm.resume_all()`.
- `GET /tasks/{id}`, WS `/tasks/{id}/ws` — без изменений.

`sma/core/db.py`: новая `list_tasks(db, status=None, kind=None, limit=100)`
(обобщение уже существующего `list_pending_tasks`, которая теперь просто
частный случай `list_tasks(status="pending")` — саму `list_pending_tasks`
можно удалить, дублирующий код).

  «Менеджер тикеров» (`sma/ui/index.html`), тот же generic
  `.accordion`/`toggleAccordion(this)` механизм. Свёрнут по умолчанию (тот
  же принцип, что и у менеджера тикеров).
  - Кнопка **«Запустить всё»** (видна/активна, только если есть
    `cancelled`/`interrupted`/`pending` задачи) → `POST /tasks/resume-all`.
  - Полный список задач: `label`, бейдж `kind`, бейдж статуса (цвет:
    pending=серый, running=синий+прогрессбар `done/total`, done=зелёный,
    error=красный, cancelled=жёлтый, interrupted=оранжевый), кнопка
    действия по статусу — running→«Отменить»
    (`POST /tasks/{id}/cancel`), cancelled/interrupted/error→«Возобновить»
    (`POST /tasks/{id}/resume`), done — без кнопки (возможно ссылка на
    результат — для forecast это уже готовый `forecast_id` из
    `output.forecast_id`).

**Обновление — единый polling, не WS-мультиплексирование, работает
постоянно (не только пока аккордеон открыт).** Раз всегда-видимая секция
«Текущая задача» должна отражать статус независимо от того, свёрнут
аккордеон или нет — таймер на `GET /tasks` больше нельзя гасить при
сворачивании (в отличие от исходного черновика этого раздела). Один
`setInterval` (интервал в несколько секунд — таблица маленькая, лишней
нагрузки нет) питает и секцию «Текущая задача», и содержимое аккордеона,
когда он открыт — не два отдельных запроса. Точечный live-прогресс
конкретной только что запущенной задачи (например, из формы прогноза)
остаётся на существующем WS `/tasks/{id}/ws`, как сейчас — не меняется,
это дополнение к polling, не замена.

Верстка — переиспользовать паттерн `.ticker-row`/`.quick-row`
(`sma/ui/style.css`, `sma/ui/tickers.js`) визуально: иконки-кнопки,
бейджи, компактная всегда-видимая секция сверху + тяжёлый список в
аккордеоне снизу — та же композиция, что уже есть у тикеров. Не
копировать код 1:1 (разная структура данных), но одинаковый визуальный
язык и структура файла/секций.

  (`sma/api/routes/forecasts.py:33-51`, `ForecastTaskResponse`) — не
  изобретается новый паттерн ответа, копируется существующий. `label`
  задачи — `f"Загрузка {ticker} [{interval}]"` (full) или
  `f"Дозагрузка {ticker} [{interval}]"` (incremental — определяется тем же
  способом, что и сейчас, до постановки в очередь, чтобы сразу показать
  осмысленный label, не «неизвестно»).
- `upsert_instrument` (создание/обновление записи тикера) остаётся
  **синхронным**, до постановки задачи в очередь — это быстрая операция
  (одна запись в SQLite), пользователь должен видеть новый тикер в «Мои
  тикеры» сразу после клика «+ Добавить», не дожидаясь своей очереди на
  скачивание данных.

**Frontend (`sma/ui/tickers.js`)**: `fetchTickerInterval()` (сейчас —
`sma/ui/tickers.js:168-183`, `await api('POST', '/candles/fetch', …)` с
прямым ожиданием результата) переписывается по образцу
`forecast.js:submitForecast()`/`connectWS()` — тот же паттерн, тот же файл
`forecast.js` как референс, ничего нового не изобретается:
1. `POST /candles/fetch` → `{task_id}`.
2. `setStatus('Задача #… поставлена в очередь', 'ok')` — честно показать,
   что это не мгновенно (особенно важно, раз очередь последовательная —
   см. предупреждение в разделе 1: если в очереди уже что-то долгое,
   ожидание может быть заметным).
3. Подписка на `/tasks/{task_id}/ws` (тот же `connectWS`-паттерн, либо
   буквально импортировать и переиспользовать из `forecast.js`, если
   сигнатура позволяет — не дублировать WS-код).
4. По `status:'done'` — тот же постобработчик, что сейчас выполняется
   синхронно после `await`: если это текущий открытый тикер/интервал —
   `window.loadCandles(...)`; в любом случае — `refreshAll()` (обновить
   список тикеров/покрытие).
5. Кнопка ⟳/«Обновить» в тулбаре — `btn.disabled` снимается сразу после
   получения `task_id` (не после завершения задачи, задача теперь видна и
   управляема через менеджер задач, а не только через саму кнопку).

## 4. Порядок выполнения

**Больше не зависит от band-forecast плана как предпосылки** (правка
2026-07-31, после добавления 3.5) — раньше здесь было написано, что без
многошаговой задачи (калибровки) нечем проверить отмену/восстановление.
Это было верно до решения перевести `candle_fetch` в очередь: теперь есть
**уже существующий, уже рабочий** тип задачи, на котором можно построить
и полностью проверить весь TaskManager (включая честную симуляцию сбоя
процесса) даже без единой строчки band_lambda. Более того — так надёжнее:
инфраструктура очереди обкатывается на простом, отлаженном коде, а
band_lambda встраивается уже поверх проверенной основы, не одновременно
с ней.

1. Схема БД: `tasks.kind/label/cancel_requested/updated_at` (3.1). Не
   привязано к band-plan миграции — можно делать независимо, раньше.
2. `list_tasks()` в `db.py`, удалить дублирующий `list_pending_tasks`.
3. `TaskManager`: `_reconcile_after_restart`, `request_cancel`/
   `is_cancel_requested`, `resume`/`resume_all` (3.2).
4. Роуты `tasks.py` (3.3).
5. **`candle_fetch` как первый и сразу проверяемый тип задачи** (3.5) —
   перенос уже работающей логики `POST /candles/fetch` на очередь,
   правка `sma/ui/tickers.js`. Это даёт полностью рабочий, тестируемый
   end-to-end TaskManager (список, отмена, «Запустить всё», восстановление
   после `kill -9`) без зависимости от band-forecast плана.
6. Фронтенд: `tasks.js` + аккордеон-секция (3.4) — можно проверять уже на
   шаге 5, не дожидаясь калибровки.
7. Сквозная проверка на `candle_fetch` (раздел 5) — TaskManager к этому
   моменту полностью готов и обкатан.
8. Дальше, уже отдельно (в рамках band-forecast плана, не этого): порт
   `run_calibration_task`/`run_pretest_task` пишется сразу с поддержкой
   `should_cancel` — переиспользует готовую инфраструктуру, не строит
   параллельно с ней.

## 5. Проверка

Основной тестовый объект — **`candle_fetch`** (уже существует, не ждать
band_lambda):

- `GET /tasks` без задач → пустой список, UI показывает «нет задач» без
  ошибок.
- Регрессия контракта `/candles/fetch`: старый ответ (`200 + FetchResult`)
  ожидался фронтом синхронно — убедиться, что после правки НЕТ мест,
  которые всё ещё пытаются читать `candles_saved`/`mode` из немедленного
  ответа (только из финального WS-сообщения/через `GET /tasks/{id}`).
  Проверить `grep` по `sma/ui/` на `candles_saved` — не должно остаться
  вне нового пути через задачу.
- Запустить дозагрузку нескольких тикеров подряд (клик ⟳ на 3-4 строках
  «Мои тикеры» быстро друг за другом) → список задач показывает их все,
  выполняются строго по одной (не параллельно — проверить через `ps`/
  нагрузку CPU, не должно быть нескольких скачиваний одновременно).
- Отменить во время выполнения → задача останавливается (для `candle_fetch`
  чек-пойнт естественный только один — между «скачал»/«записал в БД», так
  что отмена реалистично либо ничего не успевает прервать на короткой
  дозагрузке, либо отменяет ещё не начатую в очереди — оба исхода корректны,
  не баг).
- **Симуляция сбоя**: убить процесс приложения (`kill -9`) во время
  выполнения задачи → перезапустить → задача в статусе `interrupted`
  (не потеряна, не зависла в `running` навечно) → «Запустить всё» →
  задача выполняется заново (для `candle_fetch` инкрементальная логика уже
  сама не перекачивает лишнее — полноценный тест идемпотентности «бесплатно»
  благодаря уже существующему full/incremental механизму).
- UI: секция «Текущая задача» показывает running-задачу **даже когда
  аккордеон «Менеджер задач» свёрнут** (это и есть смысл правки — раньше
  в этом разделе был написан обратный вариант, «остановить polling при
  сворачивании» — исправлено на «polling работает всегда», см. 3.4).
  Запустить дозагрузку, свернуть аккордеон, убедиться, что прогрессбар
  в верхней секции всё равно обновляется. Дождаться завершения — секция
  переходит в «Нет активных задач» (или показывает следующую из очереди,
  если она была).

Отдельно, уже на стороне band-forecast плана (после портирования
калибратора, не блокирует эту проверку): то же самое для `calibration` —
отмена между T оставляет частично посчитанные T в `forecast_settings`,
восстановление продолжает с недостающих T.
